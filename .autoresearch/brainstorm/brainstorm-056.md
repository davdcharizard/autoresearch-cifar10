# Brainstorm EXP-056

## Web Search & Literature Review
- **AugMix (Hendrycks et al., ICLR 2020)** + **TrivialAugment (knowledge/papers/trivialaugment.md)**: the diversity that helps CIFAR top-1 comes from a broad pool of GEOMETRIC (rotate, shear, translate, scale) and PHOTOMETRIC (brightness, contrast, color, sharpness, posterize/solarize/equalize) ops applied with random magnitude. The current pipeline only covers translation (RandomCrop) + reflection (flip) + occlusion (Cutout); rotation/shear/scale and photometric ops are NOT covered except via the (wall-limited, subset-only) CPU AugMix.
- **torch.nn.functional.affine_grid + grid_sample** (core torch 2.9.1, no new dep — confirmed): batched, per-sample-parameterized affine warps (rotation/shear/scale/translate) run as a single GPU kernel on a (B,3,32,32) tensor — sub-millisecond on an H20. Photometric ops (brightness = scalar mul, contrast = lerp toward batch/grey mean) are trivial batched tensor ops. This is the mechanism to deliver rich augmentation GPU-side.
- No external paper search this loop — the relevant references (AugMix, TrivialAugment) are already distilled in the knowledge base; this loop is an engineering-direction pivot grounded in project history.

## Experimental History Review
- **The ONLY lever that lifts top-1 here is augmentation diversity** — every single improvement in the project's history is capacity (EXP-000/001) or augmentation (EXP-002 Cutout, **EXP-003 Cutout CPU→GPU +0.58**, EXP-012 TrivialAugment, EXP-052 AugMix, EXP-054 AugMix-subset). All other axes (optimizer/gradient/objective polish, normalization, schedule, classifier-head, feature-routing, capacity both ways) are CLOSED. [project-insights.md High Importance; goal-learnings § Patterns]
- **As of EXP-055 the CPU-side augmentation-diversity lever is MAPPED at its feasible frontier = w3 / p=0.5 = 96.45**: magnitude null (EXP-053), width>3 regressed (EXP-055 −0.44pp), coverage<50% under-regularizes (EXP-055). [goal-learnings § Failed Approaches]
- **The binding constraint that caps the proven lever is the CPU dataloader WALL** (NUM_WORKERS=8, frozen): heavy PIL augmentation starves the 8 workers → wall blows toward 600s, forcing the rich AugMix to a coverage-limited SUBSET (EXP-052/054). The GPU is IDLE ~6-7ms of every 14.8ms wall-step (dt=8ms GPU compute, ~6.8ms dataloader-wait starvation). [goal-learnings § Protocol Findings High Importance]
- **DIRECT PRECEDENT for the GPU-augmentation move**: EXP-003 moved Cutout from a per-sample CPU transform to a vectorized GPU batch op → recovered epochs (per-sample CPU `.item()` syncs throttled throughput ~30%, EXP-002) AND was a +0.58pp improvement (95.42→96.00). goal-learnings § Low Importance (EXP-002): "vectorize/GPU-side augmentation recovers epochs and compounds accuracy." Cutout already runs GPU-batched in the train loop (`cutout_batch`) — the pattern is proven and in-codebase.
- **Budget mechanics**: budget gates on Σdt (GPU step time, 300s). CPU augmentation is "free" w.r.t. Σdt (runs on parallel workers) but costs WALL. GPU augmentation costs Σdt (epochs) but not dataloader-wall. Key insight: the current wall has ~6-7ms/step of WASTED dataloader-wait; moving cheap augmentation onto the idle GPU and lightening the CPU pipeline can convert wasted wall into useful full-coverage diversity at a small epoch cost.
- **Untried gap**: GPU-side augmentation BEYOND Cutout (geometric affine, photometric) — confirmed absent from the experiment index.

## Candidate Ideas

### 1. GPU-batched diverse augmentation (affine + photometric), full-coverage — the throughput unlock
**Summary**: Implement a vectorized GPU augmentation applied to the full batch in the train loop (alongside the existing `cutout_batch`), and LIGHTEN the CPU pipeline to just RandomCrop+Flip+ToTensor+Normalize (remove the CPU `RandomApply([AugMix()])`). The GPU op: per-sample random AFFINE warp via `affine_grid`+`grid_sample` (rotation ∈ ±~15°, shear ∈ ±~0.1, scale ∈ ~[0.9,1.1]) + cheap PHOTOMETRIC jitter (random brightness scalar, contrast lerp toward per-image mean). All per-sample-parameterized via seeded `torch.rand`, full-coverage. This delivers the proven diversity lever (geometric+photometric, currently only reachable via wall-limited subset CPU AugMix) to 100% of images, off the CPU dataloader and onto the idle GPU.
**Reasoning**: Directly attacks the binding constraint (CPU wall) that caps the only working lever — the explicit top recommendation from EXP-055/053/052 analyses. Strong in-project precedent: EXP-003 did exactly this for Cutout (CPU→GPU) and won +0.58pp. The GPU has ~6-7ms/step idle (dataloader starvation); a sub-ms affine+photometric op converts wasted wall into full-coverage diversity. Lightening the CPU pipeline DROPS the wall (no AugMix starvation), buying margin; the small dt increase costs a few epochs (probe + gate). Full-coverage geometric (rotate/shear/scale) is genuinely NEW augmentation (current pipeline has none of it) applied to ALL images vs the winner's 50%-subset.
**Sources**: EXP-003/002 (goal-learnings § Patterns/Low; tsv row 003 +0.58); EXP-052/054/055 (wall-limited subset frontier); knowledge/papers/trivialaugment.md, AugMix; torch F.affine_grid/grid_sample (core, confirmed no new dep).
**Estimated Effort**: medium (new ~25-line GPU aug function mirroring `cutout_batch`'s batched, seeded, no-CPU-sync style; one CPU-pipeline edit; dt/epoch probe).
**Risk Assessment**: (a) **Epoch wall** — if the GPU aug adds too much dt (grid_sample memory traffic), epochs drop and the net under-trains (the recurring killer: EXP-002/004/038). Mitigated: affine+photometric on (128,3,32,32) is sub-ms on H20, and lightening CPU recovers wall; probe dt early and gate (abort if dt > ~10ms / epochs < ~80). (b) **Diversity mismatch** — GPU affine+brightness/contrast is a SUBSET of AugMix's op pool (no posterize/solarize/equalize/autocontrast); full-coverage may not match subset-AugMix's richer per-image ops → within-noise null. (c) grid_sample padding/interpolation artifacts (use padding_mode='reflection', bilinear). Worst case: clean no-improvement that still VALIDATES the GPU-aug infrastructure for richer follow-ups.

### 2. Augmentation strength annealing over training (compute-neutral)
**Summary**: Decay the CPU AugMix application probability `p` (or severity) over training — strong diversity early (p=0.5), annealing toward near-clean (p→0) in the final ~20% of steps — so late epochs converge on near-clean data. Implemented by recreating/ramping the transform or gating AugMix application by training fraction.
**Reasoning**: The model is mildly UNDER-converged at 300s (final_test_loss ~0.197, EXP-054). Heavy augmentation throughout fights final-epoch convergence; annealing aug late is a known trick (matches LR-anneal-to-0) that can sharpen the final optimum. Compute-neutral (CPU-side, no epoch-wall risk), low implementation risk, and a genuinely untried axis (aug-over-TIME, distinct from the closed LR-schedule and the mapped aug-strength axes).
**Sources**: EXP-054 (under-convergence signal); goal-learnings (schedule axis = LR only, aug-time untried).
**Estimated Effort**: low-medium (per-step/epoch gating of AugMix by training fraction; the train loop already tracks the time fraction for LR).
**Risk Assessment**: Speculative magnitude — may be within the ±0.25pp noise band. Confound: changes total augmentation exposure (less aug overall) which EXP-055 showed can hurt; must anneal only LATE to preserve early diversity. Fails gracefully to no-improvement.

### 3. RandomCrop padding amount sweep (4→6/8) — minimal safe diversity probe
**Summary**: Increase `RandomCrop(32, padding=4)` → `padding=6` or `8`, widening the translation-augmentation range. CPU-cheap (negligible), full-coverage, compute-neutral.
**Reasoning**: Translation magnitude is an augmentation-diversity dial that's never been swept (EXP-037 tried padding-MODE, not AMOUNT). A wider crop range adds translation diversity to all images essentially for free.
**Sources**: EXP-037 (padding-mode null, amount untried); standard CIFAR practice (pad 4 is default; some recipes use more).
**Estimated Effort**: low (one-number change).
**Risk Assessment**: Low EV — padding 4 is the well-tuned CIFAR default; larger padding can push crops too far off-object and mildly hurt. Likely within-noise null/small regression. Very safe, very fast.

## Idea Evaluation
The strategic situation is decisive: the only lever that has EVER moved top-1 on this project is augmentation diversity, and it is now mapped to its CPU-feasible frontier — every remaining gain on this lever lies on the far side of the CPU dataloader wall. Two of the three candidates (2, 3) operate within the already-mapped CPU augmentation space: #3 sweeps a single translation dial that is at its tuned default (low EV), and #2 tests an untried aug-over-time axis but is speculative and risks the very coverage-reduction that EXP-055 showed hurts. Neither attacks the binding constraint.

Candidate 1 is the one move that does. It has the strongest evidence of any option: a DIRECT in-project precedent (EXP-003 moved Cutout CPU→GPU and won +0.58pp, with the recovered-epochs mechanism recorded as a goal-learning), a clear and quantified mechanism (the GPU is idle ~6-7ms/step while the CPU starves; affine+photometric is sub-ms; lightening the CPU recovers wall), and it unlocks the exact thing the lever is starved for — full-coverage rich diversity. Its mechanism is clear, its expected impact is the highest (it can deliver to 100% of images what the winner only reached on 50%), and although its effort is medium and it carries an epoch-wall risk, that risk is the project's best-understood failure mode with a ready mitigation (cheap op + dt/epoch gate) and a graceful failure (a no-improvement that still builds reusable GPU-aug infrastructure). Evidence, mechanism, and impact all favor #1 decisively; #2 is the lower-risk fallback for a future loop.

## Chosen Idea
**Selected**: Candidate 1 — GPU-batched diverse augmentation (affine + photometric), full-coverage, replacing the wall-limited CPU AugMix.

**Why this idea**: It is the only candidate that attacks the binding constraint (the CPU dataloader wall) that caps the project's single proven lever, it has a direct winning precedent (EXP-003 Cutout CPU→GPU, +0.58pp), and it unlocks full-coverage rich diversity that was previously wall-unaffordable. Highest evidence, clearest mechanism, highest expected impact; the epoch-wall risk is well-understood and gated, with a graceful failure that still yields reusable GPU-augmentation infrastructure.

**Hypothesis**: Moving augmentation off the starved 8-worker CPU dataloader onto the idle GPU — a sub-ms batched affine (rotate/shear/scale) + photometric (brightness/contrast) op at full coverage, with the CPU pipeline lightened to crop+flip — will keep dt within ~1-2ms of the 8ms baseline (epochs ≥ ~80) and the wall comfortably < 600s. Prediction: IF full-coverage geometric+photometric diversity regularizes at least as well as the 50%-subset CPU AugMix net of the modest epoch cost, best_test_acc ≥ 96.55 (bar = baseline 96.45 + 0.1). A within-noise null would still validate the GPU-augmentation path and localize whether the missing photometric ops (posterize/solarize/equalize) are what the lever needs.
