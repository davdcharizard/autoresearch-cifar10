# Idea Review EXP-033

## Prioritized Feedback

1. **The three-point terminal average is the strongest candidate, but the accepted best-final gap is not itself evidence of stochastic iterate variance.** EXP-027's 94.32% best versus 94.22% final can also reflect ordinary late overfitting, sparse evaluation, or the final partial epoch; one deterministic trajectory does not identify noise as the cause. The proposal is still well targeted because it changes the boundary representative at near-zero counted cost, the local weight-averaging note supports carefully windowed averages, and EXP-013 leaves short parameter-only averaging genuinely open. Refine the claim to a falsifiable exploratory mechanism rather than an inferred diagnosis, and keep `final_test_acc >= 94.42%` as the required mechanism-support condition even if an earlier live evaluation raises the primary `best_test_acc`.

2. **Terminal live BatchNorm buffers are the averaging proposal's principal unresolved assumption, and semantic preflight cannot validate their statistical compatibility.** `idea-03.md` correctly avoids the invalid operation of averaging running variances and avoids unbudgeted recalibration, but averaged convolution weights and BN affine parameters need not be calibrated to the terminal live moments. The short 95/97.5/100% clean-tail window makes this materially different from EXP-013's 65%-start whole-state EMA, not immune to the same class of mismatch. Preserve the fixed live-buffer policy, log exact snapshot steps/times, prove buffers remain bitwise terminal, and pre-register that a normal-exposure endpoint regression implicates either parameter-space curvature or BN mismatch without authorizing an adjacent window or recalibration rescue.

3. **The checkpoint timing and restoration contract must cover the exact production sequence, not only arithmetic in isolation.** The proposal charges the two in-training device clones before the existing synchronization, while terminal backup, averaging, evaluation, and restoration occur in the excluded evaluation interval. Verify that each threshold decision uses the stated pre-step time, each snapshot is the first post-update state whose pre-step time is at least 285.0/292.5 seconds, clone work is included in that step's `dt`, and neither snapshot is registered in the module or optimizer. The exception-injection test, stable clone-window CV, `>=99%` throughput retention, wall projection, object-ID/optimizer-reference checks, unique terminal evaluation, and final restoration should all remain hard fail-closed gates.

4. **Batch 512 has the largest systems ceiling but weak alignment with the diagnosed accuracy limiter.** `02-system-understanding.md` shows 98% of step time is forward/backward and 98.9% memory headroom, so measuring larger-batch utilization is justified. However, even at the 1.10x gate it performs about 14.3k updates versus 25,978 accepted, halves BN and batch-shared-mixup decisions, and doubles the examples sharing each coefficient. EXP-009, EXP-016, and EXP-028 already show that 159-172 passes do not compensate for altered optimization or adaptation. Treat the four-constant candidate as an indivisible exploratory optimizer operating point, not an optimization-equivalent speedup; retain the complete-body reciprocal-rate gate, real-loader/wall gate, and prohibition on adjacent batch/LR/momentum repairs.

5. **The batch-512 gate establishes feasibility, not accuracy evidence, and the extra evaluation opportunities need explicit reporting.** A passing `>=146.308096` projected-pass gate proves useful H20 image rate but cannot prove that doubled LR and roughly 45% fewer Nesterov decisions preserve boundary quality. Because higher throughput creates more epochs and every-fifth-epoch evaluations, report the unique evaluation count and best-final gap so a maximum-over-more-checkpoints effect is visible. Keep `best_test_acc >=94.42%` as the sole goal verdict and final accuracy/loss as corroboration; a valid miss closes the exact `512, 0.4 -> 0.004, 32000-cap` operating point after one run.

6. **Alpha 0.1 offers the cleanest attribution but has no observed over-regularization symptom and sits in a uniformly negative local neighborhood.** `idea-01.md` accurately distinguishes weaker concentration from the failed alpha-0.4 direction and protects batch-shared coefficients and the 65% duration. Yet EXP-002 made alpha 0.2 the strongest standalone gain, EXP-004/005/015/020 rejected nearby duration, strength, and correlation changes, and EXP-027 improved both accuracy and loss with no evidence that its composition is too regularized. Preserve the one-line diff, distribution/RNG checks, normal-exposure gate, and fixed-seed interpretation, but present it as low-confidence family closure rather than the likely next improvement.

7. **Do not over-interpret any fixed-seed ten-example win.** All three proposals use the mandated seed 42 and target a 0.10-point change, while alpha changes the CUDA draw trajectory, batch 512 changes packing and decision count, and averaging changes only one evaluator-entry state. These are legitimate treatments, not rerolls, but no one-shot outcome estimates multi-seed robustness. Apply the same primary threshold, integrity audit, no-rerun rule, and exact-family closure to the selected experiment; mechanism corroboration can qualify the conclusion but cannot replace the registered metric.

## Pick

**Short Predetermined Parameter Averaging.** It wins because it attacks the diagnosed late generalization/boundary problem while preserving the accepted model, optimizer trajectory, full-gradient update count, augmentation stream, batch statistics, and every earlier evaluation. It is materially different from the failed long-horizon whole-state EMA: only three predetermined clean-tail parameter states are averaged, the terminal state retains one-third weight, and live BN buffers are never averaged. Batch 512 has a higher hardware ceiling but weak accuracy alignment and substantially coarsens the learner; alpha 0.1 is cleaner but is a low-upside closure test in a negative neighborhood. Advance the exact `[95%, 97.5%, 100%]` average only with production-sequence timing, complete restoration/finite/state-integrity checks, fixed terminal-live BN semantics, a single terminal averaged evaluation, and the separate `final_test_acc >=94.42%` mechanism criterion.
