# Plan Review EXP-033

1. **[Code Changes / Milestone 2 / Verification 3 and 6] The plan promises unchanged live behavior/trajectory outside the terminal view, but its required counted snapshot copies necessarily change the post-95% training trajectory.** Each clone is included in `dt`, so it advances `total_training_time`, changes every later time-derived LR/progress value, and can remove a terminal optimizer step relative to `67c8e98`. A construction/RNG identity preflight cannot prove the stronger invariant. Replace the impossible identity requirement with an exact prefix invariant through the first due snapshot plus explicit bounds/audits for the intended timer-only divergence afterward (snapshot cost, LR/time offset, and lost steps/passes); otherwise a verifier may either reject every correct implementation or silently certify a false isolation claim.

2. **[Verification 6] “RNG unchanged around averaging” is invalid if the interval includes the evaluator call and is under-specified if it does not.** The frozen evaluator constructs a DataLoader iterator, whose ordinary worker/base-seed setup may consume the main-process CPU RNG even with `shuffle=False`; a fake evaluator that consumes no RNG cannot establish production equivalence. Assert that backup/install/restore arithmetic itself consumes no RNG, and separately require the candidate terminal path to have the same RNG delta as one call to the accepted evaluator. Do not restore evaluator-consumed RNG, because that would itself depart from the frozen accepted behavior.

3. **[Milestone 3 / Verification 10] The scored-run evidence cannot support the required “exact live-state restoration.”** Equality of one logged finite scalar checksum before install and after restore is collision-prone: offsetting corruption in two parameters passes, and the plan calls the checksum diagnostic while simultaneously using it to back a hard restoration condition. Use a fail-closed elementwise/bitwise comparison against the terminal backups for every parameter after `finally` (logging a compact pass flag and first mismatch), or a byte-level digest with parameter names/shapes; keep the scalar only as informational output.

4. **[Milestone 2 / Verification 7-8] The timing treatment is ambiguous about what `incremental_snapshot_s` measures, so the exposure gate can double-charge or under-charge the intervention.** Step 7 says to measure “two ... snapshots” against undefined “no-op/control copies,” while step 8 multiplies the resulting increment by two. Define one timed treatment as exactly one production `detach().clone()` sweep over all parameters, define the control as the same loop/synchronization without allocation/copy, report paired per-window differences, and then multiply that per-snapshot median by two. Time the terminal sequence separately as exactly one backup plus the actual fixed-order arithmetic/install/restore, including synchronization; otherwise the preregistered retention and wall projections are not reproducible.
