# Adversarial Plan Review EXP-044

## Prioritized Concerns

1. **[Verification Procedure 6-8 / statistic autograd] The plan never independently qualifies the nonzero adapter-to-feature gradient that governs essentially the entire scored trajectory.** Step 6 proves the adapter-weight gradient at `D=0`, but its requested zero dispersion contribution to feature/backbone gradients is true for any implementation of `sigma` because multiplication by `D=0` blocks that path. Step 8 checks only that a post-update contribution is finite and nonzero. Neither check verifies PyTorch's `torch.var(..., correction=0)` backward against the required population-standard-deviation derivative `(x-mu)/(64*sqrt(var+1e-5))`, including centering, the `1/64` factor, epsilon, and reduction over exactly the two spatial axes. Add a deterministic nonconstant fixture with fixed nonzero `D` and an independent FP64 feature-gradient/JVP or scalar-objective oracle; also require an exactly constant channel's statistic gradient to be zero, not merely finite. Otherwise a wrong-axis, wrong-scaling, or otherwise incorrect backward path can pass every semantic gate and be scored.

2. **[Verification Procedure 5 / exact-neutral claim] The common-gradient acceptance bounds are too loose to establish the plan's central isolation claim.** At zero adapter weight the treatment is mathematically required to preserve all common first-step gradients, yet `rtol=3e-3, atol=2e-4` can accept a 0.3% relative error and can completely mask changes in small gradients. This is materially weaker than the exact common-gradient result achieved for the closely analogous zero-start EXP042 and conflicts with the stronger exact requirements for logits/state/RNG. Require byte equality where the actual graph permits it, and otherwise use per-tensor absolute and relative-L2 bounds justified by a demonstrated reduction-order difference rather than a broad blanket tolerance; explicitly fail on any changed `None` status and report the worst tensor, not only global maxima.

3. **[Verification Procedure 4-6 / production-path oracle] The plan does not specify how the harness obtains the production `spatial_std` and post-addition `hidden`, so it can accidentally test a duplicate formula rather than the code that will be scored.** Unlike EXP043's directly callable production helper, both values are forward locals. Saying to "compare production mean and std" is not executable unless the harness captures the actual adapter input (and the actual hidden sum) via hooks, an instrumented compiled candidate, or another fail-closed mechanism. The AST whitelist alone proves syntax, not runtime axes/values. Specify capture of `dispersion_adapter`'s real input and a direct reconstruction from captured `features`, and tie the gradient oracle to that same production call.

4. **[Verification Procedure 6-7 / gradient and update oracle scaling] The purported independent full-model oracle can be circular as written.** The plan gives the algebraic `dL/dD` formula but does not state whether `g_hidden` is derived independently from logits, labels, classifier/head weights, ReLU mask, residual scale, mixup lambda, and mean-CE batch reduction, or simply read from candidate autograd. Using an autograd-captured `g_hidden` would only recheck the final outer product and would not catch a missing `0.1`, a missing `1/B`, or incorrect lambda weighting. Likewise, predicting every SGD update from the production gradients proves PyTorch SGD bookkeeping but not gradient correctness. Define an independent sum-objective oracle and a separately derived mean hard-CE/mixup oracle with explicit `0.1/B` and lambda factors before using those gradients in the fresh/preseeded Nesterov checks.

5. **[Verification Procedure 10-11 / timing pairing] The four whole-run retentions combine early and hard pair index `i` without defining a common temporal block for those measurements.** If early and hard `A/C/C/A` cycles are run as separate regime batches, `early_i` and `hard_i` are unrelated points in a drifting GPU timeline; arbitrary index pairing can change the "every retention" gate and its CV. Preregister a single blocked schedule that measures each accepted/candidate early/hard quartet locally, or conservatively evaluate all early-by-hard pair combinations. Also state exactly which four ratios feed each population CV. Without this, the 127-pass gate is not reproducible despite its precise threshold.

6. **[Verification Procedure 1, 9, and 12 / execution and score audit] Several mandatory audits are prose requirements rather than runnable, persisted checks.** In particular, the plan does not give exact commands for branch identity, frozen-file hashes/diffs, ignored-harness status, GPU allocation, or compilation, and the final audit says only "one H20" without requiring the scored log's `Device: cuda` line or recording CUDA device properties/visibility from the scoring process. `nvidia-smi -L` inventory plus unchanged fallback-capable `torch.device("cuda" if ... else "cpu")` does not by itself prove the run used the intended H20. Spell out the commands and parsed assertions, persist their outputs in `03-execute.md`, and require the scoring process to report/verify CUDA and the H20 identity before treating a summary as valid.
