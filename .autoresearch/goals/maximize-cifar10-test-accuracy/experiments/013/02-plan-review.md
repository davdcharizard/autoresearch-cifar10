1. **Plan §Code Changes / §Smoke: restore invariant is false.** The SAM block restores with `p.add_(e_w)` then `p.sub_(e_w)` (02-plan.md:118-137), but fp32 add/sub is not bit-exact in general. The smoke asserts `torch.equal` for every param (02-plan.md:200-202), so M1 can fail on a correct-looking SAM implementation; if the assertion is relaxed, the plan must explicitly accept that `optimizer.step()` and coupled weight decay run on weights with tiny residual perturbation.

2. **Plan §Smoke: it does not exercise the actual SAM training step.** The snippet reimplements ascent/restore outside `train.py`’s loop (02-plan.md:175-214) and never runs the second backward, `optimizer.step()`, Nesterov momentum, coupled weight decay, `report_loss`, or the planned restore-before-step ordering. It could pass while the real block is misordered or still using the first-pass gradient.

3. **Plan §BN helpers / §Smoke: BN “first pass only” is under-verified and not fully true.** Setting BN `momentum=0.0` (02-plan.md:66-74) prevents running mean/var updates, but PyTorch BN still increments `num_batches_tracked` on the perturbed training forward; with `AveragedModel(..., use_buffers=True)` in `train.py`:255-257, that buffer is part of EMA state. The smoke only checks momentum restoration (02-plan.md:203-209), not that BN buffers remain unchanged across an actual perturbed forward.

4. **Plan §Decision + Verdict: best-of-multiple-cells inflates the chance of a noise win.** The verdict picks the best of cells A/B, plus possible lighter fallback reruns, against one same-session baseline (02-plan.md:53-57). Confirmation is only required for “thin” winners in `[96.48, 96.55)`; a selected 96.56-style one-off can pass despite the known ±0.1pp epoch-jitter/noise and the extra looks.

5. **Plan §Epoch bands / §Abort Criteria: 110-114 epochs is an undefined verdict zone.** The plan says SAM cells are acceptable at `≥115` and abort/re-run at `<110` (02-plan.md:49,166), while wins require `num_epochs ≥115` (02-plan.md:55,218). A 110-114 epoch SAM run that does not end with `best==final` is neither valid, abort, nor clearly confounded.

6. **Plan §Under-anneal tail check: `best_test_acc > final_test_acc` is too brittle.** The plan treats `best==final` as under-anneal-confounded and requires `best > final` for a win (02-plan.md:50,55,218), but both values are rounded summary metrics from noisy per-epoch evals. A valid annealed run can tie its final rounded best, and an under-trained run can have final 0.01 below best from eval noise, so this check can reject or accept for bookkeeping reasons rather than training dynamics.
