# Adversarial Plan Review: EXP-043

## Prioritized Concerns

1. **[Milestone 2; Code Changes; Verification steps 4-7 and 9] The harness has no specified way to execute the production projector it claims to verify.** The cache and projection loop are local statements inside `main()`, not an importable function, while the preflight is also required to block evaluator/test-data construction and works from synthetic fixtures. Merely importing `train.py` cannot access that local cache or invoke just the inline loop. Unless the plan specifies an AST/exact-source execution mechanism or factors the projector into production code (which would change the prescribed diff), the harness must duplicate the loop; a duplicated reference can pass all algebra, update, RNG, and timing checks while the actual loop is misplaced, omitted, or different. This is a fundamental verifier gap, not just missing test detail.

2. **[Chosen hypothesis; Milestone 4; Verification step 12] The result classification contradicts the preregistered exposure condition.** The hypothesis requires both at least 127 realized passes and `best_test_acc >=94.58`, but step 12 says a valid score below 127 passes is still the sole result and defines necessary success only by completion plus accuracy. A run at 126 passes and 94.58% would therefore be called successful by the plan even though it fails the stated hypothesis and gains accuracy under a materially different exposure regime. The plan must explicitly separate goal-metric success from hypothesis support and require realized `num_steps*256/50000 >=127` for the latter.

3. **[Milestone 3; Verification steps 9-10] The timing gate cannot reliably resolve its own 2.536% retention boundary.** It permits each four-window population CV to be as high as 5%, then compares independent accepted/candidate medians against a 2.536% cutoff with no paired-ratio uncertainty or confidence bound. Counterbalancing limits drift but does not make a noisy point estimate authoritative; a candidate slower than the cutoff can readily pass. In addition, the fixed-fixture windows do not specify use of the real persistent-worker/RandAugment loader, so the claimed "complete-step" retention may differ from the scored path. Require a paired accepted/candidate ratio criterion with uncertainty narrower than the margin and state exactly which real data-path components execute.

4. **[Hard Constraints; Milestone 2; Code Changes] Creating `experiments/043/preflight.py` is not reconciled with the literal constraint that only `train.py` may be modified.** Being under the globally ignored `.autoresearch/` tree prevents a tracked production diff, but it does not by itself create an exception to "only `train.py` may be modified by experiments." The plan needs to cite the project convention or explicit exemption that permits disposable verification artifacts; otherwise this is an unacknowledged scope violation.

5. **[Verification steps 1, 3, 8, and 11] Several mandatory audits are prose rather than executable, fail-closed checks.** Step 1 supplies no commands or pass predicates for local-data presence, branch/status, the complete allowed diff, evaluator-harness immutability, stale-log absence, or compilation. Steps 3 and 8 likewise say to require broad source, schedule, cadence, and single-device invariants without specifying how the preflight establishes them. Step 11 asks to require "one H20" from a `run.log` whose production code prints only `Device: cuda`. These gaps allow an executor to interpret the checks differently or assert facts the recorded evidence cannot prove; provide exact commands/checks and recorded outputs for each invariant.
