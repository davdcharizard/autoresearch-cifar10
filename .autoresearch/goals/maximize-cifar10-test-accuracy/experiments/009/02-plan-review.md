1. **Highest — Milestone 2 / Verification Procedure 4 does not define “production-path” tightly enough for a threshold-setting benchmark.** The production interval from `t0` through `torch.cuda.synchronize()` includes the pinned copies, LR calculation and param-group writes, progress/mixup branch, `optimizer.zero_grad`, Beta sampling and `randperm`, forward/loss, the `torch.isfinite(loss)` Boolean check (which can itself synchronize), backward, and optimizer step. The plan only explicitly promises copies plus “mixup forward/loss/backward/step”; omitting any fixed-cost portions inflates the BF16/FP32 ratio, and the expected 1.147x result has only 4.7 percentage points of margin over the 1.10 gate. Require the preflight to execute the same line-for-line timed body, with only autocast enabled/disabled, or factor that body into one shared benchmark function whose included operations are enumerated before measurement.

2. **High — Milestone 2 / Verification Procedure 4 leaves timing order and state matching open to result-conditioned choices.** “Balanced repeated 3x50-step windows with endpoint repetition” does not preregister an exact six-window order, and “a fresh production `WideResNet`” does not say whether FP32 and BF16 begin from cloned weights/optimizer state and equivalent RNG states or whether their instances continue independently between interleaved windows. Specify the order before observing timings, clone the same initialized model and optimizer state into both configurations, define how each configuration advances across its three windows, and define the ratio and CV formulas (including sample versus population CV). Otherwise drift, cuDNN/DVFS order effects, or choosing a favorable interpretation near 1.10 can decide whether the only scored run is launched.

3. **Medium — Verification Procedures 4–5 need fail-closed evaluator and exhaustive dtype assertions.** Because importing `train.py` immediately executes module-scope `evaluator = Eval()`, require patching `prepare.Eval` before that import with a dummy whose `evaluate()` raises, assert the resulting `train.evaluator` is that dummy, and assert no real `Eval`/test `CIFAR10(train=False)` construction occurred. Also require the semantic step to inspect every non-`None` parameter gradient and every created momentum buffer after backward/step, rather than an unspecified representative tensor, while explicitly asserting FP32 mixed loss and BF16 treatment logits. These checks prevent an accidental test-loader construction or a partial dtype check from passing the feasibility gate.
