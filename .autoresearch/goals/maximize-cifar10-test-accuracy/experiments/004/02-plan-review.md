Below is my prioritized concern list for Plan EXP-004. I read the plan, goal definition, brainstorm, EXP-002 report, the results TSV, and `train.py`.

---

**1. [Verification Protocol §7 / Necessary Conditions] The pass threshold sits inside single-run noise, and the protocol has no way to distinguish a real +0.10 gain from a lucky draw — yet a marginal pass gets committed as the new baseline.**
The bar is `best_test_acc >= 94.17%`, exactly +0.10 over the 94.07% baseline. The plan itself pre-registers 94.17–94.21% as "noise-sensitive," and the brainstorm calls the expected effect "modest and close to single-run noise." CIFAR-10 run-to-run std for a WRN at this budget is comfortably ~0.1–0.2%, i.e. the whole improvement window. Because seed rerolling is forbidden (correctly) and only one run is executed, there is no de-noising mechanism: a 94.18% result driven purely by variance passes verification, is classified `improvement`, and becomes the committed baseline for all future experiments — a noise-anchored ratchet. The plan flags the band but still treats any ≥94.17% as a pass. This is the most fundamental risk and it is not an implementation bug but a measurement-reliability gap the plan does not resolve.

**2. [Chosen Idea "Hypothesis" / Configuration Changes / Verification §6] The hypothesis asserts "without changing realized exposure," but exposure is not gated, and the change plausibly increases it — confounding the attribution.**
The hard-label path (`outputs = model(inputs); loss = F.cross_entropy(...)`, lines 240–241) is cheaper per step than the mixup path (elementwise mix + two `cross_entropy` calls + permutation, lines 232–238). Moving the cutoff 0.65→0.50 replaces 45s of the more expensive path with the cheaper one inside a fixed 300s counted budget, so the run likely completes slightly more steps/passes than EXP-002's 141.9. The brainstorm explicitly requires candidates to "preserve the roughly 142-pass exposure," and EXP-003 was careful to hold passes constant — but Verification lists `num_steps`/passes only as *informational* (§Informational Metrics, `num_steps * 256 / 50000`) with no gate. If accuracy moves, you cannot cleanly attribute it to "more hard-label refinement" vs. "more total exposure." Add an explicit passes check (e.g. within ~1–2% of 141.9) to the verification gates, or acknowledge exposure as a co-varying factor in the pre-registration.

**3. [Milestone 2 / Verification §8] The hardcoded parameter count `691,674` is asserted, not derived, and never appears in any prior artifact.**
Neither the EXP-002 report, the TSV, nor `train.py` states 691,674; the code computes `num_params` at runtime (line 172). Since the architecture code is untouched, the count is trivially invariant — but pinning a specific literal that no source confirms creates a spurious failure/friction path if the true WRN-16-2 count differs. Either verify the number against a run first, or drop the literal and just require "num_params unchanged vs. EXP-002."

**4. [Abort Criteria] The "one implementation fix/retry" allowance for a missing/repeated `Mixup disabled` record has no plausible trigger for a one-line constant change and slightly widens the retry surface.**
The only change is `MIXUP_END_FRACTION = 0.65 → 0.50`; the transition-print logic (lines 222–228) is untouched, so a missing or duplicated `Mixup disabled` record would indicate an unrelated pre-existing bug, not something a "fix/retry" on this change addresses. The guard that "weak accuracy never authorizes a retry" is good, but the retry clause as written is a loophole with no legitimate use here — consider removing it so the run is strictly single-shot.

**5. [Abort Criteria / "between 48% and 52%"] Minor: the transition-window check is looser than necessary and could mask a schedule regression.**
At a 0.50 cutoff the switch fires at the first step where `progress >= 0.50` (line 221), i.e. ~150.0s ≈ 50.0–50.3%. A ±2% window (48–52%) is far wider than the sub-1% jitter actually expected; tightening it to ~49.5–51% would make the check meaningful rather than always-satisfied. Not blocking, but the current bound verifies almost nothing.

No concerns on the scope of the code change itself: the diff is confined to a single in-scope constant in `train.py`, respects the read-only `prepare.py`/harness constraint, the single-H20 and once-per-epoch-eval constraints, and the `timeout 600s` kill rule. Those are sound.
