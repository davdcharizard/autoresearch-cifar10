# Adversarial Plan Review EXP-045

## Prioritized Concerns

1. **[Verification Procedure 10-11 / timing pairing] The registered schedule cannot produce the four independent local pairs that the gate claims.** The single sequence `AE,CE,AH,CH,CH,AH,CE,AE` contains only two accepted/candidate windows per regime, hence two local early pairs and two local hard pairs. Step 11 nevertheless requires four regime ratios and four combined retentions; obtaining four from these data would require reusing windows or taking cross-products, creating pseudoreplication. It also pairs early and hard measurements taken at different positions in the drift sequence. Specify two complete cycles (16 windows total) or reduce the gate consistently to two preregistered local early/hard quartets; define the exact pair indices before execution. Otherwise the precise every-retention threshold and ratio CV can be passed or failed by arbitrary pairing.

2. **[Configuration Changes / identity shortcuts] The plan's topology count is false for the accepted network.** `STAGE_BLOCKS=(2,2,3)` creates seven blocks; three have learned projections (`layer1[0]`, `layer2[0]`, `layer3[0]`), leaving four identity shortcuts, not the stated five in line 30. A preflight that implements this requirement literally will reject the correct candidate, while one that silently ignores it weakens the promised topology audit. Correct the count and enumerate the four identity blocks so the raw-`x` oracle is unambiguous.

3. **[Verification Procedure 5-7 / phase and gradient oracle] The gradient oracle does not identify which production tensor is being differentiated.** Step 5 explicitly captures the production pool input/output, but step 7 asks for "pooled-input gradients" and a four-site distribution without saying whether this means the post-pool tensor (which cannot test redistribution), the preactivated pre-pool tensor, or a duplicate standalone formula. Tie the oracle to the captured production `preactivated` tensor and projection output, use a fixed independent upstream gradient, and state the analytic `dW` and `d(preactivated)` formulas. Also require the accepted control's three non-selected phases to have zero shortcut gradient. Without those bindings, a verifier can pass while testing an unscored duplicate or only the trivial projection backward.

4. **[Verification Procedure 10-12 / timing state and peak memory] Window restoration and the memory gate are underspecified.** Accepted and candidate weights begin byte-identical but diverge after the first update, so "restoring identical model/optimizer/input/RNG state" must mean reloading the same preregistered parameter bytes and empty/preseeded momentum state before every window, not carrying either arm forward or copying one arm's evolved state into the other. Likewise, candidate peak allocation is invalid if both models coexist or peak stats include accepted/warmup allocations; require one live arm at a time and reset/synchronize peak statistics immediately before each candidate window. These omissions can bias the exposure gate or cause a false resource failure.

5. **[Verification Procedure 1 and 12 / source and resource audit] Mandatory provenance checks remain prose rather than persisted, fail-closed assertions.** "Query index," "one idle H20," "only `train.py` diff," and "frozen `prepare.py`/`pyproject.toml`" do not specify the commit/hash commands or how idleness and visibility are checked. Record and assert `HEAD`/branch, the exact `git show a7c42dc:train.py` hash, frozen-file hashes, `git diff --name-only a7c42dc`, ignored-harness status, `CUDA_VISIBLE_DEVICES`, Python CUDA device count/name, and `nvidia-smi` utilization/process state immediately before timing and again before the sole score. The log's generic `Device: cuda` line alone cannot prove the required single idle H20 ran the scored command.
