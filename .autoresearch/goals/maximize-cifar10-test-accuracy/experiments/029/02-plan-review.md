1. **[Milestone 2 / Verification Procedure 5] The exposure projection omits a batch-size-dependent part of the scored timer.** The proposed CUDA benchmark uses device-resident synthetic tensors, while `train.py` starts each counted step before the nonblocking input/target H2D copies and ends it after `torch.cuda.synchronize()`. Halving the batch doubles copy launches and other per-step host work for a given image exposure; the paced loader test begins at loader delivery and therefore does not restore this omitted counted cost. Because the plan uses the synthetic retention to enforce sharp `0.9022` / 120-pass / 46,875-update gates, it can approve a candidate that only falls below them once scored. Time pinned-host-to-device copies and the complete scored `t0`-to-synchronize body, or separately measure and add the omitted accepted/candidate cost before applying the fixed projection.

2. **[Milestone 2 / Verification Procedure 4] “Exact accepted clean-tail crop/flip replay” is underspecified and is not generally possible across batch 256 and batch 128 worker assignment.** Changing batch size changes which shuffled samples are packaged into each worker task, so persistent workers consume their crop/flip RNG streams on different sample identities even when RandAugment perfectly restores each worker's Torch RNG. The stated exemption only covers post-iteration parent RNG and does not define the actual replay oracle. Specify that replay is a paired batch-128 test with identical sampler order, worker assignment, and base-transform RNG, comparing candidate RandAugment-active-then-disabled against the same batch-128 crop/flip-only oracle; do not compare per-sample outputs to the accepted batch-256 loader.

3. **[Verification Procedure 5] The balanced timing protocol does not say that model, optimizer, and RNG snapshots are restored for every arm/path window.** Merely starting with “byte-equal models” and running A-B-B-A leaves accepted and candidate at different optimizer ages and processes twice as many examples per accepted 50-step window; measuring mixup and hard paths sequentially also makes the later path inherit a trained state. Dense-kernel timing should be largely state-insensitive, but non-finite behavior and allocator/autotune effects can still make this a weaker causal comparison than claimed. Predeclare fresh/restored identical model and optimizer snapshots, deterministic input fixtures, and private timing RNG state for every accepted/candidate and mixup/hard window, with warmup after each relevant shape switch.

4. **[Verification Procedure 6] The differential wall formula double-counts candidate compute-rate differences against a fixed counted-time budget.** `345.3 + max(0, candidate_epoch-base_epoch) * projected_epochs` compares paced epoch durations even though both scored runs always spend 300 seconds inside the counted step timer; a slower candidate epoch is offset by fewer projected epochs, not extra wall time per epoch. This can falsely abort an otherwise wall-safe candidate. Keep the absolute `45.3 + candidate_epoch * projected_epochs` projection, and make the differential projection compare loader stall outside the production `t0` timer (or subtract each arm's paced consumer time before differencing) rather than raw paced epoch durations.
