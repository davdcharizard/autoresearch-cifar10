# Adversarial Plan Review — EXP-007

1. **[Milestone 2; Verification Protocol steps 3-4] The semantic preflight can validate a hand-reproduced mutation without exercising the production transition code.** The plan says the stubbed process will bind `optimizer.param_groups` and change the first weight-decay value, while the scored implementation performs a separate inline assignment inside the `mixup_enabled and not use_mixup` branch. That proves PyTorch accepts the mutation, but it does not prove the actual branch mutates the intended live group, preserves the other group, or emits values read back after the mutation. A typo or a transition message formatted from constants could therefore pass the preflight and runtime log checks. The check should invoke the same production helper/path used by the training branch, or the transition should log the actual post-mutation values of both live groups and verification should assert them.

2. **[Code Changes; Milestone 4; Informational Metrics] The norm telemetry cannot support the planned attribution because it has no accepted-baseline control.** EXP-002 did not record the decayed-parameter norm at 65% or at the endpoint, so EXP-007's transition-to-final norm change conflates ordinary hard-label SGD updates, momentum, and the absence of decay. It cannot show that disabling decay caused “unchecked norm growth” relative to continued `5e-4` decay. Record the values as descriptive diagnostics only and do not use their direction or magnitude to distinguish the late-decay mechanism unless a genuinely comparable baseline measurement already exists; an extra baseline run would violate the preregistered single-scored-run protocol.

3. **[Code Changes; Verification Protocol step 6] Placement of the final CUDA norm reduction relative to the existing timing and VRAM snapshots is unspecified.** Current `train.py` captures `t_end` and `peak_vram_mb` before printing the summary. If `final_decayed_weight_l2` is computed during summary printing, its synchronization and temporary allocations are excluded from both reported `total_seconds` and `peak_vram_mb`, despite those values being used for constraint verification. Compute the final norm before capturing `t_end` and peak memory, or explicitly document that the diagnostic is outside those measurements and rely on the outer `timeout` for total-runtime validity.
