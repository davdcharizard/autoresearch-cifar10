1. **[Verification Procedure 9] The phase-weighted stall projection uses the wrong units.** The plan computes `.65 * active_stall + .35 * inactive_stall` per epoch and then multiplies by total projected epochs, but 65/35 are fractions of counted **time**, not fractions of epochs. Active and hard step medians can differ, so their epoch shares are proportional to `.65 / active_step_s` and `.35 / hard_step_s`; the current formula can understate candidate wall time at the exact `<500s` gate. Compute each arm's active and hard epoch counts directly (`195 / (batches * active_step_s)` and `105 / (batches * hard_step_s)`) and sum `phase_epochs * phase_stall` before differencing or forming the absolute projection.

2. **[Code Changes `throughput.json` / Verification Procedures 7-8] The persisted timing payload has no declared provenance or single-write enforcement.** An ignored stale payload from an earlier implementation, device state, or partial run can be consumed by `--loader-timing`, and ordinary overwrite behavior would also permit an accidental second throughput measurement despite the no-rerun rule. Require exclusive creation, atomic completion, and validation of the accepted commit, exact candidate diff/hash, constants, device identity, timestamp/session nonce, window counts, and pass status before loader timing reads it; fail closed if the file already exists or provenance differs.

3. **[Verification Procedures 5 and 11] The registered RandAugment lag interval is off by one.** Mixup logs `step` before executing its first hard batch, whereas RandAugment logs after the epoch's final batch increments `step`. If the threshold is first observed on batch 1 of a 97-batch candidate epoch, the legitimate lag is exactly 97; zero is impossible. Requiring `[0,97)` can reject correct production behavior. The source-faithful bound is `1 <= randaugment_step - mixup_step <= 97`.

4. **[Verification Procedure 5] “Exact clean-tail replay” does not yet pin the batch-dependent worker fixture needed to make that assertion meaningful.** Batch 512 changes batch tasks, worker assignment, dropped indices, and worker RNG consumption relative to accepted batch 256. The verifier must compare the candidate active-then-disabled loader with a crop/flip-only **batch-512** oracle using separately reset but identical sampler generators, worker base seeds, task assignment, and complete preceding active-epoch consumption, and should trace worker id plus sample index/crop/flip decisions. Otherwise equality may fail for benign packing differences or pass while checking only aggregate target order rather than per-worker RNG isolation.

5. **[Verification Procedure 12 / Informational Metrics] The primary verdict can still benefit from more metric samples without any endpoint gain.** At the projected exposure, batch 512 will normally produce about 30 evaluations versus 27 accepted, while final accuracy/loss are explicitly non-veto corroboration. That is allowed by the goal's `best_test_acc` metric, but it is not evidence that the doubled-LR learner improved boundary quality; a lone 94.42 spike with a worse endpoint would satisfy the stated mechanism language. Predeclare the exact projected/realized evaluation count and restrict the analysis claim to a fixed-protocol best-metric improvement unless endpoint behavior independently supports the optimization hypothesis.
