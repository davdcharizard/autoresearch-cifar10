## Prioritized adversarial concerns — Plan EXP-001

**1. [Execution Environment / Estimated runtime; Verification step 5] The 600 s hard ceiling and the eval-overhead lever point in opposite directions, and the plan has no control over it.**
The budget is 300 s of *counted training*, but `timeout 600s` and verification step 5 (`total_seconds <= 600.0`) gate on *total* wall-clock, and exit 124 is classified as **failure**. From the baseline: 99 epochs → `total_seconds=592.7` with only 300 s counted → ~293 s of excluded overhead, i.e. ~2.7–3 s per per-epoch eval plus startup/download. The plan's sole margin argument is "the wider model should complete fewer epochs." But (a) WRN-16-2's eval forward pass over the full 10k test set is materially more expensive per image than ResNet-20, so cost-per-eval *rises*, and (b) the accuracy hypothesis wants *more* data passes / epochs, which increases eval count. These pull against the ceiling: a genuinely good, many-epoch run is the one most likely to breach 600 s and be scored a failure. The plan provides no lever (no epoch cap, no eval-cost estimate for the new model, no reduced eval cadence — which is anyway constrained to ≥once/epoch). This is the most likely way a real improvement gets thrown out. At minimum the plan should project per-eval cost × expected epochs + startup against the 600 s wall before committing the run.

**2. [Milestone 2 smoke test; Estimated runtime] The central feasibility risk — too few data passes — is asserted, not measured, and the smoke test doesn't check it.**
The hypothesis explicitly depends on "roughly 45 or more dataset-equivalent passes" (brainstorm line 94), and the brainstorm's own risk note flags "a slower model may complete too few data passes." Yet the Milestone 2 smoke test verifies only logits shape, finite loss, and one optimizer step (line 12) — it never measures steps/sec or projects epochs-in-300 s. WRN-16-2's dominant cost is stage-1 (32 channels at full 32×32 resolution, 4 convs), which is several× ResNet-20's stage-1 FLOPs; batch 256 does not recover the throughput. The plan should extend the smoke test to time N steps and project epochs/data-passes, and abort *before* the 10-minute run if the projection is far below the ~45-pass assumption — otherwise it burns the full budget to discover an underfit.

**3. [Verification steps 1 & 6; goal Necessary Conditions] The pass threshold (+0.1 pp = 91.64%) is inside single-run noise, and `cudnn.benchmark=True` adds nondeterminism.**
The baseline 91.54% is a single seed-42 run; typical CIFAR run-to-run variance is ~0.2–0.3 pp. A result of 91.65% clears verification while being statistically indistinguishable from baseline — a marginal "pass" that games the measurement rather than demonstrating real improvement. The plan compounds this by enabling `torch.backends.cudnn.benchmark = True` (Code Changes line 29), which selects nondeterministic algorithms, so even at fixed seed the outcome has an added luck component. The plan targets ≥92.0%, which would be safely above noise — so the concern is specifically that the *verification gate* accepts a near-91.64% result. Recommend the plan treat only a comfortably-above-noise margin (e.g. ≥91.9%) as a genuine pass, or at least flag a bare pass as noise-suspect rather than a confirmed improvement.

**4. [Code Changes — model replacement] Weight initialization for the new model is unspecified.**
The existing model relies on `self.apply(_weights_init)` doing `kaiming_normal_` on all Conv2d/Linear (train.py:69–76). The plan says "Replace the ... block/model" (line 26) but never states how init is handled for the pre-act WRN — in particular the 128→10 classifier and BN affine params. `kaiming_normal_` on the final linear yields large-variance initial logits, which interacts badly with peak LR 0.2 + Nesterov in the first steps before warmup ramps. Leaving this to chance risks early divergence (only caught reactively by the non-finite-loss abort). The plan should specify init explicitly rather than inheriting the ResNet-20 convention silently.

**5. [Code Changes — LR schedule] Time-keyed LR reads a one-step-stale, sync-inclusive clock; confirm the first-step and truncation edges.**
LR is computed "from the prior completed training time" (line 28), where that clock is `total_training_time += dt` accumulated *after* `torch.cuda.synchronize()` each step (train.py:178–180). So step 1 sees t=0 → LR floor 0.002 (fine), but the schedule lags realized time by one (increasingly large) step, and cudnn autotuning on the first benchmark=True calls inflates the earliest `dt` values counted against both the 15 s warmup window and the 300 s budget. Low impact on accuracy, but the plan asserts a clean "cosine reaches 0.002 at 100%" — verify the last (overshooting) step still lands near the floor and that `training_seconds ≈ 300` (step 5) holds given the sync-inclusive per-step accounting.

**6. [Configuration Changes; brainstorm risk note — acknowledged] Simultaneous architecture + batch + LR + weight-decay changes prevent attribution.**
Noted only for completeness since the brainstorm already flags it (line 64) and pass/fail against baseline is the stated bar: a failure will not isolate whether the model, the batch-256/LR-0.2 coupling, the 5e-4 decay, or the schedule was responsible, so a negative result yields little to carry into EXP-002. Not a blocker, but the plan's execute/analysis phase should be prepared to log enough (realized LR trace, per-epoch acc) to reason about the cause rather than just the scalar.
