Below is my review of the EXP-005 plan. I read the plan (`005/02-plan.md`), the goal definition, the brainstorm (`005/01-brainstorm.md`), the EXP-002 and EXP-004 analyses, and `train.py`. Concerns are ordered hardest/most-fundamental first.

---

**1. [Code Changes / Milestone 1 / Verification step 8] The "identical RNG call sequence" claim is false, and the confound it hides is large relative to the +0.10pp bar.**
The plan repeatedly frames alpha 0.4 as a clean isolation that "preserves the seed/RNG call sequence" (Milestone 1) and changes "only one constant." But `MIXUP_ALPHA` feeds `torch.distributions.Beta` (train.py:188–191), whose CUDA sampling goes through a Gamma rejection sampler that consumes a *variable, alpha-dependent* number of underlying RNG draws per `distribution.sample()` (train.py:121). Every such draw advances the shared CUDA Philox offset, so the very next `torch.randperm` (train.py:122) — and every mixup pairing and permutation for the rest of the run — diverges from the EXP-002 trajectory starting at the first mixup batch. The measured delta is therefore *alpha change + a full reroll of the mixup pairing sequence*, not alpha alone. At the ±0.1pp scale this plan operates on, that confound is not negligible, and the plan's verification (step 8: "no seed... change") treats trajectory identity as established when it is not. This should be stated honestly in interpretation; the result cannot be attributed purely to alpha.

**2. [Abort Criteria / Verification step 7] The success threshold sits exactly on the plan's own declared noise band, yet a pass is committed as the new baseline.**
Verification step 7 requires `best_test_acc >= 94.17%`, and the Abort Criteria pre-register 94.17–94.21% as "noise-sensitive." So the minimum passing result is, by the plan's own admission, statistically indistinguishable from baseline+noise — yet on an `improvement` verdict the loop commits the change and moves the moving baseline to that value (as EXP-002 did to 94.07). Combined with concern #1 (the delta partly reflects a pairing reroll), there is real risk a noise-driven pass in [94.17, 94.21] gets locked in as a genuine gain and anchors all future experiments. The plan gives no provision to flag such a result as provisional; it treats the threshold crossing as binary. The single-seed / no-reroll constraint makes this unavoidable statistically, but the plan should at least mark a pass inside its own noise band as low-confidence rather than a clean win.

**3. [Idea rationale — brainstorm "Reasoning" / plan premise] The intervention has an explicitly weak prior and is two-sided, but the verification is one-sided.**
The brainstorm's own Risk Assessment states "There is no local evidence alpha 0.2 is under-strength," and EXP-004 already showed this WRN is *sensitive to reducing* regularization exposure — it says nothing about whether *strength* is the limiting axis. The mechanistic argument ("materially mixed examples are too rare") is asserted, not evidenced; mixup's per-batch scalar means alpha 0.4 also produces more *near-0/near-1* pass-through batches, not only more central mixes. This is fine as an exploratory probe, but the plan's framing (hypothesis: "will... raise best_test_acc to at least 94.17%") presents a coin-flip as a directional expectation. Not an execution bug, but it inflates the expected value of a run that the evidence suggests is as likely to over-regularize as to help.

**4. [Verification step 6 — `300.0 <= training_seconds <= 301.0`] Self-imposed tightness has no functional basis and could misclassify a valid run.**
The goal only requires respecting the fixed budget and completing under 10 min. The time loop (train.py:207, 270) breaks as soon as `total_training_time >= TIME_BUDGET_S`, so training_seconds is deterministically ~300.0–300.x — but pinning the ceiling at 301.0 is an arbitrary gate the goal does not demand. If an unusually slow final step (e.g. a 1s+ hitch) pushes it past 301.0, the plan's own protocol would flag an otherwise-valid run. This adds a needless invalidation surface; the constraint that matters (`total_seconds <= 600`, one eval/epoch) is already covered elsewhere.

**5. [Milestone 2 — offline distribution check] The sanity check validates the wrong distribution.**
Milestone 2 proposes sampling "fixed-seed Beta(0.2,0.2) and Beta(0.4,0.4)" offline to confirm the mass shift. Harmless, but note the run uses a *device-resident* Beta with a single scalar sample per batch (train.py:188–191, 121); an offline CPU/fixed-seed histogram confirms textbook Beta behavior, not anything about the actual per-batch dynamics or the RNG interaction in concern #1. It is decorative verification, not evidence the change behaves as intended in situ — don't let it stand in for that.

---

No scope or reward-hacking violations in the mechanical sense: the diff is genuinely one in-scope constant in `train.py`, only `train.py` is touched, `prepare.py`/harness are untouched, no dependencies added, the run is single-H20 with `timeout 600s`, and step 7 explicitly forbids result-conditioned retry (a good anti-hacking guard). The substantive risks are the attribution confound (#1) and the noise-floor threshold (#2), both of which bear on whether a "pass" is real.
