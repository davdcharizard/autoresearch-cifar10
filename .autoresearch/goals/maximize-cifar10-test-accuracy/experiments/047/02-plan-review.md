# Adversarial Plan Review EXP-047

## Prioritized Concerns

1. **[Configuration Changes line 31 / state identity] The statement that “all model state ... remain exact” is false for the scored early path and contradicts the bundled mechanism.** Candidate BatchNorm buffers intentionally follow ordinary augmented inputs, while accepted buffers follow mixed pixels; after the first early update, parameters and momentum also intentionally diverge. Only the state schema, construction bytes, optimizer membership/options, and default-path result from the same incoming state are exact. Restrict the identity claim accordingly, or the executor can either reject the intended clean-BN treatment or incorrectly report early trajectory identity.

2. **[Verification Procedure 6-8 / production-local oracle] The plan does not specify an executable way to capture the unblended production post-GAP `z` or its gradient.** `z` is a local produced by functional ReLU/GAP/flatten; a `pooled_head[0]` pre-hook sees only `z_mix`. A harness can therefore satisfy the wording by recomputing a duplicate `z` and testing that duplicate rather than the tensor used by the scored forward. Specify fail-closed instrumentation that retains the actual functional GAP output, plus a pre-hook on `pooled_head[0]` for the actual `z_mix`, and bind the forward and Jacobian comparisons to those captured tensors. Otherwise a wrong blend site or disconnected/scored implementation can pass an apparently independent oracle.

3. **[Verification Procedure 6, 8, and 9 / pairing direction] The fixed fixtures are not required to distinguish the two common direction errors.** If the harness uses the customary reversal permutation, then `p == p^-1`, so a wrong gather/scatter direction passes; if it uses `lambda=0.5`, swapping the primary and permuted weights also passes. Require at least one non-self-inverse cycle permutation and a fixed coefficient strictly different from `0`, `0.5`, and `1` for the production forward, target-alignment, and `index_add_` gradient oracle. The separate lambda-1 and identity-permutation invariants do not detect either bug.

4. **[Verification Procedure 8 / update oracle] “Nesterov updates for every parameter/buffer” conflates two different state transitions.** SGD never owns or updates BatchNorm buffers; those mutate during the forward, while only the 52 trainable tensors participate in coupled-decay momentum/Nesterov. Require independent optimizer equations for every parameter and separately compare expected BN running-stat/counter transitions and all unchanged buffers. Otherwise the verifier must either invent optimizer semantics for buffers or silently omit part of the claimed all-state check.

5. **[Verification Procedure 11-12 / timing gate] The plan lists 16 windows but does not preregister which windows form each of the four retentions, and it omits peak-stat reset placement.** For each eight-window block, explicitly pair positions `(AE0,CE1,AH2,CH3)` and `(AE7,CE6,AH5,CH4)`; arbitrary early/hard index pairing can change the “every retention” result under drift. Also reset and synchronize CUDA peak-memory statistics immediately before each candidate retained window and record the maximum candidate peak with accepted/warmup models deallocated. Without these details, the precise exposure and 2,048 MiB gates are not reproducible.
