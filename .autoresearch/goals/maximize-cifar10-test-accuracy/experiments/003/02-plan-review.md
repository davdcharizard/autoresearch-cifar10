I've read the plan, goal, brainstorm, proposal, and `train.py`. Here is the prioritized concern list.

---

**1. [Verification steps 1 & 7 / Abort Criteria — measurement validity vs. noise floor] The 0.1 pp acceptance margin is at or below single-run seed noise, and the protocol forbids any variance control.** The threshold is `best_test_acc >= 94.17%` — exactly baseline (94.07) + 0.1. Two compounding factors make a bare pass indistinguishable from noise: (a) `best_test_acc` is a *max* over ~a dozen evaluations (`epoch % 5 == 0` plus final in `train.py:274`), so it is upward-biased by favorable eval-point sampling even with no real gain; (b) CIFAR-10 WRN single-run test accuracy typically varies ±0.1–0.15 pp across seeds. The plan bans replication ("Do not reroll the seed or run a result-conditioned repeat"), which is correct per goal constraints, but it means a result of 94.17–94.22 will be classified `improvement` with no evidence it exceeds noise. This is inherited from the goal, so it is not fixable in-plan, but the plan should at minimum report the margin and flag sub-~0.15 pp passes as tentative rather than a clean CutMix win (the proposal already hedges this, but the Verification/Abort sections do not).

**2. [Milestone 2 / Feasibility & Budget — the 95% throughput gate is under-specified and self-inconsistent] Two different 95% references and an in-process timing bias.** The smoke gate (Milestone 2, Abort Criteria) requires "at least 95% of the accepted mixup path" measured by warming 20 / timing 100 steps for *both paths in one CUDA process*. But the pre-registered full-run interpretation (Abort Criteria) uses "95% of EXP-002's 141.9 realized passes" — a different, historical reference. A run can pass the in-process gate yet fall below 95% of 141.9 (or vice-versa) because in-process mixup timing ≠ EXP-002's actual environment. Additionally, timing both paths sequentially in one process gives the second-timed path warm cudnn autotune/caches; whichever path runs second is advantaged, so the comparison order can bias the ratio. Specify a single reference and control for warm-cache ordering.

**3. [Code Changes bullet 3 / Proposal "Exact Algorithm" step 2 — integer-rounding method is unspecified] The side-length rounding rule affects both the zero-area fallback rate and the exact-equality unit test.** `sqrt(1 - lambda) * 32` must be converted to integer width/height, but floor vs. round vs. `int()` is never stated. This matters concretely: with `Beta(1,1)` (uniform), `E[sqrt(1-λ)] = 2/3`, so nominal side ≈ 21 px and *nominal area ≈ 50% of the image on average* — patches are large, and the rounding choice plus center-clipping determines the realized mean pasted fraction and how often the "zero pasted area → hard-label" fallback fires. The Milestone-2 test requires `lambda_effective` to "exactly equal `1 - pasted_area / 1024`", which is only well-defined once the rounding and clip-to-bounds integer arithmetic are pinned down. Fix the rounding convention in the plan before implementation, or the test's "exact" criterion is ambiguous.

**4. [Code Changes bullet 2 — the CPU-generator rationale is partly spurious and quietly changes the RNG trajectory vs. EXP-002] "Avoids perturbing DataLoader shuffle state" does not hold for the code being replaced.** The current `mixup_batch` (`train.py:122`) draws its permutation with `torch.randperm(..., device=inputs.device)` — i.e., the *CUDA* generator — which already does not touch the CPU sampler RNG that drives DataLoader shuffling. So the stated justification for the dedicated CPU generator is not a real problem being solved. More importantly, moving lambda/coordinate sampling to a separate fixed-seed CPU generator while keeping the permutation device-local changes which RNG streams are consumed relative to EXP-002; the "single conceptual variable" / "clean one-variable comparison" claim (Proposal Recommendation) is weaker than stated because the stochastic trajectory is not identical. This won't invalidate the run, but the plan overstates the cleanliness of the comparison.

**5. [Execution Environment / Verification step 6 — "training_seconds approximately 300" hard-codes an assumption about `TIME_BUDGET_S` that the plan never verifies] Tolerance is undefined and the budget value is imported, not confirmed.** `TIME_BUDGET_S` comes from `prepare.py` (read-only, `train.py:13`) and is not quoted in the plan. All timing checks ("~300 counted seconds", "195 s transition", "105 s tail", "63–68% window") derive from EXP-002 rather than the actual budget. If CutMix overhead raises per-step `dt`, counted `training_seconds` still ≈ `TIME_BUDGET_S` (the loop is time-gated), but *data passes* drop — which is the real risk, not `training_seconds`. The verification checks `training_seconds ≈ 300` (which is nearly guaranteed by the time gate and thus a weak check) while the meaningful exposure check lives only in the informational `num_steps` derivation. Consider making the passes/exposure check a necessary condition, and state the `training_seconds` tolerance.

**6. [Abort Criteria — "permits one implementation fix/retry" on a missing/repeated transition log] Bounded, but confirm the retry is not result-conditioned.** Allowing one fix/retry when the `CutMix disabled` transition is missing or duplicated is reasonable, but the plan should make explicit that the retry is triggered only by the *log/transition defect* and never by the accuracy outcome, to stay clean of the goal's no-reroll rule. As written it is close but relies on the reader not conflating "implementation fix" with "rerun because the number was low."

Nothing else in the CutMix pixel/clone/area-correction logic (destination clone + pre-materialized donor patch in Code Changes bullet 3) appears unsound; the aliasing handling and finite-loss guard preservation are correct.
