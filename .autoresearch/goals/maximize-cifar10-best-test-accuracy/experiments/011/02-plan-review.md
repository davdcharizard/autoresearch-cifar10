Below is my adversarial concern list for the EXP-011 p=0.75 plan. I've confirmed the mechanical scope is clean — the change is genuinely one literal (`CUTMIX_PROBABILITY` at `train.py:23`, referenced only in `cutmix_collate` at line 116), `fork_rng(devices=[])` isolates the gate/cutmix draws so the transform RNG stream is identical between p=0.5 and p=0.75 (the mixed-batch set at 0.75 is a strict superset of 0.5's), and no out-of-scope files are touched. So my concerns are not about scope; they are about whether a "pass" here means what the plan will claim it means.

---

**1. [Verification Protocol steps 1/6 + Milestone 3] The primary gate is a single-seed threshold crossing that the plan itself expects may land inside noise — this is the measurement-gaming risk the goal explicitly forbids.**
The verdict hinges entirely on `best_test_acc >= 94.25%` from one fixed-seed run (+0.10 over the 94.15 baseline). The goal definition (`01-definition.md`, "Do not use seed hacking...", "Improvements must be genuine training enhancements... rather than seed selection") demands the improvement be real, but the idea-review (item 5) and EXP-010's own analysis concede the effect is "not a precise effect estimate" and a ±0.10 margin is "plausibly inside single-seed CutMix/RNG variance." The plan changes the optimization trajectory (more mixed batches → different gradients → different final weights), so a bare 94.25–94.35 result is statistically indistinguishable from stream luck. The plan flags this ("weak causal evidence," step 6) but does nothing structural about it: per the loop machinery, *any* value ≥94.25 is recorded as `improvement`, committed, and **merged as the new moving baseline** — so a noise-driven bare pass permanently raises the bar for EXP-012 (which then needs ≥94.35). Note EXP-010 cleared its threshold by +0.50; a +0.10 pass here is roughly 5× more fragile. The plan should require the "improvement" claim to be corroborated by the diagnostic trajectory (switch checkpoint, first-weak checkpoint, and final NLL all moving the right way — which step 7 gathers but explicitly subordinates: "Diagnostics cannot override the primary gate"), not the bare threshold alone, and should surface the baseline-inflation risk of a bare pass.

**2. [Execution Environment + Verification step 7] The ~26.9k-step / throughput-parity assumption is extrapolated past its evidence, and step count is both a gate and a possible cause of a bare miss.**
The plan estimates "around 26.9k steps based on identical hard/soft cost" and gates on "no unexplained material [step] loss" vs EXP-010's 26,898. That parity was measured by EXP-010 at ~50% mixed (10.823/10.829 ms hard/soft). At p=0.75 the worker-side `cutmix()` collate work rises ~50% over EXP-010's soft-batch volume. GPU step time is unchanged, and workers had ~2× headroom (179–199 batches/s vs ~93 batches/s GPU demand), so this is likely absorbed — but the plan asserts it rather than measuring it, and if workers ever become the binding constraint, fewer steps in the fixed 300 s could itself produce a bare miss and then be flagged as an anomaly by the very gate that assumed parity. The Milestone-1 preflight already spins up strong-loader batches; it should capture realized batches/s at p=0.75 rather than inheriting EXP-010's 50%-mixed timing as given.

**3. [Verification step 5 — minor, brittle assertions] Hard-coded exact-value gates risk spurious `invalid` verdicts.**
Step 5 requires "300.0 counted seconds" exactly. The loop accumulates `dt` until `total_training_time >= TIME_BUDGET_S` and the terminal step overshoots, so `training_seconds` (printed `.1f`) can read 300.0 *or* 300.1; requiring the literal "300.0" could fail a perfectly valid run. Similarly "final strong provenance between 70-80%" is safe for the full-run count (σ≈0.3% at n≈21k) but is stated with the same rigidity as the 1,000-batch preflight (σ≈1.4%); keep these as sanity bands, not equality gates, so a healthy run isn't discarded on a rounding artifact.
