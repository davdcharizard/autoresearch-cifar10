## 1. The experiment's own algebra shows the effect is at or below single-seed noise, yet a bare pass auto-ratchets the baseline (Proposal §Mechanism; Plan §Verification step 6; Brainstorm §Review)

The plan itself quantifies the intervention's total footprint: the omitted inherited term decays below 1% in ~44 weak steps, and cumulative parameter displacement is `≈0.09·b_s`, "comparable to one final strong update" — i.e. roughly **one SGD step out of ~5,400 weak-tail steps**. The gate is the *minimum* passable delta (baseline 94.15 → `>=94.25`, exactly +0.10). This recipe's run-to-run `best_test_acc` spread (single seed, timing-jittered epoch boundaries, a max over ~19 evaluations) is plausibly ±0.1 on its own. So a 94.25–94.35 "pass" cannot be attributed to the mechanism rather than noise — the plan concedes this ("formally valid but weak single-seed evidence") but does not resolve it. Under the loop's rules a bare pass is recorded as `improvement`, committed, and **merged as the new moving baseline**, which every future experiment must then beat. This means the plan has a real path to ratcheting the baseline upward on noise from an intervention it admits is nearly inert. There is no second seed, no repeat, and the no-rescue clause forbids one — so the verdict is a single coin-flip draw against a threshold inside the noise band. This is the central soundness problem, and it is not fixable within the "one run, no rescue" frame the plan adopts.

## 2. The 18–20 evaluation-look tolerance is a measurement-gaming vector and contradicts the project's own EXP-013 learning (Plan §Verification step 6: "18-20 plausible looks … do not invalidate solely for 18/20")

`best_test_acc` is a **max over evaluation passes** — more looks = more draws at a favorable peak. Project insight (EXP-013): *"Batch-dependent epochs can bias max-over-checkpoints metrics via extra evaluations… equalize elapsed evaluation count."* The momentum reset does not change per-step timing, so the candidate's tail-epoch count and evaluation count should be **identical** to EXP010's; there is no legitimate reason to build in a ±2 tolerance. The stated rule "report count asymmetry but do not invalidate solely for 18/20" is only one-directionally safe: if the candidate happens to get an *extra* tail look versus baseline, that extra max-draw can push `best_test_acc` over 94.25 with no genuine improvement, and the plan explicitly waives invalidation for it. Fix direction: require the candidate's evaluation count/schedule to match the EXP010 reference exactly, and treat a candidate with more looks than baseline as invalid (not merely "noted"), because it changes the number of max-draws.

## 3. The entire safety milestone depends on external EXP022/EXP028 corpus files that are not confirmed to exist, with no permitted fallback (Plan Milestone 2; §Verification step 4; Proposal §gates — SHA `e04dc2f…`, `ffefe98…`)

Milestone 2 / step 4 hard-require two registered corpora by exact SHA-256 (200 strong records, 64 weak hard records) produced by *prior* experiments. `.autoresearch/` is gitignored and `data/` is untracked (git status), so there is no guarantee these artifacts survived to today (2026-08-06). If either file is absent or its hash has drifted, Milestone 2 cannot run, and the no-rescue clause forbids regenerating, substituting, or relaxing the gate — so the plan is simply unexecutable with no defined off-ramp. The plan "verifies existence" but specifies no contingency for non-existence. This should be checked *first* (before branch/implementation work), and the plan needs an explicit branch for "corpus missing."

## 4. The copied-state safety scaffolding is disproportionate to this intervention and adds its own failure surface (Plan Milestone 2; §Verification step 4; Proposal §copied-state gates)

The class-concentration (>95%), update-spike (>25% of param norm, >5× ratio, >5× median), and loss-EMA gates were built to catch the recurring **high-LR global-optimizer collapses** (EXP-020/022/028 — Nesterov amplification, Lookahead location/velocity mismatch, PNM spikes). Zeroing momentum *removes* velocity and *reduces* update magnitude at LR 0.01; it structurally cannot trip these gates. So the ~300s copied-state controller is near-certain to pass regardless of merit — it provides no discriminating signal for this change, while introducing real execution risk: it is a large body of *untracked, unreviewed* controller code (plus the corpus dependency of #3) whose bugs can false-fail and block an otherwise-fine run under the no-rescue policy. The safety scaffolding is protecting against a failure mode this intervention doesn't have, at the cost of new ways to abort.

## 5. Hardcoded environment invariants in the production gate can spuriously fail (Plan §Verification step 5 / Proposal §Production verification: "eight workers stopped", "59 reset buffers")

The gate requires "eight stopped workers," i.e. it assumes `NUM_WORKERS == 8` (imported from `prepare.py`, not verified in the plan). If the node's `NUM_WORKERS` differs, `workers_stopped: <n>` fails the gate for reasons unrelated to the hypothesis. Same class of brittleness as the "59 buffers" count — 59 is verifiable from the architecture (conv1:1 + bn1:2 + 3×(3 blocks×6 tensors)=54 + fc:2 = 59, confirmed), but "eight workers" is an environment assumption, not a code invariant. Either read the expected worker count from `prepare.py` at check time or drop it as a hard gate.

## 6. Minor: `training_seconds ∈ [300, 301)` window vs. the reset absorbed into the first weak step (Plan §Verification step 5; Proposal §implementation "absorbed by that step's existing synchronization")

The plan (correctly, honestly) lets the 59 async `zero_()` kernels be caught by the first weak step's `torch.cuda.synchronize()` (train.py:248), so their cost lands *inside* a timed `dt`. That is the non-hacking choice, but it means the first post-switch `dt` is inflated by the reset kernels. The gate `TIME_BUDGET_S <= training_seconds < TIME_BUDGET_S+1` (i.e. <301) has <1s of slack; combined with normal loop overshoot this is fine, but the plan should confirm the assumption that a single step's `dt` (few ms + kernel launches) cannot push the final overshoot past the 1-second window on this node, rather than asserting it.
