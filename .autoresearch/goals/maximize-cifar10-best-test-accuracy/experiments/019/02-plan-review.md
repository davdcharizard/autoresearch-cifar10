# Adversarial Review - EXP-019 Plan (Balanced Mixup/CutMix Geometry)

## Prioritized Concerns

### 1. The "isolated one lever" framing is false: this is a compound change and net regularization is NOT held constant - attribution is unrecoverable under the single-shot, approximately 10-image gate. **[Most fundamental]**
Plan M1 (line 8) and the brainstorm ("isolates one declared lever," `01-brainstorm.md:19`) sell this as a clean single-lever test. It is not. The intervention simultaneously moves **three** dials: transform geometry (regional CutMix to global Mixup) on the `[0.25,0.5)` interval, alpha (`1.0 -> 0.4`), and the 25/25 split. The only quantity actually held fixed is *mixed-batch probability* (`u<0.5`), which the plan repeatedly frames as the isolation ("total soft-target probability exactly 0.50," line 36). But *effective regularization strength* is not held fixed: Mixup(0.4) is not CutMix(1.0) in strength, and the plan provides no calibration that they are comparable. The idea review already flagged this (`01-idea-review.md:15`, concern #2a). Consequence: with no-retry (line 26/54) and +0.10 approximately 10 test images of resolution, a null or sub-baseline outcome cannot distinguish "geometry complementarity is absent" from "alpha-0.4 too strong/weak," "25/25 split wrong," or "net regularization drifted." A pass is equally weak causal evidence. This is inherent to introducing a new transform, not fixable by more gates - but the plan should state it as a reduced-attribution bet rather than an isolation.

### 2. alpha-0.4 was chosen post-review to be "testable," directly against the proposal's own underfit rationale - raising EXP-011-style over-regularization risk on a run that cannot retry. **[Material - the alpha-0.4 refinement]**
`idea-02.md:19` deliberately picked endpoint-heavy alpha-0.2 *because* "global interpolation usually preserves a dominant original example rather than imposing the stronger central blends of alpha 1. This is important under the already difficult N1/M7 phase." The refinement to 0.4 (plan line 37; `01-brainstorm.md:90`) moves toward exactly the central mass the proposal warned would hurt the hard strong phase, motivated by making the mechanism "testable" - a change in *direction* of the mechanistic argument, not a strengthening of it. The learnings show EXP-011 raising strong-phase regularization dropped the switch checkpoint 2.91 pts and best top-1 0.15 (`03-experiment-learnings.md:108`), and identity/underfit-family changes are a recurring failure (lines 86-87). The 87.08% marker is correctly pre-registered as diagnostic-only (line 26, plan line 39) - which properly blocks reward-hacking via early-stop/retune - but it does nothing to de-risk a single-shot over-regularization outcome. The plan does not reconcile the 0.4 choice with the very rationale the proposal used to justify staying low.

### 3. The strong-loop geometry counter must fully replace the `targets.ndim == 2` heuristic, or the proportion integrity gate is silently corrupted. **[Concrete implementation trap]**
Current `train.py:221` counts CutMix via `cutmix_batch_count += int(targets.ndim == 2)`. Mixup soft targets are also `ndim == 2`, so if any remnant of the ndim heuristic survives, Mixup batches are miscounted as CutMix, the log misreports geometry, and the production proportion gate (verification step 8: 23.5-26.5% each CutMix/Mixup) reads approximately 50% CutMix / approximately 0% Mixup and fails. The plan intends kind-based counting (lines 9, 31, "count all geometries"), so this is not a plan omission - but it is the single most likely implementation error and the plan does not spell out that the old `ndim==2` count and the `else: assert targets.ndim == 1` branch (`train.py:223`) must be rewritten around conditional 3-tuple/2-tuple unpack keyed on `randaugment_enabled`. Flag it explicitly so the implementer does not leave a partial heuristic.

### 4. The "bitwise worker RNG restoration around every collate call" gate is not literally observable inside forkserver workers. **[Gate precision - minor]**
Plan M2 (line 13) and verification step 3 require proving "bitwise CPU RNG restoration around every collator call" across the eight forkserver workers. Worker-internal RNG state is not inspectable from an external controller under `multiprocessing_context="forkserver"`; only single-process collate RNG-neutrality (save `get_rng_state`, call collate, compare) is directly verifiable, plus aggregate proportions/finiteness from the 8-worker run. The essential property (collate is RNG-neutral, guaranteed by `fork_rng(devices=[])`) IS verifiable single-process, so this is not fatal - but as written the gate claims a per-worker per-call measurement that cannot be taken. Reframe to what is actually measurable so it is not an unfalsifiable checkbox.

## Points examined and found sound (no action)
The RNG/provenance core is clean: one `torch.rand(())` before any transform means retained CutMix (`u<0.25`) and hard (`u>=0.5`) batches are bitwise-identical to EXP-010, and `fork_rng(devices=[])` discards Mixup's Beta (torch-CPU) draw so the downstream transform/`u` stream is unperturbed - the "mixed decisions equal to control by construction" claim holds because both mix iff `u<0.5`. GPU step is genuinely neutral (both arms are 50% `[B,10]` soft / 50% `[B]` hard CE), so the exposure/timing gates are appropriate and not gameable. Scope is respected (train.py-only; temp controllers external, deleted, read-only). Test-set isolation holds (preflight uses training/held-out-weak batches; `Eval.evaluate` untouched; eval cadence unchanged, so best_test_acc is not inflated). Sole-run/no-reroll discipline is consistent with `01-definition.md:18`.

## Verdict: **APPROVE** (execution-sound)
No execution-fatal or reward-hacking defect. Concerns #1 and #2 are interpretability/robustness limitations of a single-shot compound change, not blockers - but the plan should (a) reframe the hypothesis as a reduced-attribution geometry+regularization swap rather than an isolated lever, and (b) acknowledge the alpha-0.4 underfit risk explicitly against `idea-02.md:19`. #3 is a required implementation reminder; #4 is a gate-wording fix. None require changing the reviewed intervention (alpha/probabilities/split), so all are addressable without violating the no-retune constraint.
