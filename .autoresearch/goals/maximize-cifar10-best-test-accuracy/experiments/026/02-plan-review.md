1. **[Milestone 3 / Verification step 5] The real-loader timing control is not pinned to the accepted 50/50 policy after `train.py` is mutated.** `train.py` will expose only the candidate `CUTMIX_PROBABILITY=0.25` and triple-return collator, while the timing plan merely says “accepted/candidate” fresh processes. If both arms import that collator, candidate-vs-candidate ratios pass near 1.0 and falsely authorize production. Require an explicit control collator with one `u<0.5` CutMix decision, assert its branch counts/target forms, and record distinct control/candidate policy identities in every raw pair.

2. **[Milestones 2-3 / Verification step 4] Capturing the exact pre-policy worker RNG state fixes source replay, but the paired GPU veto is still not causally deterministic.** The plan sets `CUBLAS_WORKSPACE_CONFIG` yet does not pin or report `torch.use_deterministic_algorithms`, cuDNN deterministic/benchmark settings, TF32 flags, or identical backend state in the fresh control/candidate processes. Because one candidate-only class-concentration event vetoes the sole run, nondeterministic convolution/backward differences can again be mistaken for a policy effect despite the immutable CPU corpus. Require matching deterministic backend flags and report them before treating arm divergence as attributable.

3. **[Milestone 2 / `preflight_balanced_mix.py`] The forkserver controller omits the required guarded entry point.** A top-level picklable `source_collate` is necessary but insufficient: starting the eight-worker loader from a path-launched script without `if __name__ == "__main__":` can recursively execute controller setup or fail during forkserver bootstrap. This exact infrastructure issue has occurred in prior goal history. The plan must pin the guard while keeping only the collator definition at module scope.

4. **[Milestone 4 / Verification step 7] Verdict checks are ordered so an incomplete or timed-out run can be mislabeled `no-improvement`.** The plan compares `best_test_acc` first and says to stop immediately if it is below 94.25, before verifying exit zero, a complete finite summary, the counted budget, and total wall time. A partial log containing a lower interim summary would therefore be recorded as a valid miss rather than `invalid`/crash. Establish completion and protocol validity first; only then classify the numeric metric.

5. **[Milestone 4 / Verification steps 7-8] Several production validity gates are not executable as pre-registered tests.** “Counted budget near 300,” “one near-80% switch,” “peak near 650 MiB,” and “no worker or allocation growth” lack numeric tolerances, sampling points, or exact comparisons; these can be waived or tightened after observing accuracy. Define exact inclusive ranges and report fields before launch, including the allowed one-step time overshoot and switch rounding.

6. **[Code Changes / current `train.py:217-223`] Triple-versus-pair batch unpacking is underspecified at the only loop that must support both.** The current header `for inputs, targets in train_iterator` raises before any `randaugment_enabled` branch can inspect a strong three-tuple. “Accepts triples only before the switch” must concretely replace the loop header with a single batch object and conditionally unpack three items for strong and two for weak; otherwise the reviewed collator crashes on the first production batch.

7. **[Milestone 3 lifecycle gate] The weak-loader worker cleanup is ambiguous.** The gate starts a weak loader and consumes its first batch, which launches eight new persistent workers, but only requires “eight workers stopped,” plausibly referring to the strong loader. Require explicit weak-loader shutdown and a zero-live-child assertion after the probe; otherwise the same preflight process can carry orphan workers into later checks or pass a lifecycle gate while leaking the rebuilt pool.
