# EXP-004 Plan Review — Prioritized Concerns

### 1. Acceptance bar (0.1 pp = 10 test examples) sits at/below single-seed noise, and the intervention *reshuffles the entire augmentation RNG stream* — a "pass" is not attributable to RandAugment
**Section:** Milestone 4 / Verification step 5 (`02-plan.md:24,81,85`); risk #6 in `idea-01.md:201-203`.
RandAugment consumes worker RNG *before* the crop/flip draws (proposal is explicit: "RandAugment necessarily consumes worker RNG and changes later crop/flip draws"). So even the plateau phase sees a *different* crop/flip stream than EXP-002 — the comparison to `91.83%` is confounded by RNG reshuffling, not just by the added augmentation. The pass threshold is `best_test_acc >= 91.93%`, i.e. exactly **10 test examples** out of 10,000 (the plan itself concedes this at `02-plan.md:85`). Seed-to-seed variance on CIFAR-10 ResNet-20 is well above 0.1 pp, and the run is single-seed by rule. Consequence: a passing run cannot distinguish "genuine invariance gain" from "favorable reshuffle," which is functionally the outcome the no-seed-hacking constraint exists to prevent — the effect just enters through the augmentation RNG rather than the seed knob. The plan proceeds to treat `>=91.93%` as `improvement` anyway. This is the deepest validity concern; at minimum the analysis must not claim causal attribution on a single within-noise run, and the plan gives no mechanism (repeat/variance estimate) to separate signal from draw.

### 2. The mandatory preflight gate does not exercise the plan's *own stated main risk* — the mid-run loader teardown/rebuild
**Section:** Milestone 2 (`02-plan.md:13-16`), Verification step 2 (`02-plan.md:57-63`); risk statement `02-plan.md:30`.
The plan names the primary risks as "worker lifecycle leaks, an approximately 19-second forkserver restart... RNG/data-order discontinuity" (`02-plan.md:30`). But the feasibility diagnostic (`/tmp/exp004_loader_bench.py`) measures *steady-state* throughput of the candidate and control loaders **separately**, each warmed and timed over 3 epochs — it never tears down one persistent loader and spins up another in the same process, and never measures two worker sets contending. The actual novel failure mode (the swap) is charged as a flat `+ 20.0` seconds in the projection (`02-plan.md:60`), a guess, not a measurement. The gate therefore returns green on the part that already works and is silent on the part that can fail. The preflight should reproduce the teardown+rebuild in one process and measure the real transition cost, or the `+20s` must be labeled as unvalidated.

### 3. Reliance on `del` + `gc.collect()` to terminate 8 persistent workers is not deterministic — orphan contention can balloon wall time
**Section:** Milestone 1 (`02-plan.md:10`), Milestone 3 orphan check (`02-plan.md:21`).
The plan releases the augmented persistent loader and runs `gc.collect()`, then builds a fresh loader. With `persistent_workers=True`, the 8 workers are owned by the loader's `_MultiProcessingDataLoaderIter`. The `for inputs, targets in train_loader` construct creates an *implicit* iterator whose reference can linger on the stack/exception frames after `break`, so `del train_loader` + `gc.collect()` does not guarantee prompt worker shutdown. If the old 8 survive alongside the new 8, 16 processes contend for ~8 cores → new-loader starvation → total wall time grows toward the 600 s timeout. The plan only checks for orphans *after the fact* (`02-plan.md:21`) and has no deterministic shutdown step (explicit iterator `del`, `_iterator=None`, or a `_shutdown_workers()` path). This needs a concrete, ordered teardown, not a post-hoc assertion. Separately: a less invasive path (a single non-persistent loader, or a transform object gated by a shared flag) would avoid the teardown entirely — the chosen mechanism imports lifecycle risk that the objective does not require.

### 4. `multiprocessing_context="fork"` mismatch between preflight and the real run; the "19 s forkserver restart" figure is unexplained
**Section:** Milestone 2 (`02-plan.md:14`), Code Changes risk (`02-plan.md:30`), estimated runtime (`02-plan.md:41`).
The diagnostic forces `multiprocessing_context="fork"` (`02-plan.md:14`), but `train.py:134-142`'s DataLoader passes **no** `multiprocessing_context` (it uses the process default). If those differ, the preflight throughput and the real run diverge, and the whole 80 batches/s gate is measuring a different configuration than what ships. Meanwhile the plan simultaneously cites a "**forkserver** restart" (`02-plan.md:30`) and estimates it at ~19 s (`02-plan.md:41`) — fork worker respawn on Linux is normally sub-second (copy-on-write), so a 19 s figure suggests the rebuild is re-instantiating the CIFAR-10 dataset from disk, not just forking workers. Either reconcile the context (set it explicitly in `train.py`, which is in-scope, and match it in the benchmark) or justify the 19 s; as written the feasibility number and the runtime budget rest on an unverified/ inconsistent worker model.

### 5. Timeout margin is razor-thin at the gate floor
**Section:** Verification step 2 projection (`02-plan.md:59-63`).
At the minimum passing rate `R=80`: `336.0 + max(0, 38629/80 − 300) + 20 = 336 + 182.9 + 20 = 538.9 s`, which passes the `<=540 s` gate but leaves only ~61 s before the hard 600 s kill. That slack must absorb first-batch latency, evaluator variance, imperfect GPU/loader overlap, *and* the untested swap cost from concern #2. The projection is conservative in one respect (it charges the slow RandAugment rate for all 38,629 batches when only ~80% are augmented), which partly offsets — but combined with an unvalidated `+20s` swap term, a candidate that barely clears 80 b/s is exposed to a timeout → `failure`. Worth widening the margin or requiring a higher rate floor.

### 6. A handful of augmented batches run in the low-LR regime before the epoch break
**Section:** Milestone 1 switch logic (`02-plan.md:10`); LR logic `train.py:177-188`.
The switch is: reach 80% counted time → finish the current epoch → rebuild loader at the next boundary. But LR steps to the cosine tail the instant `progress > 0.8` (`train.py:177-183`), while the transform only changes at the epoch boundary. So the batches between "80% reached" and "epoch broken" run *augmented at low LR* — the exact combination the plateau-only design intends to avoid. It is bounded (≤ ~1% of budget, since ~99 epochs ≈ 1%/epoch) and the plan does break the epoch promptly, so impact is small — but the verification "exactly one switch at/just after 80% and no later than 85%" (`02-plan.md:26,83`) will pass even though transform-switch and LR-switch are not co-located. If clean separation is the point, break the *transform* at the same batch that crosses 80%, not at the epoch boundary.
