I've read the plan, goal definition, brainstorm, proposal (idea-03), and the current `train.py`. The design is careful and the arithmetic checks out (param count 1,073,962 and total BN activation elements 376,832 genuinely offset — compute really is near-neutral). Below are the concerns that survive that scrutiny, hardest first.

## Prioritized concern list

**1. The experiment is under-powered to detect the effect it claims — a "pass" is indistinguishable from noise.**
*(Milestone 3 / Verification steps 9–10 / plan Hypothesis; proposal §Hypothesis: point prediction 94.30, gate 94.25.)*
The success gate is baseline+0.10 = 94.25, and the point prediction is 94.30 — a 0.05pp cushion. That is well inside single-run variance for a width-2 ResNet-20 on CIFAR-10. The plan runs exactly one seed-42 run, forbids reruns (Abort Criteria: "one valid seed-42 run determines the verdict"), and explicitly bars every trajectory diagnostic (checkpoints, slopes, best/final gap) from acceptance (step 10: "cannot override the primary gate"). So if the run lands at 94.25–94.35 there is no mechanism in the plan to establish the gain is real rather than seed luck — which directly tensions with the goal's demand for "genuine training enhancements … rather than seed selection." The same-seed Conv-weight alignment (step 3) partially controls initialization variance, but data-shuffle RNG, CUDA nondeterminism, and the architecture change itself are uncontrolled. The plan provides no variance estimate for the 94.15 baseline either, so the decision is single-run vs. single-run at the resolution limit. This is not fixable by more gates; it should at minimum be surfaced in the plan as "weak causal evidence at the noise floor" and the acceptance framed accordingly.

**2. Self-imposed VRAM no-go (≤650 MB, ≤64 MB over control) can abort a legitimately valid run for a reason the goal does not care about, and is measured on the wrong quantity.**
*(Milestone 2 / Verification step 6 / Abort Criteria; proposal §Capacity.)*
VRAM is not a goal constraint — the H20 has 98 GB and `peak_vram_mb` is explicitly only a "soft VRAM-cost signal" (goal 01-definition L44). Yet the plan makes 650 MB a hard no-go with only ~51 MB headroom over EXP-010's 598.7 MB. Preactivation moves `BN_in` *before* the stride-2 conv, so the transition blocks now retain the larger pre-downsample tensors (e.g., 32ch@32×32) for backward — a plausible peak increase even though total element count is neutral. Two problems: (a) a marginal VRAM bump would kill an otherwise-valid accuracy experiment for a non-goal reason; (b) the gate is checked in a 500-step microbenchmark (step 6), whose peak allocation need not equal the full-run peak (which also spans the evaluator and the loader recreation at the 80% switch). The gate therefore may pass in the benchmark and be irrelevant to, or under-estimate, the real run.

**3. The change bundle cannot isolate the mechanism the hypothesis names.**
*(Configuration Changes L29–31; plan Hypothesis / brainstorm "foreground final feature conditioning and unrectified residual sums.")*
"Canonical full preactivation" is three simultaneous changes: (i) block reorder to BN-ReLU-Conv, (ii) removal of stem BN-ReLU + new terminal BN-ReLU, and (iii) preactivating the first and both transition shortcuts (Option-A now slices/pads a ReLU'd, non-negative tensor rather than raw signed `x`). The plan's own hypothesis foregrounds "final BN-ReLU feature conditioning and signed residual-sum representation" as the operative mechanism — but the design also alters shortcut transport semantics (transition skips carry non-negative zero-padded features while ordinary skips carry signed `x`), so a positive or negative result cannot be attributed to the claimed mechanism. This is disclosed in idea-03, but the plan still writes a mechanism-specific hypothesis it structurally cannot test. State the hypothesis as "the full-preactivation package as a whole," not the isolated conditioning claim.

**4. The go/no-go feasibility gates project from stale EXP-010 constants that the actual run is not held to.**
*(Verification step 6: `floor(26898 * control/candidate) >= 26091`; step 7 / Estimated runtime: "EXP-010's 330.7-second total"; Abort Criteria "projected exposure >=26,091 steps.")*
Step retention and the <540 s runtime are *projections* built on EXP-010's 26,898 steps and 330.7 s, measured on a different run/GPU state. The candidate's real step count is set by live conditions at run time (thermal, contention, loader recreation cost at the augmentation switch), not by the microbenchmark ratio. Nothing in the plan re-checks realized exposure against the 97% floor after the fact — step 10 only "compares actual steps … as diagnostics." So the run can pass the timing gate, then under-deliver exposure, silently confounding the accuracy comparison the plan treats as clean (the "at least 97% of EXP-010's exposure" clause in the hypothesis becomes unverified).

**5. Bitwise RNG/weight-identity is elevated to a hard abort gate, risking termination of a valid run over an attribution nicety.**
*(Abort Criteria L43; Verification step 3: "global CPU RNG states byte-identical after construction," "every same-named Conv/Linear tensor bitwise equal.")*
This holds only if Conv/Linear *creation order* is preserved exactly (stem conv1 → each block's conv1 before conv2 → fc) and nothing else touches the global generator. That is achievable (BN construction draws no RNG), but the plan makes any deviation a launch-blocker. Adding the explicit first-unit flag / `preactivate_shortcut` attribute and reordering `BasicBlock.__init__` (the plan changes `bn1` to `BatchNorm2d(in_channels)` and adds a flag) is exactly the kind of edit that can perturb submodule registration order. Since bitwise identity serves attribution, not correctness, a benign reorder would abort a scientifically valid experiment. Consider demoting it from an abort criterion to a recorded diagnostic, or pinning the construction order explicitly in the code-change spec.
