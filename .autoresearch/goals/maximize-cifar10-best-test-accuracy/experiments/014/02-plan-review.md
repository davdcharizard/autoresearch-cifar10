# Adversarial Plan Review — EXP-014

**1. The verification cannot attribute a "pass" to the idea (Milestone 3 / Verification step 10 / Informational Metrics line 66).**
The design is engineered to start *bitwise-identical* to the 94.15% baseline (zero-init max_fc, exact logit/RNG/gradient identity). The acceptance gate is a single fixed-seed run clearing 94.25% (+0.1pp). CIFAR-10 ResNet single-run trajectory variance is routinely ±0.2–0.3pp, i.e., larger than the effect being chased. Worse, the one diagnostic that could show the max path actually did something — first-step max-path gradient/update norms — is explicitly captured only "in preflight outside the timed production path" (line 66), so the accepted run logs *nothing* about max-path contribution. Consequence: a 94.25–94.35 "pass" is indistinguishable from stochastic training noise, and the experiment will report `improvement` for the idea even if the max path contributed ~nothing. The hypothesis ("learns useful class-specific localized readout ... raises best_test_acc") is causal, but nothing in the protocol can separate that cause from run variance. The plan concedes this ("weak single-seed evidence") without adding any mechanism (e.g., logging max_fc weight-norm / logit-contribution at the best epoch in the production run) to make the claim falsifiable.

**2. The change is most likely a near no-op by construction (Code Changes; Configuration "First backward"; Abort Criteria line 46).**
max_fc starts at exactly zero and is subject to weight_decay=1e-4, which pulls it back toward zero. It only receives gradient signal, and only begins feeding gradient back into the max features, *after* the first optimizer step — then must grow from zero across a budget where the meaningful readout-shaping happens late. The plan sets no minimum-effect / activation threshold: there is no criterion of the form "max_fc must reach weight-norm > X or the mechanism is deemed inactive." So the expected outcome (best_acc ≈ baseline ± noise) is exactly the outcome the plan will read as either a pass (if noise is favorable) or a valid no-improvement — with no way to tell it apart from "the mechanism never engaged." This undercuts the entire point of preferring the *learned* concatenated readout over a fixed blend.

**3. best_test_acc is a max-over-19-evaluations statistic, and the targeted delta is sub-eval-spacing (Verification step 10).**
The primary metric takes the maximum accuracy over ~19 evaluation points. Adjacent dense-tail evaluations on this model typically differ by more than 0.1pp. Therefore the +0.1pp threshold can be met by a single lucky evaluation spike in the tail that has nothing to do with the max path. This is an inherent property of the "best over run" metric, but the plan leans on it with a design whose true mean effect is ~0; it should at minimum report final_test_acc and the best/final gap alongside, and treat a pass driven by a single isolated spike as non-evidence rather than improvement.

**4. The "exactly 19 unique evaluation epochs" gate can waste the single allowed run (Verification steps 7 & 9, Milestone 3).**
Dense-tail evaluation count is a function of how many weak-tail epochs fit in the last 20% of wall-time, which depends on per-step timing. Adding adaptive_max_pool2d + a Linear shifts step time slightly; if that moves even one epoch boundary, the tail eval count becomes 18 or 20 and the run fails the step-9 gate. Because the plan permits "exactly one valid seed-42 run" with no reroll, a benign timing perturbation that changes eval count would burn the only run. The plan treats 19 as a hard equality check without a tolerance or a fallback, which is fragile given it simultaneously accepts up to ~3% step-time change elsewhere.

**5. Thin exposure margin against launch-bound overhead (Milestone 2 / Verification step 6).**
The exposure gate is `floor(26898 * control/candidate) >= 26091` — only ~3% slack. The change adds two extra per-step GPU operations (adaptive_max_pool2d and a second Linear), each a separate kernel launch. `02-system-understanding.md` explicitly warns that "nominally small reductions can be launch-bound" (the SE example). On an ~11ms step, two launches plus the extra reduction are small but non-zero, and the margin is narrow enough that a real feasibility abort is plausible — after which the plan has no fallback beyond declaring the experiment infeasible. Confirm the measured per-step delta has headroom well inside 3%, not merely at the boundary.
