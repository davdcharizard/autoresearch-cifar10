Below is my adversarial review of EXP-030. Findings are ordered most-fundamental first, each tagged to the plan section it attacks.

---

**1. [Verification Protocol §7 / Hypothesis] The predicted effect size sits inside single-run nondeterministic noise, and the protocol forbids the only thing that could separate signal from noise.**
The gate is `best_test_acc >= 94.25` (baseline 94.15 + 0.10); the point prediction is 94.30 — a claimed margin of ~0.10–0.15. train.py sets `torch.manual_seed(42)` but never calls `torch.use_deterministic_algorithms(True)` and no `CUBLAS_WORKSPACE_CONFIG` is set (the infra note for EXP-020 confirms this env is required for determinism and is *not* the default). Default cuDNN convolutions are nondeterministic, so run-to-run `best_test_acc` variance for this model is plausibly ≥0.1–0.2 pp — i.e. at or above the entire improvement margin. The Abort Criteria explicitly bans "another seed" and "rerun of a valid result," so a seed-42 run landing at 94.25–94.30 cannot be distinguished from a lucky draw, and the verdict likely won't reproduce. This is inherited from the benchmark's single-seed protocol, but the plan should at minimum state that a bare pass at this margin is not a reproducible improvement claim — right now §7 treats crossing 94.25 as dispositive.

**2. [Verification Protocol §6–8, Milestone 3, Config Changes] Hard gates and diagnostics are built on EXP010 reference numbers that the plan never sources.** The plan asserts, as pass/fail gates or comparison anchors: `num_steps` floor 26,629 (from "26,898"), "19 unique evaluations," `num_params=1073962`, "eight stopped workers," `training_seconds` 300-budget, plus diagnostic anchors 89.73% final-strong, 93.16% first-weak, and 0.1934 NLL. None of these cite EXP010's report/log path. If any is misremembered (e.g., EXP010 actually logged 18 or 20 tail evaluations, or a different step count), a valid run is falsely invalidated or a diagnostic is miscalibrated. These constants must be pulled from EXP010's actual `04-analysis.md`/`run.log` before being used as gates, not from memory.

**3. [Verification Protocol §6–7] Validity gates are over-coupled to timing jitter, risking spurious "invalid" on a legitimately-measured accuracy.** `num_steps`, `num_epochs`, and evaluation count are all wall-time-dependent, yet the plan applies inconsistent rigor: steps get a ~1% floor (26,629) but evaluations are pinned to *exactly* "19 unique evaluations" with no tolerance. The change adds zero per-step work, so counts *should* match EXP010 — but CUDA nondeterminism and GPU-load jitter can shift which epoch crosses a checkpoint boundary by ±1, changing the eval count and/or dropping below the step floor. A slightly slow run could then be marked invalid even though `best_test_acc` — the only primary metric — was validly produced. Either give the eval-count gate an explicit ±1 tolerance or downgrade it to informational; do not let it veto the metric.

**4. [Code Changes / Milestone 1 / §8] The "byte-identical strong phase" and "identical state/RNG" claims are false under the actual (nondeterministic) execution, which mis-frames the strong-phase diagnostic.** Only the *pre-CUDA* initial parameter/RNG state is genuinely identical between runs; once training hits nondeterministic cuDNN kernels, the strong phase will diverge run-to-run regardless of `ANNEAL_START_LR`. Consequently §8's instruction — "Strong-phase material drift cannot be blamed on `ANNEAL_START_LR` … investigate it as protocol/environment evidence" — will label ordinary nondeterministic variance (a few tenths at the switch checkpoint vs EXP010's 89.73%) as a protocol fault. The strong-phase comparison needs an explicit nondeterminism tolerance band, or it will generate false "environment" alarms.

**5. [Verification Protocol §3 / Milestone 1] The "exactly 2.0× first-weak displacement" preflight is tautological and validates arithmetic, not the experiment.** For SGD with weight decay, if both arms share identical momentum buffer and gradient (guaranteed, since `ANNEAL_START_LR` is unread until progress>0.8) and only `lr` scales 2×, the first-step displacement `lr·buf` ratio is exactly 2.0 by definition — and diverges from 2.0 on every subsequent step. Passing this gate confirms nothing beyond "SGD scales the step by lr." Additionally, §3 says the controller "imports/**duplicates**" the schedule math; if it duplicates rather than imports the real `train.py` branch, the audit can pass while the production code path differs. Import the actual code path; don't treat this gate as evidence the intervention is sound.

**6. [Abort Criteria / §5–6] Crash-vs-infra-retry policy is underspecified and internally inconsistent.** The Abort Criteria state "Exactly one scored fixed-seed run is allowed" and ban any rerun, but §6 carves out "unless a documented infrastructure fault invalidates the run" without saying whether a re-run is then permitted — and the infra note for EXP-015 explicitly allows "one unchanged full-protocol infrastructure retry" for a device-cold/crashed first process. Clarify: a *crash/infra fault* is re-runnable once; only a *valid completed* run is non-repeatable. As written, a legitimate infra crash could be misread as a terminal failure.

**Minor:** §6 gates `total_seconds < 600`, but the launch uses `timeout … 595s`, so any run reaching 595 s wall is killed (status 124) before printing a summary — the effective cap is 595 s, not 600 s. Harmless given the 330–345 s estimate, but the `<600` bound is unreachable and should read `<595`.
