Below is my adversarial review of the concrete EXP-009 plan. Concerns are ordered hardest/most-fundamental first, each anchored to the plan text.

---

**1. [Config Changes / whole premise] The dominant numerical change is a 2× increase in decay on exactly the parameters that already showed underfit — pushing a fit-limited model further into the failure mode.**
The plan frames itself as "selective moderate decay" (§Code Changes, §Chosen Idea), but relative to the `1e-4` baseline the arithmetically dominant change is `WEIGHT_DECAY` on the 20 conv/linear kernel tensors going `1e-4 → 2e-4` (§Config: "explicit 2e-4 for 20 tensors / 1,071,200 parameters"). Those kernels carry essentially all the norm pressure (2,762 BN/bias params are negligible). `03-experiment-learnings.md` Patterns say width-2 is *fit*-limited in 300s ("Width-2 capacity beats the fixed-time update loss"), and EXP-008's `5e-4` failure on those same kernels was an *underfit* collapse (90.08→81.29, tail still rising at termination). Doubling kernel decay is a smaller step in the identical direction that just failed. The plan never reconciles "add more norm pressure to the kernels" with the standing finding that the model is fit-limited, not norm-limited — this is the same diagnosis inversion flagged in `01-idea-review.md` #2, carried into execution unaddressed.

**2. [Code Changes / Verification step 8 — attribution confound] The run changes two levers at once versus baseline, and no verification step can isolate them.**
Against the `1e-4`-on-everything incumbent, this plan simultaneously (a) doubles kernel decay `1e-4→2e-4` and (b) zeroes BN/bias decay `1e-4→0`. Any outcome — improvement or regression — cannot be attributed to selective targeting vs. the scalar bump. Verification step 8's mechanistic check (strong-checkpoint recovery toward 90.08%) does not disentangle them either, because both levers move the strong checkpoint the same way. The plan presents this as testing a single hypothesis ("moderate kernel norm control without shrinking BN affine"), but the learning it can actually yield is ambiguous regardless of verdict. This is the "fusion" `01-idea-review.md` #4 recommended, but the plan inherits it without acknowledging the attribution cost or proposing any control.

**3. [Verification steps 1/5 / Abort Criteria — expected value] A single-seed, no-reroll run targeting a ≤0.2-point effect at a 93.65 gate is most likely a no-improvement inside the noise band.** 
Known endpoints are 93.55 (`1e-4`) and 93.38 (`5e-4`); the interpolated/selective point most plausibly lands 93.4–93.6 — below the 93.65 threshold (step 5). The idea review (#1, #5) already noted there is no evidence the top-1 curve is non-monotonic above `1e-4`, so the incumbent may already be optimal. The plan hard-codes `best_test_acc >= 93.65` with one seed and prohibits reroll (§Abort Criteria) — correct per protocol, but it means a 93.58-type result (well within run noise) is a definitional failure. The plan offers no argument that the expected effect clears the noise floor; it pre-registers success at a margin its own history suggests is unlikely.

**4. [Verification step 7 — operational] "Static/runtime group verification before the full run" risks violating the `run.log`-absent precondition and is under-specified.**
Step 7 requires runtime confirmation of group counts (`20/1,071,200`, `39/2,762`) and decay values `{2e-4, 0}` "before the full run," while step 3 requires `test ! -e run.log` immediately before launch. If the group check is done by adding a print to `train.py` and running it, it (a) writes to stdout/`run.log` and (b) risks leaving a stray/uncommitted diff that step 7's own `git diff -- train.py` check would then flag. The plan should specify that the group inspection runs via a separate scratch harness that neither writes `run.log` nor alters `train.py`, and that it is torn down before launch. As written the two preconditions can collide.

**5. [Milestone 1 / Code Changes — implementation ambiguity] The partition rule must be pinned to `requires_grad` trainable tensors and to `named_parameters` traversal order to reproduce the pre-registered counts.**
The plan states the split as `ndim > 1` vs `ndim <= 1` over `model.parameters()`, and the verification hard-codes exactly 20/39 tensors. This only holds if every parameter is iterated once and all are trainable (true here), but the plan does not state the traversal method or that both groups must be exhaustive-and-disjoint at construction time (it asserts the property in verification but not in the build step). A partition that accidentally drops a param (e.g., filtering on a stale name predicate) would still "run" and could silently exclude a tensor from optimization while passing the `num_params` model-count check (step 4), which counts model params, not optimizer-covered params. Recommend the implementation assert `sum(len(g['params']) for g) == len(list(model.parameters()))` and total numel equality, not just the count table.
