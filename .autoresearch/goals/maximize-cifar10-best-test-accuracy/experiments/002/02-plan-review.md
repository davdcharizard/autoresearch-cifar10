Below is my prioritized, execution-grounded concern list for Plan EXP-002. Each is tied to the plan section it attacks.

---

## Concern 1 — Baseline vs. experiment are measured under different evaluation cadences (Verification step 5 / Config "Validation cadence" / Milestone 1)

The plan requires `best_test_acc >= 91.77%` against a *moving baseline of 91.67%*, but the experiment evaluates at only **7 budget checkpoints** while `best_acc = max over evaluated epochs`. Two problems:

- **Peak can fall in an unsampled epoch.** In the cosine tail (80→100% progress) only the **0.90 checkpoint and the terminal eval** are sampled — yet this is exactly the region where accuracy climbs fastest as LR anneals from 0.1 to 1e-4. If the true peak lands at, say, the ~95% epoch (plausible if the last epochs slightly over-fit at very low LR), it is never evaluated and the run reads `no-improvement` for a schedule that genuinely peaked ≥91.77%. The plan's own basis for trusting sparse sampling ("EXP-001 was monotonic, final==best") does **not** transfer: EXP-001 held high LR for only 15% and annealed smoothly the whole time; an 80% high-LR plateau produces a noisier trajectory where final==best is not guaranteed.
- **Footing mismatch with the recorded baseline.** The plan never confirms that the `91.67%` baseline in `04-results.tsv` was itself measured with the same 7-eval protocol. If it came from the unmodified per-epoch `train.py` (99 evals → 99 samples of `best`), the baseline had far more chances to catch a peak than this experiment gets with 7. The comparison is then not like-for-like, and it biases *against* the experiment. Milestone 3 gates on "baseline `91.67%`" but does not verify the baseline's eval cadence.

This is the most fundamental issue because it can invalidate the pass/fail decision itself, independent of whether the schedule is good.

## Concern 2 — Predicted margin is exactly the pass threshold, with no cushion against single-run nondeterminism ("Chosen Idea" hypothesis / Verification step 3)

The hypothesis predicts `91.77%` and the bar is `91.77%` — **zero margin**. The 80% hold is chosen to sit right next to the baseline's known-good 83% first-drop, so the intervention is deliberately close to baseline dynamics. CIFAR-10 ResNet20 run-to-run variation at a *fixed* seed is still ~±0.1–0.2pp due to cuDNN/atomic nondeterminism (the seed is fixed at 42, correctly, so this is not seed-hacking — but it also means the schedule change is not the only source of the delta). A result of exactly 91.77% (one 0.01-quantum above 91.76) would satisfy the letter of the check while being statistically indistinguishable from baseline noise, which directly conflicts with the goal's requirement of a "genuine training enhancement rather than seed selection." The plan has no replication or margin-of-safety provision, and single-run execution cannot distinguish a real +0.10 from nondeterministic drift.

## Concern 3 — The "refinement tail" the experiment claims to add is mostly *not* low-LR, undercutting the stated mechanism ("Code Changes" LR function / risk paragraph)

By the plan's own math, only "the last roughly 4% of total updates fall below `0.01`." The remaining ~16% of the tail sits between 0.1 and 0.01. The baseline, by contrast, drops to a flat `0.01` at ~83% and holds it for its entire last ~17%. So relative to the baseline, this schedule spends **less** time in the ≤0.01 regime, not more — it merely reaches a lower floor for a brief final sliver. The hypothesis ("add a short guaranteed refinement tail the baseline never reaches") is therefore testing a confounded change: it simultaneously (a) replaces the baseline's flat-0.01 tail with a cosine ramp and (b) briefly dips to 1e-4. A null result will not be interpretable — it won't distinguish "low-LR refinement doesn't help" from "the cosine ramp removed the baseline's beneficial flat-0.01 phase." This weakens the experiment's diagnostic value even if execution is clean.

## Concern 4 — "Exactly seven eval lines" is a hard failure gate with a fragile assumption (Verification step 5 / eval policy)

Verification step 5 fails the run unless there are exactly 7 `eval ep` lines and 7 unique epochs. The eval policy "consume all reached thresholds after each evaluation" means that if any **single epoch spans two adjacent checkpoints**, that epoch evaluates once and consumes two thresholds → only 6 evals total → automatic fail, even for an otherwise-successful, in-budget run. This is safe *only* while per-epoch counted-time advance (~1% of budget) stays well below the minimum checkpoint gap (10%). That holds under EXP-001's timing, but the gate is brittle: any throughput regression that lengthens epochs, or a slow first epoch, silently converts a good run into a verification failure. The plan should treat "7 evals" as a diagnostic, not a hard invalidation criterion, or make the consume-logic explicitly emit one eval line per crossed threshold.

## Concern 5 — Gated evaluation introduces an unbound-variable / summary-integrity risk that the plan patches by assertion rather than by construction ("Code Changes" — terminal metric initialization)

The original loop evaluates every epoch, so `test_loss`/`test_acc` are always bound before the summary. Gating eval means early epochs (progress <20%, e.g., epoch 1) run with **no** evaluation, leaving `test_loss`/`test_acc` unbound until the first checkpoint. The plan relies on "unconditional terminal metric initialization" plus an assert. This works only if the terminal-eval branch is truly guaranteed on the final epoch — but note `training_done` is evaluated at the epoch boundary, and if `MAX_STEPS`/budget logic and the checkpoint-consume logic are implemented in the wrong order, the terminal eval could be skipped while `final_test_acc`/`final_test_loss` are still printed from a stale earlier eval. `py_compile` and `ruff` (Milestone 2) will **not** catch this — it's a runtime/logic issue. The plan should specify that the terminal eval branch is unconditional and that the printed `final_test_*` come from that terminal eval, not merely assert non-null.

## Concern 6 — Scheduler removal leaves a dangling reference risk not fully covered by the listed checks (Milestone 1 / Config "Learning-rate scheduler")

The plan removes `MultiStepLR` (train.py:145–147) but the training loop still calls `scheduler.step()` (train.py:176) and reads `optimizer.param_groups[0]["lr"]` for logging (train.py:190). If `scheduler.step()` is not also removed, the run crashes at runtime. Ruff's F821 may flag an undefined name, but only if `scheduler` is fully deleted rather than shadowed; `py_compile` will not catch it. The plan's "Code Changes" text describes assigning LR manually but does not explicitly enumerate deleting the `scheduler.step()` call — worth making explicit so the manual-LR assignment and the scheduler-call removal are treated as a single atomic edit.
