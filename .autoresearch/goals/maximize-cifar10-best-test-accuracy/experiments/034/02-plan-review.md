## Execution-Soundness Concerns — EXP-034 (Conv-only fan-out init)

**1. [Most fundamental — Milestone 3 / Verification step 6 / proposal "single-seed risk"] The claimed effect is smaller than the measurement's noise floor, and no noise floor is established.**
The gate is +0.10 (94.15 → 94.25). The proposal's *own* predicted band is 94.00–94.35% (midpoint ~94.17, below the gate). Production runs **exactly once** under default TF32 / nondeterministic cuDNN (`03` env: production is *not* deterministic — only the controller subprocesses set `CUBLAS_WORKSPACE_CONFIG`), and seed reroll is forbidden. Run-to-run cuDNN algorithm/atomic nondeterminism on this recipe is plausibly ±0.1–0.2%, i.e. comparable to or larger than the effect. The plan never runs the *baseline* under the same nondeterministic regime to measure that variance, so a "pass" at 94.25 is statistically indistinguishable from a lucky nondeterministic draw of an unchanged (or worse) trajectory. Whatever verdict it yields, the experiment cannot attribute it to fan-out. This is the core validity problem and no amount of preflight machinery addresses it.

**2. [Verification step 5 / proposal "Immutable-corpus trajectory safety"] The 600s+ safety gate is calibrated to admit the candidate and structurally cannot detect the primary failure mode the proposal itself names.** The bounds (whole-model update ≤5×, ≤25% of param norm; per-Conv update ≤50% of tensor norm; ratios ≤5×) are explicitly widened to "leave room" for the anticipated 10.67× stem / 2× transition relative updates — so they only trip on a catastrophic blow-up, not on the actual risk. The proposal's top-ranked risk (medium-high) is that "compute-neutral init changes pass short probes but suppress full strong-phase fit" (EXP012/015) — a *slow-horizon underfit* that a ~264-step fixed-corpus replay cannot surface. The gate therefore passes exactly the failure it is blind to, while consuming the majority of the experiment's wall-clock. Treat "trajectory safety passed" as evidence of no NaN, not evidence of safety.

**3. [Verification step 5 vs. step 6] The preflight validates a numerical/optimization regime that is not the production regime, so passing it does not bound production.** The replay uses (a) deterministic backends (`CUBLAS_WORKSPACE_CONFIG=:4096:8`), (b) CPU-ordered fixed corpora, and (c) **constant LR 0.1 / 0.01**. Production uses (a) nondeterministic TF32 cuDNN, (b) the live data pipeline, and (c) an *elapsed-time cosine* schedule (`progress = total_training_time / TIME_BUDGET_S`, train.py:229) where LR 0.1 is held only briefly. The update-geometry bounds measured at a constant 0.1 do not correspond to the decaying-LR trajectory that actually runs. The plan words this as an authorization gate ("Production is authorized only if…") which overstates a screen that is, by its own admission, "representative rather than proof."

**4. [Verification steps 6–7 / abort criteria] `best_test_acc` is a running max over timing-dependent per-epoch tail evaluations, and only the *absolute* 19-look ceiling is gated — not parity with the baseline's look count.** Evals fire once per epoch in the dense tail (train.py:287–296), so the number of maxima draws depends on how many epochs land after `LR_HOLD_FRACTION` within the 300s budget. If the candidate completes 19 tail evals while the EXP-010 baseline completed 18, the candidate gets a structurally extra chance at the maximum unrelated to init quality. The plan caps at 19 but never requires the candidate's look count to *equal* the baseline's, so an asymmetric extra look (18 vs 19) can supply up to a tenth-of-a-point of "improvement" that is pure look-count inflation. Given concern #1's noise scale, this matters. Gate on equal look count, not just ≤19.

**5. [Verification step 1 / abort criteria — lower priority] Pervasive hardcoding of "94.25 from 94.15" invites a stale comparator despite the re-query instruction.** The threshold 94.25 is baked into Milestone 3, step 1, step 2, and the abort criteria, while only step 1 says to re-derive it from `exp-index.sh baseline`. If the moving baseline has advanced (any committed improvement since `7c1e7d8`), the hardcoded gate silently under-shoots. Make the derived value load-bearing and delete the literal from the downstream sections, or the abort logic can run against a stale number.

**6. [Code Changes / Execution Environment — path consistency, low priority] The preflight controller path is stated two ways.** "Code Changes" says create `experiments/034/preflight_fanout.py`; Verification step 5 runs `.autoresearch/goals/maximize-cifar10-best-test-accuracy/experiments/034/preflight_fanout.py`. Both land in the gitignored experiment dir (no scope violation), but the relative-vs-absolute mismatch should be reconciled so the run command and the artifact location cannot diverge.

Note on scope: the production diff is genuinely confined to the `_weights_init` branch in `train.py` (the only writable file), the Linear call is preserved verbatim, and `mode="fan_out"` does not change RNG draw count — so downstream RNG/data/CutMix order is preserved and construction stays clean. No scope or RNG-attribution flaw there; the concerns above are about whether the *measurement* can support the verdict, not whether the code change is in-bounds.
