## Adversarial Plan Review — EXP-013 (Batch-256 Linear Scaling)

### 1. [Verification Protocol steps 9–10; idea "Expected Phase Exposure" / "Dense-tail wall amplification"] Evaluation multiplicity inflates the primary metric — treated only as a wall-time cost, never as an accuracy confound.
`best_test_acc` is `max` over every per-epoch evaluation (`train.py:288-292`, `dense_tail_due = progress >= LR_HOLD_FRACTION` fires once per epoch after 80%). Because batch 256 has only 195 steps/epoch, epochs are shorter in counted time, so the plan itself projects **~22–23 evaluator calls vs EXP-010's 19** (idea lines 276-278). Those extra ~3–4 draws land in the annealing tail, exactly where test accuracy peaks and where `best_acc` is set. Taking the max over more terminal snapshots systematically biases `best_test_acc` upward independent of any genuine training improvement. The gate is only +0.10 pt (94.15→94.25), which the plan itself calls "ten test images" — well within the max-of-more-draws bias. The goal's anti-gaming clause explicitly forbids gains "rather than seed selection or evaluation changes" (`01-definition.md:5`); a higher evaluation count is effectively an evaluation change. **The plan flags the extra evals only as a 540s wall-time risk (Milestone 2/3, idea "Dense-tail wall amplification") and never as a confound to the head-to-head accuracy comparison against a 19-eval baseline.** This is the central threat to the validity of any positive verdict and it is unaddressed.

### 2. [Verification step 10 "mechanism integrity"] Passing the image-slot integrity check does not rule out that a positive result is driven by concern #1.
Step 10 computes `image_slots = num_steps * 256 >= 4.131M` and treats that as confirming "mechanism integrity." But that check only proves the run processed more images; it provides zero evidence that any accuracy delta came from exposure rather than from the extra tail-evaluation draws. The plan presents exposure-confirmation and accuracy-improvement as if the former validates the causal story for the latter — it does not. A null exposure effect plus 3–4 lucky tail draws would satisfy every "mechanism-supporting diagnostic" (switch ≥87.08%, first weak ≥93.16%, ~50% CutMix) the plan lists while the +0.10 gate is crossed by measurement noise.

### 3. [Code Changes / idea "Mandatory Real-Loader and Wall Gates"] "The evaluator remains fixed at batch 256" is a mischaracterization that feeds the wall-time projection.
The evaluator is `Eval()` imported from `prepare.py` (`train.py:14,35`) and is independent of the module-level `BATCH_SIZE` constant — changing `BATCH_SIZE` to 256 affects only `make_train_loader` (`train.py:127`) and the cosmetic `img_per_sec` log line (`train.py:261`). The eval pass cost is whatever `prepare.py` fixes it at, unchanged by this experiment. The plan's claim (idea line 273: "The evaluator remains fixed at batch 256") is simply wrong terminology. It is harmless to correctness, but the 540s projection (step 7) multiplies `projected_eval_count * measured_eval_pass_seconds`; if the eval-pass measurement is taken believing eval batch size scaled with training batch, the per-pass number could be mis-attributed. Verify the eval-pass timing is measured as-is and the projection uses the true (unchanged) eval cost.

### 4. [Milestone 2 / Verification steps 5-7 / Abort Criteria] Pre-run gates risk being rubber-stamped from the already-known diagnostic numbers rather than re-measured.
The plan repeatedly pre-fills the answer — "The observed 1.5571 step ratio, 28.44% image-throughput gain, and 1,120.2 MB peak pass these gates with useful margin" (idea line 246) — before the paired H20 timing is actually re-run. With the "pass" values already asserted, the executing agent may treat steps 5–7 as confirmatory box-ticking and skip genuine fresh-process re-measurement. The gate is only meaningful if the five alternating pairs are actually run and the CV/throughput/headroom values come from that run, not copied from the prior serial diagnostic. Nothing in the plan forces the measured numbers into `03-execute.md` in a way that distinguishes re-measurement from restatement.

### 5. [Abort Criteria / idea "no warmup" predeclaration] The counted-budget timer excludes loader wait, which weakens the loader-saturation abort as a protection for the exposure premise.
`t0` is set at `train.py:225`, *after* the blocking `for inputs, targets in train_iterator` fetch (`train.py:218`). So iterator wait is excluded from `total_training_time` (the 300s counted budget) and only shows up in wall time. This means a loader that cannot sustain 256-sample N1/M7+CutMix batches will *not* reduce the counted GPU-step count — the run will still "spend" 300 counted seconds of GPU compute and hit its image-slot target — while wall time silently inflates and drives even more tail evaluations (compounding concern #1). The real-loader gate (idea "Mandatory Real-Loader and Wall Gates") checks `wall/count <= 1.05` in a 500-step probe, but a probe passing at 500 steps does not guarantee sustained delivery across ~17k steps and 84–89 passes as worker prefetch buffers drain. The loader-saturation failure mode is thus more consequential than the plan's framing (a mere wall-time nuisance) suggests.
