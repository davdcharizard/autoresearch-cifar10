Below is my adversarial review of the concrete plan. Concerns are ordered hardest/most-fundamental first. Each is tagged to the plan section it attacks.

---

**1. [Execution Environment → "Estimated runtime ~350–450s" + Config Changes → validation cadence] The wall-clock savings that justify the whole timeout-safety argument are unquantified and may not exist.**
The baseline ran 595.4s end-to-end (brainstorm line 22). The plan asserts the run will now finish in 350–450s, which implicitly credits removing ~78 evaluations (99 → ~21) with recovering ~150–245s, i.e. ~2–3s *per eval*. But the baseline's untimed overhead (595.4 − 300 − startup ≈ 290s) is spread across ~96 epochs and includes **per-epoch/per-step training-data-loader wait**, which is untimed (`t0` is set *inside* the batch loop at train.py:167, so the `for ... in train_loader` fetch stall between iterations is excluded from `total_training_time`) and is **independent of eval frequency**. Reducing evals does not reduce epoch count (still time-bound at ~96) or that per-epoch data-loading cost. If per-eval cost is actually ~1s (40 test batches, forward-only), the true saving is ~80s → total ~515s, not 350–450s — leaving the run near the 600s hard abort it claims to have removed. The plan provides no measurement of per-eval vs per-epoch-data cost to back the estimate. This is the plan's central safety claim and it is unverified. Action: measure the per-eval cost (or set `persistent_workers`/reduce loader restarts) before trusting the margin.

**2. [Validation policy (lines 40–49) + Verification NC1] Self-handicapped measurement vs. the baseline it must beat.**
`best_test_acc` is `max` over *evaluated* epochs. The baseline's 91.67 was the max over **99** evaluations; this plan takes the max over **~21** and leaves the **60%–80% window completely unmonitored** (coarse checkpoints stop at 60%, dense eval starts at 80%). At 60% the cosine LR is still ~0.045 and at 80% ~0.014, so accuracy is still climbing through that blind spot. If the true peak lands in 60–80%, or between two sparse early checkpoints, the reported `best_test_acc` under-counts the model's real best while the baseline enjoyed full-density sampling. That asymmetry can manufacture a false `no-improvement` verdict on a genuinely-better training run. Action: at minimum extend dense eval down to ~60–70%, or add checkpoints in the gap.

**3. [Config Changes → Learning-rate scheduler (line 53)] Collapsing the high-LR phase from ~83% to 15% is a large, under-hedged bet, not the "negligible" change the plan frames.**
The brainstorm (line 21) notes the baseline holds lr=0.1 until ~83% of the budget. This plan holds 0.1 for only 15% then cosine-decays, so for the middle ~68% of training the effective LR is far below the baseline's. The stated hypothesis (terminal refinement wins) is plausible, but the plan repeatedly characterizes this as "essentially no throughput/compute cost" (line 27, 51) and conflates *cost* with *risk to the metric*. Drastically curtailing high-LR exploration can underfit a 0.27M-param net and *lower* accuracy. The 15% hold is the only mitigation and it is a guess. This is the primary way the experiment fails to clear +0.1pp even when executed correctly; the plan should acknowledge it as the dominant metric risk, not a free change.

**4. [Milestone 1 / Config Changes] Nesterov + cosine are changed together — improvement is non-attributable.**
Two training-dynamics variables move at once (Config Changes lines 52–53). If `best_test_acc` improves, the plan cannot say whether the schedule or Nesterov drove it. The brainstorm pre-registers "cosine-with-standard-momentum" as a disambiguation follow-up, so this is acknowledged — but it means EXP-001's result, improvement or not, gives ambiguous causal evidence for the schedule fix that is supposedly the point of isolating this experiment.

**5. [Verification NC1, lines 84–86] The pass threshold can be cleared below the goal's real bar via rounding.**
`best_test_acc` is printed with `%.2f` (train.py:228). NC1 passes on `best_test_acc >= 91.77` parsed from that rounded string. A true value of 91.765 prints as `91.77` and passes, though its true delta over 91.67 is 0.095pp — under the goal's "at least 0.1 percentage points" (definition line 26; TASK.md line 28). This is a measurement-gaming edge: the plan should require the printed value to be strictly ≥ 91.78 (or compare at higher precision) to genuinely satisfy the 0.1pp rule.

**6. [Verification NC3, line 93] Duplicate-eval check is coupled to an exact print string the plan also edits.**
`rg '^  eval ep '` depends on the two-space `\n  eval ep {epoch:3d}` format at train.py:210–212 surviving the rewrite of the validation block. Since Milestone 1 restructures exactly that print/eval region, a formatting change (or dropping the leading two spaces / epoch field) silently breaks the uniqueness verification — it would return zero lines and vacuously "pass." The plan should pin the eval-line format as an invariant, not assume it.

**7. [Code Changes, line 27 — "compute the LR before every optimizer update from prior accumulated `total_training_time`"] LR-source timing under-specified where it matters for the terminal phase.**
`total_training_time` is only incremented *after* `torch.cuda.synchronize()` (train.py:178–180), so "prior accumulated" means the schedule always lags one step. This is harmless mid-run, but note the loop terminates the instant `total_training_time >= 300`, so `progress` reaches ~1.0 (and lr ~1e-4) only at the final step — the model receives essentially zero optimizer steps at the intended terminal LR. That is inherent to cosine, but it undercuts the plan's repeated framing of a "genuine refinement phase" (lines 54, 27): the refinement is a limit, not a phase. Worth confirming the last few percent of decay actually delivers the claimed benefit rather than being a vanishing tail.
