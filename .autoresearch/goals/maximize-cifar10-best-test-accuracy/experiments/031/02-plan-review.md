Review of EXP-031 plan (execution soundness / gates / reward-hacking / leakage). Concerns ordered hardest-first, each tied to the section it attacks.

---

**1. Absolute step-floor gate on a wall-clock-budgeted run is invalid — it conflates candidate overhead with node-speed variance (Milestones 2–3; Verification steps 5–7; Config "≥26,629").**
`num_steps` is an *output* of the `while total_training_time < TIME_BUDGET_S` loop in `train.py:213` — it varies run-to-run with node conditions, not just with the candidate's cost. Yet step 7 makes `>= 26,629` a hard *integrity* precondition for the improvement verdict, and step 8's improvement decision sits behind it. A genuinely-better candidate with **zero** overhead can land at 26,500 steps simply because the H20 was ~1% slower that hour, and the plan would mark it invalid. Exposure control already lives correctly in the *paired-ratio* gate (step 5, `candidate/control`); duplicating it as an absolute production floor is both redundant and wrong. Worse, combined with "one unchanged retry for documented external infrastructure failure" (Abort Criteria), the floor creates a retry-until-fast-node loophole: a sub-floor run can be relabeled "infrastructure" and re-run until a faster node clears both the step floor and the accuracy gate — favorable-condition selection. Remove the absolute step floor from the verdict; keep only the measured ratio gate.

**2. The reference step count 26,898 is an unverified literal underpinning the entire timing gate (Verification steps 5, 7, 8; Config).**
`floor(26898*control_mean/candidate_mean) >= 26629`, "at least 26,629 steps," and "Compare steps with 26,898" all hinge on 26,898 being the accepted recipe's actual step count on *this* node *today*. Nothing in the plan derives it — not from a same-day fresh baseline, not from EXP010's log. Historical step counts quoted across learnings scatter widely (27,143 / 27,268 / 26,469 / 23,465). If 26,898 is stale, the "1% overhead" gate is silently miscalibrated. Derive the control step count from the fresh paired control arm (or a same-day baseline run), not a hardcoded constant.

**3. The "bounded ≤10% residual" guarantee — the central safety claim — is never verified over the actual production trajectory (Milestone 1 calibration; Adversarial Review Response "scale-drift observability"; Verification steps 2, 4).**
Three facts compound: (a) `s` is frozen from **initialization in eval mode** (step 2), where BN running stats are default (mean 0, var 1) and the net is essentially random-conv + identity-BN — an activation regime with little relation to the trained descriptor scale that matters during the run; the plan itself concedes "initialization calibration does not guarantee later descriptor scale." (b) The exact-corpus replay (step 4) only observes RMS from short from-state windows over EXP022/EXP028 batches — not the 26k-step production path. (c) The only observer that spans the real run is the eval-mode diagnostic, which is *explicitly non-blocking* ("cannot veto a completed metric," Abort Criteria line 46). Net: the area-insensitivity / CutMix-artifact-amplification risk the review names as load-bearing has **no gate that can stop a run** where the residual blows past 10% in mid-training. The plan presents drift observability as a safeguard; it is only telemetry. Either justify why init-calibrated `s` bounds the trained residual, or add a blocking mid-training scale check — otherwise the safety apparatus is theater around an unbounded quantity.

**4. Corpus dependencies are assumed present but never confirmed (Milestone 2; Verification step 4).**
Step 4 requires EXP022's 200-batch corpus (`e04dc2f…`) and EXP028's 64-batch corpus (`ffefe98…`) to exist on disk with matching SHA-256. These are prior-experiment artifacts under `experiments/`; the goal's own protocol mandates removing completed logs and discarding code on non-improvement, and there's no guarantee these serialized tensors survived. If either file is absent, all of Milestone 2 is unrunnable and there is no fallback. Add an explicit existence+hash precheck before committing to the safety milestone.

**5. Calibration must byte-match production init, and the device/mode choices are underspecified (Milestone 1; Verification step 2).**
`train.py:158-186` seeds `manual_seed(42)`+`cuda.manual_seed(42)`, constructs `ResNet` on CPU (Kaiming init draws from the CPU RNG), *then* `.to(device)`. If the calibration controller constructs on GPU, or in a different op order, it draws a different init and produces a different `s` than production actually sees — silently. The plan says "identical model/source/corpus hashes" but doesn't pin construction device/order or state that BN is at default running stats. Specify: same seed, same CPU-construct-then-`.to(device)` order, and record the init tensor hash so the frozen `s` is provably the one production instantiates.

**6. The eval-mode diagnostic must piggyback on `Eval.evaluate()`'s existing forwards, and this is left implicit (Code Changes; Verification steps 3, 7).**
`Eval.evaluate(model, device)` (`train.py:289`) is read-only and runs its own forward passes over the **test set**. For train.py to "accumulate around each evaluator call" without adding a separate forward pass or extra `evaluate()` call, `ResNet.forward` must stash detached descriptor stats each call and train.py reads the attribute after `evaluate()` returns. The plan never states that no additional forward/eval pass is introduced — yet step 7 gates on "evaluator call count unchanged" and "18-19 unique evaluator epochs." Make explicit that the diagnostic adds zero forward passes and zero `evaluate()` calls. Also note for the record: the reported ratio is therefore a **test-set** statistic — harmless as pure telemetry, but this makes the "must not retune `s`" prohibition (Adversarial Review Response) load-bearing against leakage; keep it absolute.

**7. Minor — hardcoded budget assumptions (Verification steps 6-7).**
`300.0 <= training_seconds < 301.0` and the `595s` bound assume `TIME_BUDGET_S == 300` from `prepare.py`. This is consistent with EXP-001's recorded 300.0s, but the gate is brittle if the imported budget ever differs; assert against the imported `TIME_BUDGET_S`, not the literal 300, so a budget change surfaces as a clear failure rather than a spurious integrity violation.
