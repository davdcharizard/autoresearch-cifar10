I've read the plan, goal definition, brainstorm, idea review, learnings, `train.py`, and `prepare.py`. Below is the bounded, prioritized concern list. The core mechanic (RandomErasing `scale=(0.25,0.25)`, `ratio=(1,1)` → deterministic 16×16 = 256-pixel patch; `value=0` = per-channel mean given `std=(1,1,1)`; `inplace=True` safety) checks out and I say nothing about it.

### 1. Verification never confirms Cutout was actually applied in the plateau loader — the whole experiment's validity rests on an unverified wiring (§ Verification Protocol step 5; Code Changes; Milestone 1)
The `augmentation_switch: cutout->base` line is a **hardcoded string** (Code Changes line 49), not derived from the transform actually wired into `make_train_loader`. Every run-time integrity gate — one `cutout->base` line, no `randaugment->base`, `workers_stopped: 8`, step count, param count (steps 4–5) — would pass identically even if the first loader were mistakenly initialized with `weak_train_tf` or the un-renamed `strong_train_tf`. The *only* mask-semantics check (Preflight step 3) is run on a **separately-constructed transform object in a throwaway process**, not on the object `make_train_loader(cutout_train_tf)` feeds the training loop. So a copy/paste error in the loader init (line 48) that trains a bare crop/flip plateau is undetectable by the protocol and would still be recorded as a valid Cutout run. The experiment claims to test occlusion vs RandAugment, but nothing in the run's own evidence proves occlusion was present. Add a runtime assertion (e.g., sample a batch from the live plateau loader and assert 256 masked positions) before this is treated as a category test.

### 2. Throughput-equivalence hypothesis guards the wrong side; the likely outcome (more steps) is a silent confound (§ Baseline/Hypothesis line 8; Verification steps 4 & 6; Decision Rules)
Cutout is a single tensor slice-fill; RandAugment is a PIL-based op with round-trips — the plan itself calls Cutout "cheaper than PIL RandAugment" (brainstorm). So EXP-006 will very likely produce **more** than EXP-004's 38,358 steps, not "at least 98.5%." But the only step gate is a floor (`num_steps >= 37783`), and step 6 only flags a gain accompanied by *fewer* than 37,783 steps as confounded. A run at, say, 39,500 steps that clears 92.40% would be accepted as "canonical Cutout beats N1/M7" and even as a "reusable recipe," when the gain could be driven by extra gradient steps (more optimization under fixed wall-time) rather than the occlusion mechanism. The plan's interpretation constraint (line 9) only hedges single-seed noise, not this step-count asymmetry. Either add an upper-side step check that flags materially-more-steps as a cheaper-augmentation confound, or explicitly re-scope the causal claim to "under fixed time, whatever step count Cutout buys."

### 3. The transform change is a positional restructure, not a literal swap; Milestone 1 phrasing invites a crashing edit (Milestone 1 bullet 2; Code Changes lines 37–47)
RandAugment currently sits at position 3 of the Compose — **before** `ToTensor` (`train.py:164`), operating on a PIL image. RandomErasing must go at position 5, **after** `Normalize`, operating on a tensor. Milestone 1 says "replace the plateau transform's RandAugment with … RandomErasing," which reads as an in-place literal substitution; done literally, RandomErasing receives a PIL image and raises `TypeError`. The correct final order appears only in the prose of the Code Changes block (line 47). This is the single highest-risk mechanical step and is guarded solely by Preflight step 3 — call it out in the milestone itself so it isn't executed as a one-line swap.

### 4. Preflight mask-count criterion is fragile w.r.t. the synthetic data it runs on (Preflight step 3; Milestone 2 / Verification "exactly 256 all-channel-zero positions")
The check counts "spatial positions where all channels are zero." Off-patch pixels that happen to be all-zero (e.g., if the synthetic tensor is constructed with zeros, or a channel coincidentally hits the mean) inflate the count above 256 and fail a semantically-correct mask; conversely a degenerate synthetic input could undercount. The criterion is only sound if the synthetic tensors are guaranteed nonzero off-patch (e.g., `randn` shifted away from 0). Specify the synthetic-data construction, or check the patch by bounding-box location rather than a global all-zero count.
