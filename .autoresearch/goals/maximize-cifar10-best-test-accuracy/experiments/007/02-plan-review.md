# Adversarial Review — EXP-007 Width-2 Execution Plan

## 1. [Exposure gate — internally inconsistent, can abort a scientifically valid run] The pre-launch `calibrated_steps >= 26,500` gate contradicts the plan's own post-launch stance
`02-plan.md:22, 91` make ≥26,500 calibrated steps a **conjunctive launch gate**: 26,000–26,499 is "explicitly a no-go." But `02-plan.md:98` states that once launched, "actual steps below 26,500 are a result to analyze, not grounds for a retry. The fixed-time goal judges net accuracy." The LR schedule is elapsed-time-driven (`train.py:206–215`), so it completes its full trajectory at *any* step count. These two positions are incompatible: the **same exposure level (e.g. ~26,400 steps) is disqualifying before launch but a valid result after.** The only defensible purpose of a feasibility floor is "don't run a doomed config," yet the plan's entire thesis is that lower exposure is not doom — it is the capacity/update tradeoff the experiment exists to measure. As written, the gate's main effect is to refuse to run the very experiment whose point is to measure that tradeoff, producing **no metric at all** (routed to "preflight-infeasible," `02-plan.md:134`) for a run that would have been perfectly analyzable. Either drop the launch floor to a genuine doom threshold (e.g. schedule integrity, OOM, non-finite), or justify why 26,499 projected is worthless while 26,499 actual is publishable.

## 2. [Exposure gate — noise-dominated margin] The 26,500 gate sits 0.24% below the point estimate, while the plan tolerates ~3% timing CV
The measured calibrated projection is 26,563 (`idea-01.md:158`), only **63 steps (0.24%) above the 26,500 floor**. Yet Milestone 2 admits benchmarks with per-width CV up to 3% (`02-plan.md:22`), and the ratio of two such measurements carries ~4% dispersion. Concretely: EXP-004's own synthetic-vs-real gap was 4% (synthetic 39,921 vs actual 38,358 steps for width-1). A fresh plan-time benchmark clocking the width ratio at 1.448 instead of 1.444 yields `38,358/1.448 ≈ 26,490 < 26,500` → abort. The launch decision is therefore governed by microbenchmark noise an order of magnitude larger than the gate margin — the threshold reads as reverse-engineered to the already-known 26,563 figure rather than as a real feasibility boundary. Combined with #1, there is a substantial chance this plan aborts at preflight and burns the loop iteration with no result. If a floor is kept, it needs margin below the point estimate, not a value pinned to it.

## 3. [Verification — spurious-failure risk] The tightened `training_seconds < 301.0` integrity gate can fail on a single slow step unrelated to the science
`02-plan.md:30, 117` require `300.0 <= training_seconds < 301.0`; EXP-004 used `< 310.0` (`004/02-plan.md:25`). The loop accumulates `dt` per step and breaks only after `total_training_time >= 300` (`train.py:227, 248`), so `training_seconds` overshoots by up to one step's `dt`. Nominally ~11 ms (fine), but a single loader stall or GPU-contention hiccup on the boundary step (the plan itself flags host-starvation and clock drift as live risks, `idea-01.md:218–219`) can push that one `dt` past 1 s, failing an integrity condition that has nothing to do with capacity. EXP-004's 10 s slack existed precisely to absorb this. Tightening to 1 s of headroom converts a benign timing jitter into a discarded run.

## 4. [Decision rules — over-attribution band] The post-hoc exposure threshold silently shifted 26,000 → 26,500 versus the reviewed proposal
`idea-01.md:281–282` route "no improvement with steps ≥26,000" to normal underfit/overfit analysis and only "steps <26,000" to "throughput shortfall as a primary confound." The plan raised this to 26,500 (`02-plan.md:133`). Consequently a valid run landing at, say, 26,200 actual steps — which the reviewed idea treated as adequate exposure worth analyzing on its merits — is now labeled "throughput drift as a primary confound," reverted, and routed to "re-benchmark before any new width experiment." This over-attributes an ordinary fixed-time result to clock drift and can bury a genuine capacity signal. The analysis threshold should not have been quietly co-moved with the launch gate.

## 5. [Premise carried into execution unresolved] The capacity hypothesis cannot be cleanly falsified, and the idea-review's #1 precondition was overridden
The idea-review's first *required* refinement was to read EXP-004's train-loss-under-N1/M7 **before planning**, and to "switch to idea-04" if the model looked generalization-limited (`01-idea-review.md:64`). The plan instead declares the value unrecoverable and proceeds (`02-plan.md:9`). The justification — re-running the baseline would be an unplanned duplicate stochastic run — is reasonable, but the consequence is unmitigated: EXP-001 reached train loss 0.0215 (`03-experiment-learnings.md:72`), pointing to a *generalization* limiter, so a width-2 no-improvement cannot distinguish "capacity was never the bottleneck" from "too few updates." The failure routing (`02-plan.md:131–132`) partially covers this by branching on tail-slope/overfit signature, but those signatures are themselves noisy on a single ~14-eval tail. The plan should state plainly that this experiment cannot confirm the capacity diagnosis on a null result, only generate a follow-up direction.

## 6. [Trajectory / metric resolution] Once-per-epoch eval over ~14 tail epochs coarsely samples `best_test_acc` exactly where EXP-004 peaked
EXP-004 peaked at epoch 98 of 99 — the penultimate epoch of a ~20-epoch tail (`004/04-analysis.md:23`). Width-2 projects only ~13–14 tail epochs (`02-plan.md:66`), and eval fires once per epoch (`train.py:260–266`). The primary metric (`best_test_acc`) is a max over these discrete eval points; a real accuracy peak occurring *between* two tail epochs is simply never observed. This is a distinct penalty from raw update loss and it directly attacks the primary metric, not just the analysis. The plan elevates tail-shape/slope analysis (good, `02-plan.md:31–32`), but that is a diagnostic; it does not restore the lost best-metric sampling resolution near the historically decisive region. Worth stating as a known downward bias on the metric itself, so a marginal miss (e.g. 92.35–92.39%) isn't misread as a clean capacity refutation.

## 7. [Gate pattern] Multiple launch gates are pinned to their point estimates, not set with margin
Beyond #2: the weak-tail-epoch gate is ≥13 against a measured 13.6 (`idea-01.md:169`), and raw throughput ≥85 steps/s against 92.1 (8% margin, `idea-01.md:170`). The 13.6-vs-13 case is especially fragile — a fresh benchmark 3% slower drops projected tail epochs below 13 and aborts. This is the same reverse-engineered-threshold pattern as the step gate; the conjunctive AND of several point-estimate-pinned gates compounds the preflight abort probability from #1/#2.
