# Adversarial Review — EXP-008 Plan (Width-2 Weight Decay 5e-4)

**Verified load-bearing facts.** Intervention is a genuine one-literal change: `WEIGHT_DECAY = 1e-4 → 5e-4` at `train.py:28`, consumed by the single `optim.SGD` group at `train.py:177-179`. Decay is coupled L2 (no RNG consumption, same kernel/FLOPs), so EXP-008 shares EXP-007's exact data order and augmentation stream — attribution is genuinely clean. `TIME_BUDGET_S = 300` (`prepare.py:7`), loop stops at counted-time ≥300 (`train.py:198,250`), switch fires purely on time at 80% (`train.py:254`) independent of decay. EXP-007: 27,143 steps, 71 epochs, strong checkpoint 90.08% @ep56, best 93.55% @ep67, tail evals ranged 93.36–93.55 (`007/03-execute.md:60-61`). Baseline 93.55 @ `8faf0f3` confirmed in `04-results.tsv`.

The scope, coupled-decay framing, and RNG-neutrality of the plan are sound; I say nothing further about them. The concerns below are ordered hardest first.

---

### 1. The step-count floor is a hard improvement gate that can veto a goal-valid win the intervention provably didn't cause. (Decision Rules "Improvement" line 95 + "Step shortfall" line 98; Milestone 3 line 25; Verification step 6 line 83)
The "Improvement" rule requires `best_test_acc ≥ 93.65%` **AND** `≥ 26,872 steps`. But the goal's necessary conditions (`01-definition.md:26-28`) impose **no** step-count requirement — the budget is fixed *time* (300 counted s), under which step count is expected to vary run-to-run. Weight decay is compute-neutral (same optimizer kernel, no added ops), so any step difference vs 27,143 is pure node-timing noise, not a property of the intervention. Yet if a run lands at, say, 26,800 steps *and* passes 93.65%, the plan reclassifies it as "exposure drift is a primary confound" (step 6) and denies the improvement verdict. `best_test_acc` is a max over ~21 evaluations spread across the whole run; it does not hinge on the final few hundred steps. So this gate can throw away a real, goal-valid accuracy gain over a sub-percent timing wobble that the plan's own mechanism argument says cannot affect the result. The step count should be *informational* for attribution, not a veto on the improvement verdict.

### 2. The compute-equivalence floor (99%) is tighter than demonstrated timing variance, and there is no EXP-008 step preflight to calibrate it. (Config "Expected steps" lines 43-44; Preflight step 4 line 61; Verification step 6 line 83)
The floor 26,872 = 99% of EXP-007's actual 27,143 — a ±1% band. But the only evidence about how much this quantity moves is EXP-007's own calibrated projection (26,469) vs actual (27,143), a **2.55% gap** (`03-experiment-learnings.md:54-56`; `007/03-execute.md:21`). The plan explicitly forgoes a GPU step benchmark for EXP-008 (Preflight step 4), so the sole reference is a *single* prior full-run number. Full runs carry contention noise the 0.3–0.45% microbenchmark CV doesn't capture (DataLoader warmup, the mid-run loader teardown/rebuild at the switch, `gc.collect()`). A genuinely compute-neutral run can plausibly dip below 26,872 from node load alone, then be falsely flagged "the scalar cannot plausibly explain it" (step 6). This directly feeds concern #1: an over-tight, uncalibrated floor manufactures the "confound" that vetoes a valid result.

### 3. Marginal-pass fragility: the metric is a max over ~21 noisy evals, and intra-run tail noise exceeds the +0.10 bar — yet the plan accepts a bare pass with no corroboration. (Decision Rules "Improvement" line 95; Abort line 68)
`best_test_acc` is `max` over all evaluations (`train.py:270-271`). In EXP-007 the late-tail evals alone spanned 93.36–93.55 — a ~0.19 pp intra-run spread, *wider* than the +0.10 (=10 test images) improvement bar. A single-seed run with no reroll can therefore clear 93.65 on one lucky tail epoch without a genuine shift in the underlying trajectory. The plan's acceptance is asymmetric: Abort criteria (line 68) forbid retrying a *marginal fail*, but the "Improvement" rule accepts a *marginal pass* on the bare threshold with no robustness guard (e.g., corroborating with a smoothed tail level or final-acc, both of which the plan already persists). A pass at 93.65–93.70 should be flagged as within-noise rather than recorded as a clean improvement. (The metric is goal-defined, so this is a framing/robustness gap, not a metric change — but the plan can add the corroboration it already collects.)

### 4. The overfit premise cannot be re-established at plan time, yet the plan proceeds as if it can, leaving a null uninterpretable. (Baseline/Hypothesis "Evidence boundary" line 9; brainstorm line 14; idea-review #1; mechanism line 46)
The whole experiment rests on "declining train loss + flat/rising test loss ⇒ late excess fit ⇒ norm control is the next limiter." Two of the three supporting numbers ("train EMA → ~0.04", "test loss bottomed near 0.214") live only in EXP-007's deleted raw log — they are absent from `007/03-execute.md`/`04-analysis.md`, which persist only final loss 0.2196 and near-switch EMA 0.2283. The idea-review's #1 asked for a *plan-time re-read* of this signature before committing; that re-read is now impossible, and the plan (line 9) merely labels it an "advisory" premise, then proceeds unchanged. Compounding this: the observed overfit is a **tail** phenomenon, but idea-04 shows 5e-4's shrinkage is concentrated in the high-LR plateau and *auto-weakens* in the low-LR tail (`007/proposals/idea-04.md:61`) — the plan's "carries into the weak tail" link (line 46) is indirect. Consequence: a null result cannot distinguish "5e-4 is the wrong magnitude," "the plateau→tail coupling doesn't hold," and "the overfit premise was never real." The plan should state this three-way ambiguity so a null isn't over-read as "decay doesn't help."

### 5. The "ten unique finite values" integrity check has a false-failure mode on a valid trajectory. (Verification step 4 line 81; Milestone 3 line 24)
`best_test_acc == final_test_acc` is a legitimate outcome — it occurs whenever the best eval is the terminal epoch, which this goal has already seen ("monotonic annealed trajectory with final equal to best," `03-experiment-learnings.md:118`). Requiring the ten summary fields to be *unique* would then fail integrity on a perfectly valid run (and could also collide on other coincidental equalities). The check should require ten fields **present and finite**, not distinct; "unique" adds a spurious rejection path with no integrity justification.
