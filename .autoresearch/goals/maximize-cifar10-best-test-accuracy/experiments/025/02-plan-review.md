Having read the plan (025/02-plan.md), the brainstorm (025/01-brainstorm.md), the goal (01-definition.md), the cited proposal (024/proposals/idea-01.md), the results TSV, the learnings, and `train.py`, here is the prioritized execution-soundness concern list.

---

## Concern 1 — Acceptance margin is inside run-to-run noise; the single fixed-seed scored run is close to a coin flip regardless of ECA merit
**Sections:** Milestone 4 / Verification step 7 / Hypothesis; proposal §"Small statistical margin"
The whole intervention is 15 parameters that are *exactly* identity at step zero (2·sigmoid(0)=1.0 bitwise, zero kernel → dgate/dresidual=0, so even step-0 shared gradients are identical to control). The target is +0.10 pp = **10 CIFAR-10 test examples**, measured as max-over-checkpoints on **one seed (42), no reroll**. Nothing in the plan bounds the expected effect size relative to the metric's own variance, and the design has no replication to separate signal from noise. Concretely this creates an asymmetric-cost trap the plan does not address: under loop discipline, a `no-improvement` verdict **discards the code**, so a mechanism that is genuinely and slightly positive but lands at 94.20% due to noise is thrown away, while a null mechanism that lands at 94.26% is accepted and merged. The proposal calls a bare pass "weak evidence," but the plan still treats 94.25% as the operative gate with no noise-band caveat feeding the eventual verdict. This is the dominant risk and it is not fixable within the single-run protocol — it should at minimum be stated up front that the scored outcome is expected to be dominated by variance, not by the 15-weight change.

## Concern 2 — Safety/timing evidence is only valid if the preflight scripts reuse `train.py`'s *actual* loader/collate/model, not a reimplementation
**Sections:** Milestone 2; Verification step 4; Execution Environment (`preflight_eca.py`, `timing_eca.py`)
The immutable-corpus gate is load-bearing (EXP-016/019/020/021/022/024 all died here). The recorded learning (EXP-019/021) is explicit: *"Fresh forkserver processes do not replay post-transform batches from seed alone"* — the whole point is byte-identical production batches. But the plan's preflight lives in separate scripts under `experiments/025/` and must regenerate "the production N1/M7/CutMix path." If those scripts rebuild `strong_train_tf` / `cutmix_collate` / the `forkserver`, 8-worker, `shuffle=True`, `drop_last=True` DataLoader by hand rather than importing and invoking `train.py`'s `make_train_loader(strong_train_tf, collate_fn=cutmix_collate)` verbatim, the corpus is drawn from the wrong distribution and every downstream veto (class-concentration, gate movement, loss-EMA) tests the wrong thing while reporting "pass." The plan says "Adapt the EXP-024 corpus controller" — "adapt" is exactly where drift enters. The plan should require the corpus be produced by the imported production loader object, and assert the recorded SHA/shapes/label-row-sums against a batch pulled directly from `train.py`.

## Concern 3 — The plan invents necessary conditions beyond the goal; a formally valid win must not be downgraded by diagnostic gates
**Sections:** Milestone 4; Verification steps 7–8; Abort Criteria
The goal defines exactly three necessary conditions (best_test_acc ≥ baseline+0.1; completes with expected summary; within budget/10 min). The plan layers on many self-authored gates — `299.9<=training_seconds<=300.2`, `total_seconds<600`, "one near-80% switch," "eight stopped workers," "expected CutMix fraction," specific gate-diagnostic recording. Step 8 correctly says trajectory/NLL/gate evidence "cannot override the formal verdict," but Milestone 4 and step 7 list `training_seconds`/`total_seconds` windows as hard `require`s in "necessary-condition order." ECA adds per-step time, so overshoot past 300.0 is expected (bounded by one step's dt via the `total_training_time >= TIME_BUDGET_S` break — should stay ≤~300.02, so 300.2 is safe, but the plan should confirm this rather than assert a tight window). The risk: a run that passes 94.25% but trips a self-invented numeric/structural check gets marked invalid — self-sabotage the goal does not authorize. Any gate stricter than the goal's three conditions must be advisory only for the final verdict.

## Concern 4 — The 3.5% timing gate is very likely to fail, spending the safety/timing budget with no scored evidence
**Sections:** Milestone 3; proposal §"Paired H20 timing" and §"Launch-bound overhead"
The plan's own history says nine identity-init SE gates cost **1.233×** (EXP-012) and backward is 75.46% of step cost, i.e. this recipe is launch-bound, not FLOP-bound. Three sequential `GAP → Conv1d → sigmoid → broadcast-multiply` chains (plus their backwards) add ~12 kernel launches, yet the gate demands `≤1.035` aggregate with every pair `<1.05` and CV `<2%`. This is not a soundness flaw — a timing no-go is honestly treated as invalid — but the plan should be explicit that the most probable outcome is a timing abort producing zero scored data, and that the 3.5% budget is being set an order of magnitude tighter than the only comparable local measurement (23.3%). It also means the elaborate corpus/timing machinery is likely to gate out before the hypothesis is ever tested.

## Concern 5 — Self-authored, self-graded safety/timing thresholds are a rescue-temptation surface
**Sections:** Milestone 2/3 thresholds; Abort Criteria; Verification steps 4–5
All numeric vetoes (max weight ≤0.25, gate ranges, loss-EMA ≤1.5×, ratio ≤1.035, ≥26,000 projected updates) live in scripts the executing agent writes. The plan forbids rescue "with fewer gates, another kernel/scale, special LR/decay, fusion, memory format, or precision," which is good — but it does not forbid the subtler hack of *editing the thresholds in `preflight_eca.py`/`timing_eca.py`* after a marginal failure. These constants should be pre-registered from this plan/proposal and asserted unchanged (e.g., the exact values in proposal §safety/§timing) before the scripts are trusted, so a borderline veto cannot be quietly relaxed to let the run proceed.

## Concern 6 — RNG-isolation of the `Conv1d` construction is asserted but never independently checked against non-`fork_rng` failure
**Sections:** Code Changes (`fork_rng`); Milestone 1 identity proof; proposal §"Exact implementation"
Wrapping the `Conv1d` default construction in `torch.random.fork_rng(devices=[])` is the correct fix (the Conv1d's default kaiming_uniform draw would otherwise shift the CPU RNG stream feeding `fc` and later blocks, and `_weights_init` only re-draws for Conv2d/Linear so the Conv1d draw is not overwritten). The concern is that the plan's "bitwise-equal shared init" proof will pass *by construction* whether or not `fork_rng` is present-and-correct only if control and candidate are built from genuinely independent RNG streams — verify the equality check compares the ECA model against the **unmodified baseline model** built from the same seed, not two ECA models. If the comparison baseline is itself constructed through the new code path, a broken `fork_rng` would still show "equality" and the RNG perturbation would silently ship into the scored run. Make the identity oracle the pre-change `train.py` model at commit `7c1e7d8`.
