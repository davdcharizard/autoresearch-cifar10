Below is my prioritized concern list for Plan EXP-029. Each is tagged to the section it attacks.

## Plan EXP-029 — Prioritized Concerns

**1. [Milestone 3 / "Paired timing and exposure gates"] The 1.01 aggregate timing gate is very likely unsatisfiable, so the production path probably dead-ends before it is ever reached.**
GC is 2 unfused kernels per conv × 19 convs = 38 extra kernel launches inserted into a ~10.9 ms step. On an H20 that step is dominated by launch/dispatch overhead, not FLOPs; 38 launches at ~5–15 µs each is ~0.2–0.5 ms, i.e. ~2–4% of the step. That blows past the *aggregate* `candidate/control ≤ 1.01` gate (and plausibly the per-pair `≤ 1.04` gate). The plan simultaneously forbids the only remedies (fused/custom kernel, `foreach` rewrite, layer subset — Abort Criteria and "no-rescue boundary"). Net effect: the plan has, by its own thresholds, a high probability of aborting at Milestone 3 with no scored result, after paying the full cost of preflight + timing harness construction. This should be stated as the expected outcome, not treated as a remote edge case.

**2. [Milestone 4 vs. Verification step 7 / proposal "Production verification"] `num_steps ≥ 26,629` is specified as both a hard production requirement and an "advisory floor" — a contradiction that decides how a passing-but-short run is scored.**
Proposal "Production verification" and Milestone 4 list `num_steps >= 26,629` under *Require*. Verification step 7 and the plan's step-121 text say "do not override a protocol-valid metric improvement if exposure unexpectedly falls below that advisory floor." These cannot both hold. Worse, the floor is razor-thin: it is constructed as `floor(26,898/1.01) ≈ 26,631`, so any real-run overhead above the timing-measured 1.01 (e.g. 1.02) drops steps below 26,629. The plan must decide, before running, whether a 94.25%+ run at 26,400 steps is an improvement or invalid — otherwise the verdict is decided after seeing the number, which is exactly the post-hoc adjudication the plan elsewhere forbids.

**3. [Milestone 2 / "Immutable strong-and-weak corpus gates"] The safety preflight is a 264-batch fixed-corpus proxy (200 strong + 64 weak) but is used to clear the exact failure mode — momentum-integrated class-geometry collapse — that the plan concedes only manifests over the full ~26k-step trajectory.**
The proposal itself states (Risks; brainstorm review) that "instantaneous projection cannot increase Conv gradient norm, but this does not bound momentum-integrated trajectory geometry," and that EXP020/022/028 collapse appeared despite exact first-step matching. A 264-step replay at fixed LR cannot exercise the late high-LR-then-cosine dynamics where that collapse actually developed. Passing this preflight therefore provides weak assurance yet is treated as a green light to the single scored production run. The gate's discriminative power against the very risk it names is low, and the plan does not acknowledge that limit.

**4. [Configuration Changes / Milestone 4 / Verification step 8] Multiple hard gates hardcode environment constants (`training_seconds` 300.0–301.0, "eight workers stopped", historical 26,898 steps, projected-total 540 s) that derive from `prepare.py`'s `TIME_BUDGET_S` and `NUM_WORKERS`, but the plan never reads `prepare.py` to confirm them.**
`train.py` imports `TIME_BUDGET_S` and `NUM_WORKERS` from `prepare.py`; the plan asserts budget=300 s and workers=8 without a verification command that checks the actual values. If either differs (or was changed in a prior loop), the `300.0–301.0` validity band, the "exactly eight strong workers stop" gate, and every step-count projection misfire and can spuriously invalidate an otherwise-valid run. The plan verifies `num_params == 1,073,962` and the baseline hash but has no equivalent check binding these two imported constants.

**5. [Hypothesis / "Decay and momentum ordering" / brainstorm Review] The plan pre-concedes the mechanism is likely near-inert, making a positive result improbable by its own reasoning.**
The chosen operator is `P(g)+λw`, explicitly *not* the paper's `P(g+λw)` invariant-mean theorem (proposal "Decay and momentum ordering"), and the review notes every Conv feeds BN, which "may make common-mode filter gradients partly redundant," so "a tiny fraction plus a null result means the mechanism was near-inert." A weak decay-preserving projection on BN-normalized convs, over a training horizon ~10× shorter than the paper's, is being asked to move seed-42 best_test_acc by exactly +0.10 pp to the gate. The plan is internally honest that the expected removed-mean fraction is small — but that same reasoning predicts no improvement, and it is worth confirming this run of the single production budget is justified given the pre-declared low expected effect.

**6. [Verification step 7 / Milestone 5] The `>= 94.25%` improvement bar sits exactly at baseline + 0.10 pp against a metric printed to two decimals (`{best_acc:.2f}%`).**
A true best accuracy of ~94.245% rounds to `94.25` and would be scored as improvement, though it does not actually exceed the baseline by 0.10 pp as the goal's necessary condition requires. This boundary/rounding effect is the difference between "improvement" and "no-improvement" and is not addressed; the plan should decide whether the printed value or a true-value margin governs at the exact threshold.
