Based on my review of the plan against the goal definition, brainstorm, idea-review, `train.py`, `prepare.py`, and `TASK.md`, here is the prioritized concern list. The intervention itself (add `LABEL_SMOOTHING = 0.05`, pass to training `F.cross_entropy`) is minimal and in-scope; the concerns are about execution soundness and verification, not the idea.

---

**1. GPU dedication/idleness is never verified, only GPU identity — a confound under the ±0.1 threshold (most important).**
Milestone 2 and Verification step 2 confirm the device is an H20 with ~98 GB and that only one index is exposed, but nothing checks the GPU is *free of other workloads*. `train.py`'s budget is wall-clock-per-step (`total_training_time += dt`, with `torch.cuda.synchronize()` on line 196), so a contended GPU silently produces fewer steps in the same 300 s. Since EXP-002's baseline `91.83` was measured on its own run, a contended EXP-003 run would complete fewer of the ~38,629 updates and could spuriously fail (or, if EXP-002 was the contended one, spuriously pass). With an expected gain clustered right at `+0.10`, this is a first-order fairness confound. The plan should add a pre-launch check that the selected GPU has ~0 MB used / no other processes (`nvidia-smi` memory.used / compute processes), not just the right name.

**2. The `299.5 <= training_seconds <= 301.0` band is a *necessary* gating condition that can false-fail a genuinely passing run.**
Milestone 3 / Verification step 4 make this a hard necessary condition, but the goal (`01-definition.md:28`) only requires respecting the fixed budget and finishing within 10 minutes — the budget is *already* enforced inside `train.py`'s `while total_training_time < TIME_BUDGET_S` loop (lines 168, 219). The loop breaks only after a step pushes `total_training_time` past 300, so the overshoot equals the last step's `dt`. A single stalled step near the boundary (dataloader hiccup, driver stall, GC) of ~1–2 s would report `training_seconds ≈ 301–302` and, per the plan's own rule, classify an accuracy-passing run as invalid. This upper band is redundant with the in-code enforcement and strictly adds false-negative risk; it should be loosened or made informational.

**3. The design commits to a single fixed-seed run with an expected effect inside single-run variance — a null result is uninformative, and a pass may be noise.**
The idea-review (`01-idea-review.md:21`, #6) and brainstorm both put the LS ceiling at roughly `+0.1` to `+0.27`, i.e. the median outcome sits on the `91.93` line. The plan correctly forbids reroll (goal constraint `01-definition.md:18`) and pre-declares the verdict, so this is inherent to the goal rather than a fixable plan defect — but the plan treats `>= 91.93` as a clean causal signal (`02-plan.md:77, 100-101`). Note in `03-execute.md` that a pass/fail this close to threshold does not by itself establish/refute the intervention; don't let the binary verdict be read as a strong effect measurement.

**4. Metric granularity at the threshold: `best_test_acc >= 91.93` is evaluated on a value rounded to 2 decimals.**
`prepare.py:47` computes `100.0 * correct / total` over 10,000 examples (0.01%/example) and `train.py:260` prints `.2f`. A true best of `91.925%` rounds to `91.93` and passes on a real gain of `+0.095` (< the goal's 0.1 pp); the reverse edge fails a `+0.104`. This is a narrow edge but, combined with concern #3, means the pass/fail boundary is at the measurement's resolution limit. Worth acknowledging so a boundary result isn't over-interpreted.

**5. Minor — runtime risk if the pinned torch predates the `label_smoothing` kwarg (PyTorch < 1.10).**
Milestone 1 verifies only `py_compile` and `ruff`, neither of which validates the `F.cross_entropy(..., label_smoothing=...)` signature; an old torch would raise `TypeError` at runtime and burn a run as a crash. A one-line check of the installed torch version (dependencies are locked and read-only per goal constraints, so this is verify-only) would de-risk before the 600 s launch. Low probability given the modern recipe, but cheap to rule out.
