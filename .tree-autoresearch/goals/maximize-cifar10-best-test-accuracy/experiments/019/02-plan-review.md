Concern list for `experiments/019/02-plan.md` (hardest first):

1. **Import-safety of the production GC helper is unaddressed (Milestone 3 bullet 2, Code Changes "official-order transformation", Verification steps 3–4).** The preflight/smoke scripts in `/tmp` are required to "import and call the exact production GC helper" from `train.py` after inserting the repo root into `sys.path`. If `train.py` is a flat script (as CIFAR speedrun baselines typically are), importing it executes the full training pipeline — GPU allocation, data loading, and a training run — inside the preflight. Making it importable requires adding a `__main__` guard or module restructure, which appears nowhere in the Code Changes section. Either the plan silently depends on an unverified property of the current `train.py`, or it implies a structural refactor larger than the stated scope ("official-order transformation, audits, summary only") with its own risk to startup/charged-time semantics. The plan must state which, and add the guard restructure to Code Changes and the smoke checks if needed.

2. **Novel in-run integrity assertions gate a one-shot metric run but are never exercised at production scale (Milestone 4, Abort Criteria ¶3, Verification step 5).** `gc_calls == num_steps`, path-count reconciliation, and audit-row reconciliation are enforced as hard terminations during the sole permitted metric launch, but the smoke covers two steps and the preflight ~1,000–2,000 steps — neither exercises the budget-exit boundary (a step where the time budget expires between backward and optimizer step, or a final partial epoch) where a counter can legitimately diverge by one. Milestone 3's single-repair allowance applies only to the preflight harness; a bookkeeping off-by-one during the metric run terminates the leaf permanently, converting an accounting bug into a definitive scientific failure. The reconciliation logic at budget exit needs to be specified (and smoke-tested) explicitly, or the assertion demoted to a recorded integrity field evaluated post-hoc.

3. **"Identical final allocation" with zero tolerance is a permanent-kill condition on a one-shot decisive preflight (Milestone 3 bullets 2–4, Abort Criteria ¶2, Verification step 4).** The preflight requires byte-identical persistent allocation after 1,024 candidate steps, and any "complete numeric failure" is final with no rerun. CUDA caching-allocator behavior (cuBLAS/cuDNN workspace growth, autotune re-plans, lazy kernel-module loads) can grow reported allocation without any retained tensor — EXP018 observed exact constancy once at 1,056 steps, which does not bound this failure mode for a different op mix (17 new reductions + 2 foreach ops). A benign allocator event would then permanently abort a scientifically sound leaf. Define a small tolerance or classify allocation-only deviations as the repairable-harness category rather than complete-numeric failure.

4. **Plan-arithmetic inventory constants are wired into leaf-abort criteria (Milestone 1 bullet 1, Code Changes "inventory", Abort Criteria ¶1).** The exact figures — 17 tensors, 2,745,264 elements, 2,266 rows, 3,626 excluded elements — are derived on paper, not measured from the constructed model, yet "inventory/reconciliation mismatch" is listed as a stop-the-leaf condition. If the plan's row/element arithmetic for this specific WRN variant (e.g., shortcut-conv count) is off, the experiment dies for a spreadsheet error while the mechanism is fine. The plan should distinguish "measured inventory contradicts the *shape* of the eligibility rule" (abort-worthy) from "measured counts differ from the plan's precomputed integers" (correct the constants pre-metric, document, proceed).

5. **The throughput projection gate freezes constants from one realized EXP002 run (Verification step 4, Abort Criteria ¶2).** `projected_total_seconds = 300 + 1.2 + projected_epochs*((467.1-300-1.2)/144)`, `27950/R`, 195 steps/epoch, and the 0.375/0.375/0.25 phase weights all assume EXP002's single-run startup, eval overhead, and phase mix reproduce exactly. Because the preflight is decisive and non-rerunnable, a projection miss in either direction is consequential: a marginal candidate could be finally aborted on a formula artifact even though the actual run has its own hard 600 s timeout and ≥27,000-step floors are, by the plan's own ¶4, "dose context, not extra goal conditions." The projection thresholds duplicate protections the metric run already enforces while adding an irreversible failure surface; the plan should justify why projection failure must be leaf-final rather than informational.

6. **Evidence-destruction ordering is ambiguous (Milestone 4 bullet 2 vs Verification step 6).** Milestone 4 requires transcribing the summary into `03-execute.md` "before deleting raw evidence," while step 6 sequences "adversarial result audit and raw-log cleanup" after transcription without pinning whether the audit reads `run.log` or only the transcript. If deletion precedes the audit, the audit verifies the transcript against itself and cannot catch transcription errors in the very numbers (best_test_acc, gc_calls, energy fractions) that decide the verdict. State explicitly that `run.log` survives until the result audit completes.

7. **The metric-run command omits `PYTHONPYCACHEPREFIX` while step 5 re-checks "only tracked `train.py` changed" including untracked files (Execution Environment, Verification step 5).** If `train.py` becomes importable (concern 1) or imports repo-local modules, the metric run can drop a `__pycache__` directory in the repository, and `git status --porcelain --untracked-files=all` would then fail the scope check spuriously after an otherwise valid run. Either apply the pycache prefix to the metric command too or exempt bytecode caches explicitly in the scope check.
