Concern list for `experiments/013/02-plan.md` (hardest first):

1. **[Milestone 4, bullet 2 — early trace] The review-mandated early-progress observability is not actually delivered at the timescale that matters.** The idea review (01-idea-review.md, point 6) required distinguishing a slow-start failure (sharp scale-40 softmax vs CutMix under a wall-clock budget) from a flat-transfer failure via progress checkpoints "at 25%/50% progress vs parent." The plan's paired trace covers steps 1/25/50/100/200 — roughly the first 2–4 seconds of a ~25,800-step run — and no parent loss trajectory at matched mid-run progress exists anywhere durable (EXP-011's `run.log` was deleted per protocol; only summary statistics were transcribed). If the run lands below 95.71, the plan cannot attribute the miss to early-optimization drag versus null geometric effect, which is precisely the diagnostic the review made a condition of adopting this idea. Either preregister mid-run comparison points the durable EXP-011 record can support, or state explicitly that this attribution is out of reach.

2. **[Milestones 3–4 / Abort Criteria — missing terminal classification for pre-metric aborts] The plan never says what tree outcome an abort before the metric run produces.** Milestone 6 classifies only metric-run outcomes. If the timing gate fails (ratio >1.03, projected steps <25,000), a correctness assertion fails un-fixably, or the "nonfinite early trace" abort fires, the plan is silent on whether that is a recorded crash/no-improvement node or a quiet abandonment. Combined with the accuracy-adjacent information in the early CE trace, an unclassified abort is a "free look" exit channel: the experiment observed candidate training behavior on real data and then vanished without a recorded verdict. Preregister the verdict an abort maps to (per tree semantics every experiment gets a row) so this path can't be used selectively.

3. **[Verification Procedure step 4 vs Milestone 4 — the 300-second preflight timeout collides with the no-rerun rule.] `timeout 300s` must cover model/dataset setup for two arms, ≥50 warmups, the 200-step paired early trace, and five rounds × two arms × (≥500 ordinary + 200 CutMix + 100 SAM steps + ≥200 eval forwards + EMA cadence/swap work).** At the measured 10/20 ms step costs that is ≥110 s of steady-state measurement alone, plus tens of seconds of CUDA/dataset startup — a plausible overrun, not a tail risk. Milestone 4 says "the first complete measurement is decisive with no timing rerun," but does not define whether a harness killed by its own outer timeout counts as a (failed) measurement or as no measurement. As written, an infrastructure timeout either dead-ends the experiment or invites a discretionary rerun the plan claims to forbid. Set the timeout from the workload arithmetic and define the infra-failure case explicitly.

4. **[Milestone 4, bullet 4 vs Milestone 6, bullet 4 — the step gate knowingly admits runs that will miss the mechanism floor.] The preflight passes at projected ≥25,000 steps, but mechanism support requires ≥25,300 realized steps — and the goal's own learnings record that paired projection overpredicts realized dose (EXP-012: projected 25,595 → realized 25,376, −219).** A candidate passing preflight at, say, 25,050 projected steps is near-certain to under-dose, reproducing exactly the EXP-012 outcome where the causal conclusion was voided while the formal verdict burned the experiment. If mechanism interpretability is a stated deliverable (Milestone 6 spends a bullet on it), the feasibility gate should be ≥25,300 plus the observed ~220-step projection bias, or the plan should state up front that it accepts running in the known under-dose band.

5. **[Milestone 1, bullet 2 — freeze/filter ordering is unpinned, and the smoke may not exercise production construction order.] `sam_parameters` is built in `main()` via the `requires_grad` filter (train.py:732), and `sam_perturb` hard-fails on any grad-less parameter (train.py:177-179).** The plan says the bias is "excluded through the existing `requires_grad` SAM filter" but never pins where `requires_grad_(False)` executes. If it lands in `main()` after line 732 rather than inside model construction, the first SAM step — at 75% progress, ~225 charged seconds in — raises, converting the sole metric run into a crash. Milestone 3's SAM smoke says "production-faithful" but is a harness re-implementation; it can pass with its own construction order while `main()`'s order is broken. Pin the freeze location (in `__init__`, per the proposal) and make one smoke assert against the module's actual `main`-path construction sequence, not a harness replica.

6. **[Milestone 6, bullet 2 / Code Changes — `num_params` summary semantics left ambiguous.] The plan requires the run to report both "stored parameters 2,748,890" and "trainable parameters 2,748,880," which forces a summary change, but never pins which count the existing `num_params:` line (train.py:984, fed by line 706) reports.** The goal's informational-metric schema and every prior node's TSV row use `num_params` = all stored parameters. If the implementer redefines it to trainable-only, cross-node comparability of the frozen summary silently breaks; the verification step that checks parameter counts would even pass. Specify: `num_params:` stays 2,748,890 and the trainable count goes on a new, separately named line.

7. **[Milestone 2, bullet 2 — per-epoch norm audit gated on "restoration" would drop the pre-EMA trajectory.] The audit is specified as running "after each existing once-per-epoch evaluation and online-state restoration," but for the first ~100 epochs the evaluation source is live and no restoration occurs (train.py:505-507).** Read literally, the audit could be implemented only on EMA-source epochs, discarding the early row-norm trajectory — which is the majority of the weight-decay radial-shrinkage window the review demanded observability for (01-idea-review.md, point 7). State that the audit runs after every evaluation regardless of source.

8. **[Milestone 4, bullet 2 — "same real training batches" replication is asserted, not specified.] The paired trace requires bit-identical batches, CutMix decisions, and drop-path RNG across two arms, but real batches come from an 8-worker shuffled `DataLoader` whose order and per-worker crop/flip streams derive from global seeding at loader construction.** Replaying them identically for both arms requires either caching materialized batches or constructing two identically seeded loaders and consuming them in lockstep — the plan specifies neither, and a subtly divergent replication would make the recorded parent/candidate CE deltas (the trace's whole output) meaningless while still "passing" as informational. One sentence pinning the replication mechanism closes this.
