Review complete. Below is the prioritized concern list for `experiments/021/02-plan.md`.

**1. Undefined verdict for a completed run that fails a "planned execution condition" — Milestone 4 / Abort Criteria (lines 27–28, 53).**
The plan makes ≥24,000 steps and charged time in [299.5, 301.0] hard "Require" items for the metric run, forbids any retry, but never states what verdict a violating-yet-completed run receives. Line 53 says a sub-24,000-step run "fails the planned execution condition but cannot authorize a metric retry" — and stops there. If the run finishes at 23,900 steps with `best_test_acc` 95.55%, the executor is free to classify it either as improvement (accepting a result outside the preregistered execution envelope — the reward-hacking direction, since the goal's necessary conditions at `01-definition.md:27-30` would be nominally satisfied) or as failure (discarding a genuine gain). Same ambiguity for a charged-time reading of 299.4 or 301.1. The plan must pin the classification for every gate-fail × accuracy combination before launch, or this becomes a post-hoc judgment call on the single non-retryable data point.

**2. Exact-count audit machinery elevated to non-retryable hard integrity gates — Milestones 2–4 (lines 13–16, 27, 50).**
The plan requires *exact* reconciliation of primary calls, replay calls, head calls, path counts, and audit samples, and declares any counter failure a structural integrity failure that invalidates the run with no retry. This bookkeeping is new code with its own bug surface, and the plan itself contains a latent off-by-one: Milestone 2 samples "at one-based step 1 and every 512th primary call" while the preflight (line 86) engineers step IDs to contain "exactly one cadence-512 feature sample" per 512-step round — so the production expected sample count (1 + floor(primary/512)) is never stated, and the preflight deliberately avoids exercising the step-1 sample path. Similarly, "primary calls equal completed steps, replay calls equal applied SAM steps" (line 13) leaves ambiguous which SAM pass (ascent vs descent) increments which counter. A bookkeeping bug here converts a scientifically valid 95.5%+ run into an unretryable integrity failure. Either the expected values must be written down as closed-form formulas pre-launch, or counter mismatches should be demoted from run-invalidating gates to audit findings.

**3. Milestone 2's audit apparatus exceeds what the chosen idea requires — Milestone 2 / Code Changes (lines 13–16, 33).**
The chosen idea is a 1,290-parameter head plus one loss term. The plan adds materially more new `train.py` code for diagnostics than for the mechanism: call counters with per-evaluation invariance checks, device-scalar loss accumulators, four-bin quartile-routed norm sampling, initial-parameter snapshots and displacement reporting, and ownership reconciliation — all executing inside the charged region of the sole metric run. The brainstorm's review (`01-brainstorm.md:81`) asked only that "sparse pooled stage-2 feature norms must be reported." Everything beyond that is unrequested scope whose only effects are added crash/gate-trip risk (see concern 2) and charged-time overhead that eats the very step budget the hypothesis depends on. The plan should justify or cut each audit that goes beyond the brainstorm's conditioning requirement.

**4. Smoke and preflight presuppose an importable-helper structure and an executable in-memory parent harness that the Code Changes section never accounts for — Verification steps 3–4 (lines 80, 86).**
Step 3 imports "the exact production helpers through the existing main guard" and "replace[s] the import-created evaluator before iteration"; step 4 executes "byte-exact parent source from `1a8de` in memory" as a paired timing arm. If EXP004's `train.py` does not already expose these seams, satisfying this protocol requires restructuring `train.py` — a change absent from the Code Changes section (line 31–33 list only companion constants, forward/loss contract, and audits) and one that can silently reorder RNG consumption or module construction. Additionally, the decisive gates (median ≤1.03, p90 ≤1.06, projected `floor(25560/R)` steps) are measured on a harness reconstruction — fixed 209/205/49/49 path mix, from-initialization weights, fixture data — not production execution, and the only bridge to reality is a parent-drift check of ≤5%, which is looser than the 3% ratio gate it is supposed to protect. A candidate that is 4% slow in production could pass a preflight whose parent arm ran 4% fast. State explicitly what refactoring (if any) the import contract requires, and tighten or justify the drift bound relative to the ratio gates.

**5. Self-judged rerun escape hatch on the "decisive" preflight — Milestone 3 / Abort Criteria (lines 22, 51).**
The preflight is framed as one-shot, but "one rerun only for demonstrated harness/environment invalidity" leaves "demonstrated" undefined and makes the executor both claimant and judge. Since the gates sit near plausible measurement noise (1.03 median, 1.06 p90), a first vector that narrowly fails creates pressure to find an "invalidity" (thermal state, stray process, allocator warm-up) and take the second attempt — gate-shopping with extra steps. The plan should enumerate in advance the only conditions that qualify as harness/environment invalidity (e.g., nonzero exit of the harness itself, GPU UUID mismatch, external process on GPU 0), and require that a rerun triggered by anything else inherits the original vector's verdict.

**6. "Diagnostics remain inside charged work where applicable" leaves the charged-timer boundary open — Code Changes (line 33).**
"Where applicable" is the only specification of which new operations are charged. Any companion or audit work placed outside the charged region (e.g., deferred host-side reduction of the loss accumulators, displacement computation before the timer stops) understates the mechanism's true cost against the fixed 300-second budget — the exact measurement the preflight gates and the step-count requirement are built on. The plan should enumerate every new operation and assign it explicitly to charged or uncharged time, and the preflight's timed region must match that assignment exactly.
