Concern list for `02-plan.md` (EXP-002, Front-Loaded Probabilistic CutMix), hardest first:

1. **Loss-weighting orientation is unverifiable by the stated smoke check (Milestone 2; Code Changes, `cutmix_batch`).** The check requires only `0 < adjusted_lambda < 1`, shape preservation, and "paired-target alignment" (undefined). A swapped correction — returning `patch_area/(H·W)` instead of `1 − patch_area/(H·W)` as the weight on `targets_a` — passes every listed assertion, and Beta(1,1)'s symmetry does not neutralize it: for any given batch the pixels are mostly original while the loss would weight the permuted label, systematically mistraining the eligible 75% of the run. The smoke check must assert the identity `adjusted_lambda == 1 − clipped_area/(H·W)` numerically and include a degenerate case (zero-area rectangle → lambda ≈ 1, loss reduces to plain CE on `targets_a`) to pin orientation.

2. **CutMix work is not pinned inside the charged-time window (Code Changes, "Before the forward pass"; Milestone 1 "timing boundary").** `train.py` charges the budget between `t0 = time.time()` (train.py:237) and the post-`synchronize` timestamp (train.py:262-265). "Before the forward pass" is compatible with placing the lambda/gate draws, permutation, and patch copy before `t0` — or in a collate/dataloader path — which would take the CutMix compute for free against the fixed 300 s budget, an execution-level accounting hack. The idea review explicitly required the work stay inside the timed region; the plan drops that requirement. Verification step 6 checks only `training_seconds` totals, which cannot detect misplacement. The plan should state that all CutMix operations execute after `t0` and before the synchronize, and structural verification should confirm in the diff that lines 237 and 262-265 are byte-unchanged.

3. **Rectangle size is never derived (Code Changes; Configuration Changes "CutMix geometry").** The plan says "draw one CPU lambda and rectangle center, compute a shared clipped rectangle" but never specifies how the rectangle's side length comes from lambda (standard CutMix uses side = `sqrt(1−λ)·W/H`). Because the area-correction step makes any geometry self-consistent with the loss, an arbitrary or fixed-size rectangle would silently pass all verification while making the "Beta(1,1)" claim in the config line and hypothesis false — the realized lambda distribution would be something else entirely. The derivation must be stated so the implementation and the hypothesis actually match.

4. **"Preserve every … seed" is not achievable as stated and the plan should not claim it (Milestone 1; Configuration Changes "All EXP-001 settings remain fixed").** The CPU Bernoulli/lambda draws consume the global CPU generator that also seeds the DataLoader's per-epoch shuffle and worker augmentation streams; `torch.randperm` on device consumes the CUDA generator shared with drop-path masks (train.py:80-85). Seed 42 is kept, but the shuffle order, crop/flip realizations, and drop-path masks all diverge from EXP-001 from the first batch. This is permitted (not seed rerolling), but the plan's preservation claim overstates isolation: any verification or later analysis that treats non-CutMix behavior as identical to the parent is wrong, and the attribution of a gain is CutMix-plus-perturbed-RNG-streams, not CutMix alone. State this explicitly rather than implying bitwise-preserved randomness.

5. **The helper smoke check's mechanism is unspecified and has side effects (Milestone 2).** Importing `train.py` to exercise `cutmix_batch` executes module-level `evaluator = Eval()` (train.py:30), which constructs the test dataset and an 8-worker DataLoader before any check runs; the plan doesn't say how the "inline" check is run (a `python -c` snippet, a heredoc, a temp file) or that it must not write tracked files or touch GPU state ordering ahead of Milestone 3's clean run. As written, "helper smoke check fails" (Abort Criteria) has no concrete procedure to fail.

6. **NaN monitoring depends on a print path that mostly lacks newlines and lags 50 steps (Milestone 3; Abort Criteria).** The pattern `loss: (nan|inf)` can only match the progress line, which prints every 50 steps with `end=""` and `\r` (train.py:280-288) — so run.log accumulates one very long physical line per epoch, broken only by eval prints roughly every ~2 s of charged time. `grep` on that file works but a NaN is visible only after up to 50 steps and only once a newline lands; more importantly, a NaN arising in the last partial epoch's progress chunk shares a physical line with earlier healthy output. The abort grep should either tolerate this (e.g., `tr '\r' '\n'` before grepping) or the plan should accept detection latency explicitly instead of implying prompt NaN aborts.

7. **Two structural checks in Verification step 6 have no parse procedure.** "Evaluation count <= num_epochs" and "a final evaluation on the budget-ending epoch" name no command; the summary lacks an eval-count key, so these must come from counting `eval ep` lines and matching the last `eval ep N` against `num_epochs`. Also note "evaluation count ≤ num_epochs" is the correct direction for catching extra evals but the plan never states the counting command, leaving the once-per-epoch hard constraint verified only by intent.

8. **CUTMIX_END and DROP_PATH_DECAY_START coincide at 0.75 (Configuration Changes).** At the same instant CutMix switches off, drop-path annealing begins (train.py:151-154). This is the declared design, but the plan nowhere acknowledges that any observed late-phase accuracy dynamics confound the two transitions — worth one sentence so the later analysis doesn't attribute the final-quarter behavior to the clean phase alone.
