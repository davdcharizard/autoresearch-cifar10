Reviewed the plan against the goal definition, brainstorm, proposal idea-01, and current `train.py` (parent EXP-004 at `1a8d0de`). Concern list follows.

**Adversarial review — EXP-011 plan concerns (prioritized)**

1. **Self-serving preflight rerun clause (Abort Criteria; Verification step 4).** "First valid measurement is decisive" is undercut by "at most one complete preflight rerun is allowed only if first-run parent round medians drift >7.5%." Drift is never defined relative to a reference: >7.5% between the five parent rounds? Against EXP-004's historical throughput (not preregistered anywhere in the plan)? Because the rerun decision is made *after* seeing whether the 1.02x gate passed, an ambiguous drift criterion is a retry-until-pass lever on the single gate that decides whether the metric run happens. Preregister the exact drift statistic (which medians, compared to what, computed how) before running the benchmark, and require the rerun decision to be derivable from parent-side numbers alone.

2. **The "bitwise live restoration proof" is tautological as specified (Milestone 2; idea-01 §Single-Model Evaluation Swap).** The check compares model tensors against the `eval_restore` snapshot immediately after copying that same snapshot back, driven by the same name-keyed list used for the copy. Any tensor missing from that list is silently corrupted by the EMA copy-in, never restored, and never compared — the check cannot fail on exactly the failure mode it exists to catch. The only real guard is the Milestone-1 coverage assertion, and the plan does not state what it asserts coverage *against*. Require the restore comparison (or at least the coverage assertion) to enumerate a freshly materialized `model.state_dict()` key set, not the shared shadow list, so a coverage gap trips an assertion rather than poisoning all post-swap training.

3. **The 180-second preflight timeout is unreconciled with the mandated workload (Milestone 3; Verification step 4).** The benchmark must run five alternating parent/candidate rounds, ≥200 ordinary + ≥100 production-faithful SAM iterations (per idea-01), enough tail pairs for ≥30 cadence-31 updates (≥930 steps — and it is ambiguous whether that is per round or total), a separate swap/evaluate/restore benchmark against the frozen evaluator, two model constructions, cudnn-benchmark autotune warmup, and *two* module imports that each execute the top-level `evaluator = Eval()` in `train.py:38` (whatever test-set loading that entails, twice). At ~12ms ordinary / ~25ms SAM steps this plausibly exceeds 180s. A timeout kill produces no valid measurement, and the plan defines no handling for that case — it is neither a gate failure nor a permitted rerun trigger. Budget the workload explicitly or raise the timeout, and state what an exit-124 preflight means.

4. **Plan contradicts the proposal on when distance audits run, which changes charged overhead (Milestone 1 line 10 vs idea-01 §Instrumentation).** The plan places "EMA update and consecutive-sample L2 work before the existing CUDA synchronization" — i.e., ~158 full-parameter norm computations charged in-loop — while idea-01 says "compute model-state distances once after charged training" and bans `.item()` during charged time. These are incompatible instructions to the implementer. If the in-loop variant is intended, the plan must say the per-sample L2 results are accumulated as GPU scalars and read only after training (no sync/`.item()` in-loop), and the latency preflight must include this work; if the post-hoc variant is intended, the previous-sample state and Milestone-1 wording are wrong.

5. **`EMA_HALF_LIFE_S=18.75` is hardcoded but labeled "derived" (Milestone 1; Configuration Changes).** Idea-01 derives it as `(1-EMA_START)*TIME_BUDGET_S/EMA_TAIL_HALF_LIVES`; the plan fixes the literal 18.75 alongside `EMA_TAIL_HALF_LIVES=4.0`, silently baking in `TIME_BUDGET_S=300` from `prepare.py`. The same assumption is embedded in the [299.5, 301.0] charged-seconds gate and the 25,200-step floor. If the constant is hardcoded, the redundant `EMA_TAIL_HALF_LIVES` config is dead weight and the "derived" claim in Configuration Changes is false; compute it from the imported `TIME_BUDGET_S` (as the proposal specifies) or drop the derivation claim and assert the assumed budget at startup.

6. **Post-hoc integrity gates on the already-consumed metric run have no defined verdict path (Milestone 5; Verification step 6).** Milestone 5 makes ≥25,200 steps, ≥145 samples, parity-difference ≤1, and zero restore failures *requirements*, while step 6 says mechanism diagnostics "do not override a valid formal improvement unless they expose a hard-constraint/integrity violation." These overlap: a parity count off by two or 144 samples is a Milestone-5 failure but arguably not a goal hard-constraint violation, and the plan never says whether such a run with `best_test_acc ≥ 95.50` is recorded as improvement, no-improvement, or failure. Since the run cannot be repeated ("Below 95.50 is no-improvement, not a retry trigger"), the classification for each integrity-gate failure must be preregistered, or the ambiguity becomes discretionary room to accept or reject a borderline result after seeing the accuracy.

7. **The parent-snapshot import path in the preflight is underspecified against module side effects (Verification step 4).** Loading "exact parent commit 1a8d0de under a unique importlib module" requires materializing the old `train.py` outside the repo and importing it with the repo root on `sys.path` so `from prepare import ...` resolves. Both parent and candidate imports execute module-level code including `Eval()` construction; nothing in the plan requires guarding against accidentally invoking `main()` or asserts that the two modules resolve the *same* `prepare` constants. A mistake here measures the wrong code or crashes at the decisive gate; specify the snapshot mechanism (`git show 1a8d0de:train.py` → temp file), the `sys.path` setup, and an assertion that neither import ran training.

8. **Sample-timestamp definition is internally inconsistent between "pre-batch progress" and "post-step sample time" (Milestone 1 line 9; idea-01 §Preregistered Horizon).** Eligibility uses pre-batch progress and cadence, but the decay timestamp is "the existing accumulated charged time" — which at the sampling point (after `optimizer.step()`, before the `torch.cuda.synchronize()`/`dt` accounting at `train.py:439-442`) still excludes the current step's dt. That is fine and telescoping as idea-01 argues, but the plan's phrase "derive decay ... from accumulated charged time" plus "sample_time" leaves the implementer free to instead read a fresher time after the sync, which would break the telescoping identity the Milestone-3 arithmetic smoke asserts. Pin the timestamp to "the `total_training_time` value used to compute this step's progress" in the plan text.
