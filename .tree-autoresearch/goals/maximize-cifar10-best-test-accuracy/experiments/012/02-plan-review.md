## Adversarial Plan Review — EXP-012 (`02-plan.md`)

Ordered hardest/most-fundamental first. Each item names the plan section it attacks.

---

**1. M6 bullet 3 + Verification step 7 — the tree verdict is decided by the one statistic the plan itself says is not the mechanism claim.**
`best_test_acc` is a max over ~133 evaluations (`train.py:927-928`). The plan makes `>=95.71` the sole controller of the tree verdict and demotes the stable-tail criterion to "record separately." EXP-011's own tail spanned 0.17 (`02-system-understanding.md:22`) and `03-experiment-learnings.md` records selected-run reversals of 0.14–0.29 points. A +0.10 movement of a maximum is therefore inside documented single-run noise, yet it is sufficient to write `improvement` into `04-results.tsv` and make EXP-012 a legal base node for all descendants. Step 7's mitigation — "do not claim Cutout alone caused the delta" — is a wording constraint with no mechanical effect on `tree.sh insert`. This is the plan's primary path to passing verification without advancing the objective.

**2. M6 bullet 3 — `idea-01.md`'s falsification consequence was deleted in transit.**
`proposals/idea-01.md:278-282` states that "a best >=95.71 with last-16 EMA mean below 95.59 … is a selected-maximum success but **falsifies the stable-generalization claim**." `02-plan.md` M6 carries the number upward (95.69) but drops the falsification entirely, replacing it with "record separately." The plan therefore has no outcome that can disconfirm the hypothesis it is testing. `03-experiment-learnings.md` (EXP-011 entry) independently requires carrying the plateau *beside* the best when setting descendant expectations; "record separately" satisfies the letter and not the function.

**3. M6 bullet 3 + Verification step 1 — both thresholds are anchored to a value the parent's own report disowns.**
`experiments/011/04-analysis.md` states the candidate "realized 0.93% more steps than the parent through ordinary run variance" and that "**descendants should not treat it as the stable checkpoint level**." The plan sets 95.71 = 95.61 + 0.10 on exactly that level. Separately, the mechanism target 95.69 vs 95.493125 is **+0.197 points**, which is below the 0.25–0.30 stable effect `02-system-understanding.md:15` says a credible child needs, and below EXP-011's own next-steps guidance ("prioritize mechanisms with plausible effect near 0.3 points"). The plan's two bars are thus simultaneously too easy (max-selected) and set beneath the stated sufficiency criterion (stable).

**4. M4 bullet 4 — the projected-steps gate is keyed to the more permissive of two available parent numbers, and flips on that choice.**
`25798/ratio >= 25500` uses EXP-011's *realized* 25,798. EXP-011's own **preflight projection was 25,570** (`011/04-analysis.md`). Substituting the like-for-like preflight figure gives 25,570/1.01 = **25,317 — a fail**. The plan never states why the realized (variance-inflated, +0.93%) figure is the calibration base. Worse, the gate is non-binding as written: it only bites at ratio > 1.0117, i.e. beyond the 1.01 latency gate that precedes it, so it adds zero independent protection while appearing to.

**5. M4 bullet 4 vs M6 bullet 2 — the preflight gate protects step count at 1%, then verification accepts a 2.3% loss.**
M4 requires ≥25,500 *projected*; M6 accepts ≥25,200 *realized*. 25,200 is below EXP-004's and EXP-006's realized 25,560/25,644 with **no candidate change at all**. A run landing at 25,250 has lost precisely the optimizer exposure the 1.01× gate existed to preserve, passes the dose gate silently, and is then reported as a clean mechanism-negative "no-improvement" — attributing to Cutout a deficit that `03-experiment-learnings.md` ("wall-clock progress makes fixed-seed phase exposure throughput-dependent") says must not be causally attributed.

**6. M4 bullet 4 — a 7.5% parent-drift tolerance gating a 1% candidate decision, plus a rerun rule that is a selection channel.**
Accepting `max/min-1 <= 0.075` on parent-only weighted rounds concedes that harness round-to-round spread may be 7.5× the effect being resolved. The medians reduce but do not characterize this — the plan reports no SE. Additionally, "parent drift is computed before candidate gates and permits at most one full rerun" means a candidate measured at ratio 1.012 is discarded, *unless* the parent drift happened to exceed 0.075, in which case the full harness (including the candidate arm) is re-measured. That is a discretionary second draw whose trigger is uncorrelated with the candidate's own validity.

**7. M5 bullet 3 + Verification step 8 — evidence is destroyed earlier than the protocol requires, by a single non-substitutable reviewer.**
`01-definition.md` procedure step 5 requires removing `run.log` only *before beginning another experiment*. Step 8 removes `run.log`, the parent snapshot, and all preflight artifacts **before analysis**. `03-experiment-learnings.md` records that EXP-010 hit exactly this: Claude "could not re-derive deleted `run.log` or preflight JSON." Combined with M5's "run Claude as the sole adversarial result reviewer … never fall back to another reviewer," the plan specifies no behavior if that reviewer is unavailable, and after step 8 the only surviving record is the same agent's own transcription of numbers it also selected.

**8. M2 bullet 3 + M6 bullet 1 + Verification step 5 — the plan adds a code path whose classification is undefined, on top of one that already exists.**
M2 deliberately creates a state that "prints Cutout diagnostics **before a nonzero exit**." `train.py:985-986` already does this: the complete summary at lines 975-984 prints, then `raise RuntimeError("EMA final audit failed")` exits nonzero. M6 requires "exit 0 … complete summary" (both). Step 5 says "any other nonzero exit is crash unless an integrity signature requires `invalid`." M6 bullet 2 says complement/RNG/state corruption is `invalid` with metric `NaN`. So the single most likely non-success path — full summary printed, audit raised, exit 1 — has three candidate verdicts (crash / invalid / summary-satisfied) and no tiebreak. `01-definition.md` makes a crashed run a failed necessary condition, so this is not cosmetic.

**9. Verification step 4 — the parent-parity assertion cannot fail, and the dual import contaminates the memory gate.**
"Import parent/candidate under distinct non-`__main__` names … **assert identical `prepare` constants**" is vacuous: both modules execute `from prepare import ...` (`train.py:13`) against the same `sys.modules['prepare']` object, so the constants are identical by construction regardless of what the snapshot contains. Separately, `train.py:44` instantiates `evaluator = Eval()` at **module scope** — importing both modules constructs two evaluators (two test-set materializations) in one process, inflating both preflight wall-clock and the peak allocation that M4's 1.30 GiB gate reads. The plan also never states whether the Cutout mask-bank setup lives at module scope or inside `main()`, which determines whether the bank is built once or twice under this import scheme.

**10. M1 bullet 3 vs M3 bullet 1 — the mask bank's dtype and layout are unspecified, and they are what the 1.01× gate measures.**
M1 specifies "one in-place broadcast multiply"; M3 specifies "**Boolean** keep semantics." These are different kernels. At the mutation point the batch is fp32 channels-last (autocast begins at `train.py:820`, after the CutMix block), while the specified `selected` buffer is a contiguous `[256,1,32,32]`. A bool/uint8 bank forces promotion; a contiguous broadcast operand against a channels-last `[256,3,32,32]` tensor will not hit the vectorized path. The plan gates candidate latency at ≤1.01× without pinning the one implementation detail that decides whether that gate passes.

**11. M4 bullet 4 + Abort Criteria — the VRAM ceiling was silently loosened, its measurement point is unstated, and the goal calls it a non-constraint.**
`proposals/idea-01.md:234` specified peak VRAM below **1.25 GiB**; the plan uses **1.30 GiB** with no stated reason. The reason is inferable — EXP-011's preflight peak was 1,277.0 MiB = 1.247 GiB, ~3 MiB under the old gate — but an undocumented threshold move to accommodate the parent is exactly the pattern `03-experiment-learnings.md` (EXP-008) warns about, inverted. The plan also never says whether the ceiling applies to the preflight process or the metric run; those differ by 54.6 MiB in EXP-011 (1,277.0 vs 1,222.4). Meanwhile `01-definition.md` states "VRAM is a soft consideration rather than a pass/fail constraint," yet Abort Criteria makes ≥1.30 GiB blocking. (For reference the new state is ~5 MiB fp32: bank 1,048,576 elements = 4 MiB, `selected` 262,144 = 1 MiB — the plan reconciles it against neither figure.)

**12. Verification step 3 — the scope check does not detect the files the plan is most likely to leave behind.**
`git diff --name-only d68f73a` reports tracked modifications only. It will not list an untracked smoke harness, benchmark script, or JSON dump written into the repository root — precisely the artifacts Code Changes restricts to `/tmp`. A stray `smoke.py` at repo root passes step 3, passes M6's "only `train.py` changed," and is then committed or not depending on the analyze phase's `git add`. The check needs to see untracked state, not just the diff.

**13. M1 bullet 1 + M6 bullet 2 — `CUTOUT_END` as a separate constant invites a decoupling that turns into a stale-variable bug, and the late-call audit cannot fail.**
`apply_cutmix` is assigned only inside `if progress < CUTMIX_END:` (`train.py:800-804`), so it persists across loop iterations. Any implementation that tests `progress < CUTOUT_END and not apply_cutmix` *outside* that block reads the last early batch's value on every late batch. Today `CUTOUT_END == CUTMIX_END` masks this; the plan introduces `CUTOUT_END` as an independently-named constant, which is the only reason someone would later change one without the other. Relatedly, M6's "zero late Cutout calls" audit re-tests the same predicate that gates the code, so it is a tautology, not an independent check.

**14. M1 bullet 2 vs M6 bullet 2 — the realized-area band is ~16σ wide and cannot detect a dose fault.**
M1's "mean masked area **exactly** 196 pixels" is a property of the 1,024-entry bank, provable at setup. M6's runtime band `[195.5, 196.5]` is a property of ~10,512 calls × 256 images ≈ 2.7M draws. Per-image area SD across the bank is 51.9 px (E[L²]=202.75, Var(L)=6.75, Var(area)=2691.6), giving SE ≈ 0.032 px — the band is **±16 SE**. It will pass under any sampling defect short of a gross indexing error, while reading in the verification report as a quantitative dose check.

**15. M6 bullet 2/3 — the mechanism statistic is not held fixed across the two runs being compared.**
M6 accepts ≥145 EMA samples where the parent produced 160 (a ~9% shorter averaging window), and the comparison statistic is "final-16 EMA" — a fixed *count* of epochs whose wall-clock span depends on realized throughput. A candidate with 148 samples and 128 epochs has its "final 16" covering a different fraction of the tail than EXP-011's epochs 118–133 did. The +0.197-point mechanism target is being read off two non-commensurate windows.

**16. Configuration Changes — two framing errors that touch scope and evidence.**
(a) "All parent hyperparameters, including `TIME_BUDGET_S=300`, remain unchanged" lists as a *parent hyperparameter* a value imported from read-only `prepare.py` (`train.py:13`) and protected by `01-definition.md` Hard Constraints; it does not belong in a section titled "Configuration Changes" at all. (b) "direct WideResNet/CIFAR evidence uses size 16" cites `papers/ricap.md:9`, whose table has **no CutMix+Cutout row** — the 3.89%→3.08% figure is a no-CutMix-baseline result, so it bounds nothing about the marginal effect here. This compounds with the plan's own dose framing ("materially below literature all-image Cutout"), which is true per-image but obscures that under the complement rule **zero early batches are left unoccluded** (`idea-01.md:290-291`), with no evidence in the lineage that the parent overfits.
