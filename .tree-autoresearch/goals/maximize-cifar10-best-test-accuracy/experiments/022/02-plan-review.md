Concern list for EXP-022 plan (`experiments/022/02-plan.md`), hardest first:

1. **Hard gates built on unreconciled hard-coded constants (Milestone 3 bullets 3–4; Milestone 5 bullet 2; Verification step 1).** The preflight and validity gates consume many preregistered numbers — the path-mix split `10512/10345/2470/2471`, the `447.9s` total, `195` steps/epoch, parent params `2,748,890`, candidate `3,260,442`/`425,315,136`, and the `[299.5,301.0]` charged-seconds window (which silently assumes `TIME_BUDGET_S=300` without reconciling it from `prepare.py`). Verification step 1 reconciles only steps/evals/EMA-samples/final-16-mean from EXP-011; the four-way path split, the 447.9s total, steps-per-epoch, and the budget are never checked against parent artifacts. A wrong split constant silently mis-weights the decisive timing ratio; a wrong count/window constant triggers a false abort. Combined with the rule that no correction is permitted once "a complete numeric vector exists" (Milestone 3 bullet 5, Abort criteria), a plan-arithmetic typo discovered post-vector unrecoverably kills the experiment. Add a step-1 reconciliation of *every* preregistered constant against EXP-011's report and `prepare.py` before any numeric measurement.

2. **Probable off-by-one in the evaluation-count validity gate (Verification step 6; Milestone 5 bullet 2).** The plan requires `rg -c '  eval ep' run.log == num_epochs` and "exactly one evaluation per epoch," yet step 1 reconciles EXP-011 at 25,798 steps ≈ 132.3 full epochs with **133** evaluations — consistent with an evals = epochs + 1 (final partial-epoch eval) structure. If the parent's own log would fail this exact gate, an honest candidate run gets classified invalid post-hoc, and Milestone 4 forbids any retry. The relation between eval count and `num_epochs` must be derived from the parent's actual log format/summary, not asserted.

3. **The "bounded harness-only correction" boundary is under-specified (Milestone 3 bullet 5; Abort criteria last bullet).** "Demonstrably malformed assertion" vs. "measured failure" is exactly the distinction an executor under pressure will bend: relaxing a gate constant after seeing a near-miss numeric vector is a timing-rerun loophole dressed as a harness fix, while a strict reading kills the experiment on a typo'd constant. The plan should state the discriminator concretely — e.g., a correction may only replace an assertion value provably inconsistent with an independently documented parent fact, may never touch a threshold that a produced measurement failed, and the corrected run must still be the sole numeric vector.

4. **Incidental harness thresholds promoted to terminal abort criteria (Milestone 2 bullets 3–4; Abort criteria bullet 3).** The `<=1 MiB` steady-state live-allocation growth over 30 cadence-31 EMA samples and the `<4096 MiB` peak are assertions about CUDA caching-allocator behavior, not about the hypothesis; the allocator can legitimately grow live-tensor bookkeeping or workspace buffers by more than 1 MiB without any leak. Since assertion failures are abort criteria and only one pre-vector correction is allowed, an allocator flake can burn the experiment's single permitted correction (or the experiment). Justify the 1 MiB figure from parent behavior or loosen it to a leak-detecting bound (e.g., growth per additional 30-sample block) rather than an absolute.

5. **The 40 eval-mode forwards per timing round feed no stated gate (Milestone 3 bullets 3–4).** The four weights cover only the charged training paths, and the conservative-total gate scales EXP-011's *entire* 447.9s (which includes startup and evaluation time) by the training-path median ratio. Either the eval-forward measurements are dead weight, or they inform the total projection through an unstated formula — an ambiguity that invites post-hoc discretion in exactly the phase the plan otherwise locks down. State what consumes the eval timings, or drop them and state the scaling assumption for the 447.9s projection explicitly.

6. **Import-without-`main` assumption is unverified (Milestone 2 bullet 1; Milestone 3 bullet 2).** The whole Milestone-2/3 harness depends on importing both the materialized parent `d68f73a:train.py` and the candidate without triggering training, and on monkeypatching their evaluators. Verification step 8's tool checks cover `uv`/`timeout`/`nvidia-smi`/`rg`/`tree.sh` but not that `train.py` is import-safe (has a `__main__` guard and no side-effectful top level). If it is not, the workarounds needed (partial import, namespace surgery) could make the smokes diverge from production behavior while still "passing," undermining the correctness evidence the metric run's validity classification later leans on. Confirm import safety as an explicit pre-Milestone-2 check.
1. **Scope enforcement**: `git diff --name-only` cannot prove that only the approved width/metadata hunks changed inside `train.py`. Add an exact zero-context diff allowlist and reject all other lines.
2. **Conditioning reward-hacking**: undefined “collapse” could let finite unfavorable diagnostics abort before accuracy. Make every finite conditioning value non-gating and remove qualitative collapse.
3. **Dose projection**: one aggregate `25798/ratio` ignores distinct early CutMix and late SAM path costs. Derive early and late exposure independently from their fixed charged-time windows and per-path ratios.
4. **Evaluation accounting**: exclude uncharged evaluation forwards from optimizer-dose ratios and use their separate ratio only for total-runtime projection.
5. **Harness retry policy**: allowing correction before a complete vector permits data-informed restart after partial ratios. Freeze/hash the harness and make the first timing datum decisive.
6. **Scientific classification**: “stable tail” is undefined. Remove it as a criterion or preregister a numeric definition.
