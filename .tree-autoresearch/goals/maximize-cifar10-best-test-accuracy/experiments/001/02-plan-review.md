Concern list for `02-plan.md` (EXP-001), hardest first:

1. **[Execution Environment / Verification §5] The 600-second outer budget rests on two unmeasured assumptions, and the plan forbids itself every mitigation.** The plan's own arithmetic (`02-plan.md:46`) shows the margin is thin: with 80–105 epochs, per-epoch eval must stay under ~2.1–2.8 s, while BASE's tiny model already cost ~0.85 s/eval — a ~10× FLOPs WRN evaluated in FP32 (per `02-plan.md:31`, eval stays FP32) can plausibly exceed that, and evaluating a channels-last model on the frozen evaluator's contiguous inputs may add layout-conversion cost on top. Yet neither the epoch estimate nor the eval latency is ever measured: the Milestone 2 smoke check (`02-plan.md:15`) tests only one training batch for finiteness — it times nothing and never touches the evaluator. Worse, faster-than-expected training makes this *worse* (more epochs → more evals), and the abort criteria (`02-plan.md:53`) explicitly demote first-epoch eval duration to "diagnostic only," so a run visibly on course to hit the 600 s kill is allowed to run to timeout and burn the single permitted attempt. The idea review's condition #4 asked for an eval-wall-clock check in Verification; the plan added the arithmetic but not the measurement. Fix: extend the smoke check to time a handful of training steps and one full `Eval.evaluate` pass, project `total_seconds`, and make a breach a pre-launch abort (or a documented go/no-go decision).

2. **[Milestone 2] The scope gate runs before the artifact-creating steps it is supposed to police, and the smoke check's mechanism is unspecified.** The `git status --short` / `git diff -- train.py` check (`02-plan.md:13`) precedes the CUDA smoke check (`02-plan.md:15`). If the smoke check is implemented as a scratch script file, it is created *after* the clean-diff gate and nothing re-checks; the abort criterion "working diff includes anything except `train.py`" (`02-plan.md:51`) is evaluated at a moment when it is vacuously true. The plan should pin the smoke check to an inline `python -c` (or equivalent no-file mechanism) and/or repeat the diff check immediately before launch. Note also that any import of `train.py` for the smoke check executes module-level `evaluator = Eval()` (train.py:25), constructing the full test loader — harmless but unaccounted for in the "one-batch" framing.

3. **[Milestone 3 vs Abort Criteria] The mid-run abort triggers are unobservable under the plan's own monitoring protocol.** Milestone 3 (`02-plan.md:19`) commits to monitoring "process liveness without streaming the log," and the Execution Environment (`02-plan.md:47`) restricts log access to "after exit" summaries — yet the abort criteria (`02-plan.md:52`) require aborting on CUDA OOM, illegal memory access, and NaN/Inf loss, all of which are only visible *in* `run.log` while the process is still alive (a NaN run typically keeps running with garbage loss). As written, every mid-run abort except the timeout is dead policy. Either permit bounded periodic greps of `run.log` for `nan|inf|CUDA` during the run, or delete the unenforceable triggers so the executor doesn't improvise.

4. **[Verification Procedure] No structural assertion catches a mis-built model; a wiring bug is indistinguishable from a refuted hypothesis.** The Configuration Changes target ~2.75 M parameters (`02-plan.md:35`), and `num_params` is printed in the summary, but verification steps 4–6 gate only on key presence, timing, and `best_test_acc`; `num_params` is filed under optional informational metrics (`02-plan.md:84`). If the WRN is wired wrong (wrong stage widths, missing blocks, drop-path silently defaulting to zero scale — the plan itself makes zero the default at `02-plan.md:29`), the run passes every necessary condition and a capacity/architecture bug gets recorded as `no-improvement` evidence against the hypothesis. Add a hard expected-range check on `num_params` (and a logged, checked drop-path/LR diagnostic at a known progress point) to the pass/fail procedure, since this single run's verdict feeds the tree permanently.

5. **[Verification Procedure §1] The `tree.sh` path is hardcoded to `/root/david/.codex/plugins/cache/deoxys/tree-autoresearch/0.1.2/...`** (`02-plan.md:60`), while project instructions reference it via `${CLAUDE_PLUGIN_ROOT}` and the working tree lives under `/SPXvePFS/...`. If that absolute cache path is stale or environment-specific, step 1 fails (or silently reads the wrong store) at execution time. Use the plugin-root variable and the repo-relative TSV path.

6. **[Verification Procedure §5] The `training_seconds ≤ 301.0` tolerance is asserted without a rationale tied to the new step time.** The loop charges the full final step before exiting, so overshoot equals one step's `dt`; the bound is only valid if a WRN-16-4 batch-256 step (including any charged `cudnn.benchmark` re-autotune on a shape change) stays under ~1 s. That's probably true, but the plan never states the expected step time this bound depends on — the smoke-check timing from concern 1 would ground it; without it, a healthy run could fail verification on an arbitrary threshold.
