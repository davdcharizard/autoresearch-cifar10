Concern list for EXP-018 plan (`02-plan.md`), hardest first:

1. **Epoch-boundary synchronization is assumed, never enforced at runtime — silent mechanism loss possible with all audits green.** (Milestone 2, bullet 1; Configuration Changes "Evaluation ownership"; Code Changes "slow evaluation") The claim "full 195-step epochs are already synchronized because `195 % 5 == 0`" is a compile-time assumption baked into the design as "swap only at a truncated *final* epoch." If actual steps-per-epoch is not 195 (e.g., loader without `drop_last` yields 196, or the time-aware loop truncates any non-final epoch), every per-epoch evaluation silently measures *fast* weights instead of slow ones, half-disabling the chosen mechanism — and the preregistered reconciliation `actual_syncs == floor(num_steps/5)` (Verification step 5) still passes, because sync *count* is independent of eval alignment. The plan records "steps since sync" (Milestone 2, bullet 3) but nowhere requires it to be zero at each non-final evaluation. Add an explicit per-evaluation assertion `steps_since_sync == 0` (or route through the swap path whenever unsynchronized) as an abort-grade integrity condition, not just a logged diagnostic.

2. **Internal off-by-one contradiction in the sync trigger that no metric-run audit can detect.** Milestone 1 bullet 2 says sync "on one-based steps divisible by five"; Code Changes ("canonical update") says "use the *upcoming* one-based step number to synchronize." If the implementer follows the second wording against a counter incremented after `optimizer.step()`, syncs land after steps 4, 9, …, 194 — the same total count (so `floor(num_steps/5)` reconciliation passes), but step 195 is then *not* a sync point and concern 1 fires everywhere. Protection currently rests entirely on one smoke assertion ("explicit-reference equality at step 5", Verification step 3) in a throwaway `/tmp` script whose harness could itself carry the same off-by-one. Resolve the wording to a single indexing convention and add the first/last-sync step indices as hard metric-run assertions (`first_sync == 5`, `last_sync % 5 == 0`), not just recorded values.

3. **The decisive preflight repeats EXP017's structural failure mode: a complex disposable harness whose first complete numeric vector is final.** (Milestone 3, bullets 3–4; Verification step 4; Abort Criteria bullet 2) The `/tmp` harness must, inside 300 s: extract parent and candidate, guard the evaluator, prove pre-sync parity and fifth-step divergence, run a long production trace, then five alternating paired rounds with ≥30 syncs and a 37.5/37.5/25 workload mix — and one harness defect after the vector prints kills the leaf with no scientific result, exactly how EXP017 ended with GC "untested." Two specific soft spots: (a) "projected steps," "projected epochs," and "projected total runtime <600 s" have no stated derivation (extrapolated from what baseline steps/sec, with what startup constant?), so the decisive gate is currently ill-defined; (b) the gates `median ratio ≤1.01` and `every round ratio ≤1.03` sit at or below the plan's own accepted noise floor (`MAD/median ≤1.5%`), so a single noisy round on a mechanism whose true overhead is ~0 can abort the leaf. Preregister the projection formula and reconcile the per-round ceiling with the declared noise tolerance before calling the vector decisive.

4. **Preflight latency is measured in the `/tmp` harness path, not the charged path of `train.py`.** (Verification step 4 vs. Milestone 1, bullet 3) The cost that actually matters is interpolation + audit work placed "inside the existing timed step before CUDA synchronization" in `train.py`, but the ≤1.01/≤1.03 ratio gates are computed from a reconstructed harness loop with evaluator guards and different surrounding code. A harness that under- or over-charges relative to the real timed region either aborts a viable leaf or admits a candidate that then misses the 27,500-step floor in the sole metric run (which the plan then cannot rerun). The plan should state how the harness's timed region is made structurally identical to `train.py`'s charged step.

5. **Brittle hard-coded constants turn benign environment drift into abort/failure of an otherwise healthy run.** (Milestone 1 bullet 1; Verification step 5) `44` tensors, `2,748,890` elements, `training_seconds ∈ [299.5, 301.0]`, and `195` steps/epoch are all asserted as exact facts rather than read from the parent at runtime. The element/tensor counts are safe-fail (abort before metric), but the `[299.5, 301.0]` window is applied *after* the one permitted metric run: if the inherited timing loop legitimately lands at, say, 300.2→301.3 due to charging the new audit work, the plan classifies a valid run as an integrity failure with no rerun allowed. State what happens to the verdict when only the timing-window condition fails — currently the plan conflates "measurement integrity" with "budget compliance," and the goal only requires respecting the fixed budget.

6. **`torch._foreach_lerp_` / `torch._foreach_copy_` are private APIs with no stated fallback.** (Code Changes "canonical update") Availability/signature varies across torch versions; the plan pins the exact calls into the canonical update. The smoke test would catch absence, but the plan never says whether fixing `train.py` after a smoke failure is permitted (the single-repair rule is scoped to the preflight harness only, and Abort Criteria bullet 1 lists syntax/RNG failures as leaf-stopping). Explicitly allow a pre-preflight `train.py` correction for API availability (with a plain `lerp_`/`copy_` loop fallback), or the plan risks aborting on a triviality.
