Concern list for `experiments/010/02-plan.md`, hardest first:

1. **[Milestone 3 / Abort Criteria — preflight repeat loophole on the binding gate]** The 1.05x median gate is the experiment's real gate (`27950/ratio >= 26500` implies ratio ≤ 1.0547, so 1.05x binds), yet the contamination rule — "may be repeated only if parent alternating-round medians drift by more than 7.5%" — has no cap on repetitions and no pre-registered definition of contamination beyond that drift number. A near-miss candidate (e.g. 1.06x) invites declaring drift and re-measuring until a favorable round passes. Fix: bound repeats (e.g. one re-measurement), require the drift evidence to be recorded before rerunning, and state that the *first* valid measurement is decisive.

2. **[Milestone 2 — equivalence procedure is underspecified in ways that make it fail or pass vacuously]** The bitwise state-dict/RNG/output comparison against a `a36dc09` import ignores that `train.py` executes `evaluator = Eval()` at module scope (train.py:34): both imports run `Eval()` side effects, imports of two same-named modules need explicit importlib handling, and whether `torch.manual_seed(42)` is applied before or after each module's import-time RNG consumption is unstated — the "global RNG state after construction" comparison is meaningless without a pinned reseed point. Also no device is specified for the "bitwise" forward comparison; on GPU with `cudnn.benchmark` autotuning, bitwise equality can legitimately fail. Since any equivalence failure is a hard abort (Abort Criteria bullet 3), an artifact of the harness kills the experiment. Pin: reseed immediately before each construction, CPU FP32 eval-mode forward, explicit importlib procedure.

3. **[Milestone 4 / Abort Criteria — the 90 s no-output / 120 s no-progress kill can destroy the single allowed metric run]** Stdout is redirected to `run.log`, so Python block-buffers; the only `flush=True` is the step-progress print at step 50 (train.py:353-362), and eval lines are unflushed. Startup (dataset load, cudnn autotune of a *new* architecture, first epoch) plus buffering can plausibly exceed 90 s with nothing in `run.log`, and the plan mandates "launch exactly once" — a false-positive stall kill leaves no retry path and no rule for what happens after one. Either monitor the process (CPU/GPU activity) rather than log bytes, lengthen the windows using parent EXP-002's measured `startup_seconds`, or explicitly permit one relaunch after a stall kill with no code change.

4. **[Milestone 5 / Verification step 6 — secondary post-hoc gates stricter and vaguer than the goal, with no defined outcome on partial pass]** The goal's necessary conditions are +0.10 over parent, clean completion, budget respected, full summary. The plan adds hard post-hoc requirements — `num_steps >= 26500`, "charged training near 300 seconds", "CutMix exposure near its fixed 0.5 gate" — with "near" undefined and no rule for the case `best_test_acc >= 95.33` but steps land at, say, 26,400 because real steps include dataloader/host overhead the synthetic preflight (pure GPU compute) never measured. As written this either forces discarding a genuine improvement or invites ad-hoc reinterpretation at verification time. Pre-commit numeric tolerances and state explicitly which gates are fail-the-run versus informational.

5. **[Code Changes / Milestone 3 — harness location vs import mechanics unresolved]** Harnesses "may exist only outside the repository," but they must `import` the modified `train.py`, which does `from prepare import DATASET_DIR, ...` and instantiates `Eval()` — all of which assume repo-root cwd/sys.path and repo-relative dataset paths. Run from outside the repo without a specified cwd/sys.path convention, the preflight can crash or silently trigger a dataset download inside the timed 180 s preflight window. Specify: harness file lives outside the repo but executes with cwd = repo root (Verification step 4's `uv run python -` from repo root satisfies this — make it explicit for Milestone 2's harness too).

6. **[Milestone 1 / Code Changes — parameterization is broader than the idea requires]** The chosen idea needs only the six-tuple block spec changed to the 1-2-3 layout; the plan instead ships a general stage-allocation constructor parameter (`stage-block tuple` argument, `STAGE_BLOCKS`/`STAGE_WIDTHS` generation machinery) into production `train.py` whose only consumer of the `(2,2,2)` path is the throwaway equivalence harness. That is test scaffolding permanently embedded in the measured artifact and a mild scope expansion beyond "implement the isolated architecture change." If kept for equivalence testing, the plan should say the parameter is retained solely for that purpose or have Milestone 5 confirm the final diff is the minimal generation logic with no dead configuration paths.
